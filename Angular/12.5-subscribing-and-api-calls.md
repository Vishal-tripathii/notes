<a name="service"></a>
# 1. Where Observables come from: the service

Every HTTP call starts here. The service **returns** the Observable — it does not subscribe.

```ts
@Injectable({ providedIn: 'root' })
export class EmployeeService {
  private http = inject(HttpClient);
  private url = '/api/employees';

  getAll(): Observable<Employee[]> {
    return this.http.get<Employee[]>(this.url);
  }

  getById(id: number): Observable<Employee> {
    return this.http.get<Employee>(`${this.url}/${id}`);
  }

  create(emp: Omit<Employee, 'id'>): Observable<Employee> {
    return this.http.post<Employee>(this.url, emp);
  }

  update(id: number, emp: Partial<Employee>): Observable<Employee> {
    return this.http.put<Employee>(`${this.url}/${id}`, emp);
  }

  delete(id: number): Observable<void> {
    return this.http.delete<void>(`${this.url}/${id}`);
  }
}
```

**The rule: services return, components subscribe.**

If the service subscribes internally, the caller can't cancel it, can't handle its errors, and can't compose it into a pipe:

```ts
// ❌ the service subscribes — nobody else can control this
getAll() {
  this.http.get<Employee[]>(this.url).subscribe(data => this.data = data);
}
```

<a name="subscribe"></a>
# 2. `.subscribe()` — the full form

```ts
this.employeeService.getAll().subscribe({
  next:     (employees) => { this.employees = employees; },
  error:    (err: HttpErrorResponse) => { this.error = err.message; },
  complete: () => { console.log('stream finished'); },
});
```

```
next      → called for EVERY emitted value (HTTP: exactly once)
error     → called on failure. TERMINAL — next/complete never fire after
complete  → called when the stream ends. TERMINAL
```

The shorthand only gives you `next`:

```ts
this.employeeService.getAll().subscribe(employees => this.employees = employees);
// ⚠️ an HTTP failure here becomes an unhandled error in the console
```

For HTTP, `complete` fires immediately after `next` — one value, then done. That's why you rarely see it used.

<a name="vs-promise"></a>
# 3. ⭐ Promise vs Observable — the same call, both ways

```ts
// ───── PROMISE (plain fetch) ─────
loadEmployees() {
  this.loading = true;

  fetch('/api/employees')
    .then(res => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json();
    })
    .then(employees => { this.employees = employees; })
    .catch(err => { this.error = err.message; })
    .finally(() => { this.loading = false; });
}

// ───── OBSERVABLE (HttpClient) ─────
loadEmployees() {
  this.loading = true;

  this.employeeService.getAll().pipe(
    finalize(() => this.loading = false),      // ≈ .finally()
  ).subscribe({
    next:  employees => this.employees = employees,   // ≈ .then()
    error: err => this.error = err.message,           // ≈ .catch()
  });
}
```

The mapping:

```
.then(fn)       ≈  next: fn        (but next can fire many times)
.catch(fn)      ≈  error: fn   or  catchError() in the pipe
.finally(fn)    ≈  finalize()  in the pipe
await           ≈  firstValueFrom()
(no equivalent) ←  unsubscribe() — cancellation
```

Two real differences beyond syntax.

**Angular parses JSON and throws on 4xx/5xx for you:**

```ts
this.http.get<Employee[]>('/api/employees')   // already typed, already parsed
fetch('/api/employees')                       // a 404 is a "successful" fetch —
                                              // check res.ok and call res.json() yourself
```

**Cancellation has no Promise equivalent:**

```ts
const sub = this.employeeService.getAll().subscribe(…);
sub.unsubscribe();   // the HTTP request is actually aborted
```

<a name="async-await"></a>
# 4. When you want async/await

Sometimes a promise reads better — sequential steps in a guard, resolver, or app initialisation:

```ts
async loadDashboard() {
  try {
    const user  = await firstValueFrom(this.userService.getCurrent());
    const perms = await firstValueFrom(this.authService.getPermissions(user.id));
    this.setup(user, perms);
  } catch (err) {
    this.error = 'Failed to load dashboard';
  } finally {
    this.loading = false;
  }
}
```

```
firstValueFrom(obs$)   resolves with the FIRST value, then unsubscribes
lastValueFrom(obs$)    waits for completion, resolves with the LAST value
```

For HTTP they're equivalent (one value, then complete). Use `firstValueFrom`.

⚠️ `toPromise()` is deprecated — it resolved `undefined` on an empty stream, silently.

⚠️ Converting loses cancellation. Two sequential `await`s can't be aborted; a `switchMap` chain can.

<a name="consuming"></a>
# 5. ⭐ The three ways to consume

## (a) `subscribe()` — imperative, most control

```ts
export class EmployeeListComponent implements OnInit {
  private service    = inject(EmployeeService);
  private destroyRef = inject(DestroyRef);

  employees: Employee[] = [];
  loading = false;
  error: string | null = null;

  ngOnInit() { this.load(); }

  load() {
    this.loading = true;
    this.error = null;

    this.service.getAll().pipe(
      finalize(() => this.loading = false),
      takeUntilDestroyed(this.destroyRef),
    ).subscribe({
      next:  data => this.employees = data,
      error: (err: HttpErrorResponse) =>
        this.error = err.status === 404 ? 'Not found' : 'Something went wrong',
    });
  }
}
```

## (b) `async` pipe — declarative, no cleanup

```ts
employees$ = this.service.getAll().pipe(
  catchError(() => { this.error = 'Failed to load'; return of([]); }),
);
```

```html
@if (employees$ | async; as employees) {
  @for (e of employees; track e.id) { <app-employee-card [employee]="e" /> }
} @else {
  <app-spinner />
}
```

No `ngOnInit`, no `ngOnDestroy`, no leak possible.

## (c) `toSignal()` — declarative, in the class

```ts
employees = toSignal(this.service.getAll(), { initialValue: [] });
```

```html
@for (e of employees(); track e.id) { … }
```

Same benefits as the `async` pipe, but readable from TypeScript too.

**Pick like this:**

```
just displaying data          →  async pipe or toSignal
need loading/error state      →  subscribe with finalize
need to trigger on an action  →  subscribe (or a Subject + switchMap)
```

<a name="unsubscribing"></a>
# 6. ⭐ Unsubscribing — when it actually matters

```ts
this.http.get('/api/employees').subscribe(…);   // ✅ completes → no leak
interval(1000).subscribe(…);                    // ❌ never completes → leaks
this.cartService.items$.subscribe(…);           // ❌ Subject → leaks
fromEvent(window, 'resize').subscribe(…);       // ❌ never completes → leaks
```

So strictly, HTTP doesn't leak. But tie it to the component's life anyway, for a different reason:

```ts
this.service.getAll().pipe(takeUntilDestroyed(this.destroyRef)).subscribe({
  next: data => this.employees = data,   // ← without this, the callback can run
});                                      //   after the user navigated away
```

```
HTTP without cleanup   →  no leak, but a callback on a destroyed component
HTTP with cleanup      →  request aborted on destroy. Strictly better.
```

<a name="nested"></a>
# 7. ⭐ The nested-subscribe antipattern

The single most common RxJS mistake:

```ts
// ❌ callback hell, no cancellation, errors unhandleable
this.userService.getUser(id).subscribe(user => {
  this.orderService.getOrders(user.id).subscribe(orders => {
    this.paymentService.getPayments(orders[0].id).subscribe(payments => {
      this.payments = payments;
    });
  });
});
```

```ts
// ✅ one chain, one subscribe, one error handler, fully cancellable
this.userService.getUser(id).pipe(
  switchMap(user   => this.orderService.getOrders(user.id)),
  switchMap(orders => this.paymentService.getPayments(orders[0].id)),
  takeUntilDestroyed(this.destroyRef),
).subscribe({
  next:  payments => this.payments = payments,
  error: err => this.error = err.message,
});
```

**Rule: one `subscribe` per stream.** Typing `.subscribe(` inside a `.subscribe(` means you want a flattening operator ([Part 12 §7](12-rxjs.md)).

Need values from *both* steps? Carry them forward:

```ts
this.userService.getUser(id).pipe(
  switchMap(user =>
    this.orderService.getOrders(user.id).pipe(
      map(orders => ({ user, orders })),      // carry `user` through
    )
  ),
).subscribe(({ user, orders }) => …);
```

<a name="crud"></a>
# 8. A complete CRUD component

```ts
@Component({
  selector: 'app-employee-list',
  imports: [EmployeeCardComponent],
  template: `
    @if (loading()) { <app-spinner /> }
    @if (error())   { <p class="error">{{ error() }}</p> }

    @for (e of employees(); track e.id) {
      <app-employee-card [employee]="e" (delete)="remove($event)" />
    } @empty {
      <p>No employees yet.</p>
    }
  `,
})
export class EmployeeListComponent implements OnInit {
  private service    = inject(EmployeeService);
  private destroyRef = inject(DestroyRef);

  employees = signal<Employee[]>([]);
  loading   = signal(false);
  error     = signal<string | null>(null);

  ngOnInit() { this.load(); }

  load() {
    this.loading.set(true);
    this.error.set(null);

    this.service.getAll().pipe(
      finalize(() => this.loading.set(false)),
      takeUntilDestroyed(this.destroyRef),
    ).subscribe({
      next:  data => this.employees.set(data),
      error: (err: HttpErrorResponse) => this.error.set(this.messageFor(err)),
    });
  }

  remove(id: number) {
    const previous = this.employees();
    this.employees.update(list => list.filter(e => e.id !== id));   // optimistic

    this.service.delete(id).pipe(
      takeUntilDestroyed(this.destroyRef),
    ).subscribe({
      error: () => {
        this.employees.set(previous);                // roll back on failure
        this.error.set('Delete failed');
      },
    });
  }

  private messageFor(err: HttpErrorResponse): string {
    if (err.status === 0)   return 'Network error — check your connection';
    if (err.status === 404) return 'Not found';
    if (err.status >= 500)  return 'Server error — please try again';
    return 'Something went wrong';
  }
}
```

The delete is an **optimistic update** — change the UI immediately, roll back if the server rejects it. That's what makes an app feel fast.

<a name="errors"></a>
# 9. Where should errors be handled?

Both places, for different jobs.

```ts
// SERVICE — technical concerns: retry, logging, shaping
getAll(): Observable<Employee[]> {
  return this.http.get<Employee[]>(this.url).pipe(
    retry({ count: 2, delay: 1000 }),
    catchError(err => {
      this.logger.error('getAll failed', err);
      return throwError(() => err);      // rethrow — the component still needs to know
    }),
  );
}
```

```ts
// COMPONENT — user-facing concerns: what to display
.subscribe({
  error: err => this.error.set(this.messageFor(err)),
});
```

⚠️ If the service swallows the error with `catchError(() => of([]))`, the component can't distinguish "no employees" from "the request failed" — and shows an empty list instead of an error. Rethrow unless you genuinely mean an empty fallback.

<a name="subjects"></a>
# 10. ⭐ Observable vs Subject vs BehaviorSubject

```
Observable       you can only LISTEN                    (no .next())
Subject          you can listen AND PUSH                (.next(), but no memory)
BehaviorSubject  listen, push, and it REMEMBERS the current value
```

## Observable — read-only, cold

The producer lives **inside** it. You can't push values in from outside.

```ts
const obs$ = new Observable<number>(observer => {
  observer.next(1);
  observer.next(2);
  observer.complete();
});

obs$.subscribe(v => console.log('A', v));   // A 1, A 2
obs$.subscribe(v => console.log('B', v));   // B 1, B 2  ← ran the function AGAIN

obs$.next(3);   // ❌ doesn't exist
```

## Subject — you push, everyone shares

Both an Observable and an Observer. It has `.next()`.

```ts
const subject = new Subject<number>();

subject.next(1);                              // 🔇 nobody listening — LOST FOREVER

subject.subscribe(v => console.log('A', v));
subject.subscribe(v => console.log('B', v));

subject.next(2);    // A 2, B 2   ← one emission, both receive it

subject.subscribe(v => console.log('C', v));  // C gets NOTHING yet
subject.next(3);    // A 3, B 3, C 3
```

Hot / multicast — one execution, shared. **But no memory:** subscribe late and you've missed everything.

## BehaviorSubject — a Subject with a current value

```ts
const bs = new BehaviorSubject<number>(0);    // ← initial value REQUIRED

bs.subscribe(v => console.log('A', v));       // A 0  ← immediately, on subscribe
bs.next(1);                                   // A 1
bs.next(2);                                   // A 2

bs.subscribe(v => console.log('B', v));       // B 2  ← gets the CURRENT value instantly
console.log(bs.value);                        // 2    ← synchronous read
```

Two things a plain Subject can't do: give new subscribers the current value, and expose `.value` for a synchronous read.

## Side by side

| | Observable | Subject | BehaviorSubject |
|---|---|---|---|
| Can call `.next()`? | ❌ | ✅ | ✅ |
| Initial value | — | none | **required** |
| Late subscriber gets | full re-run | nothing | current value |
| `.value` | ❌ | ❌ | ✅ |
| Cold/hot | cold (unicast) | hot (multicast) | hot (multicast) |
| Typical use | HTTP calls | events | **state** |

## Why it matters

```ts
@Injectable({ providedIn: 'root' })
export class AuthService {
  // ❌ Subject: a component created AFTER login sees nothing —
  //    it thinks nobody is logged in
  // private user$$ = new Subject<User | null>();

  // ✅ BehaviorSubject: any component, at any time, gets the current user
  private user$$ = new BehaviorSubject<User | null>(null);

  readonly user$ = this.user$$.asObservable();       // expose read-only

  login(creds: Credentials) {
    return this.http.post<User>('/api/login', creds).pipe(
      tap(user => this.user$$.next(user)),
    );
  }

  get isLoggedIn() {
    return this.user$$.value !== null;               // guards need a synchronous answer
  }
}
```

`isLoggedIn` is impossible with a plain `Subject` — a route guard must answer *right now*, and only `BehaviorSubject` holds a value to answer with.

`asObservable()` hands out a listen-only view so components can't call `.next()` and write to your state from anywhere.

## The other two

```ts
new ReplaySubject<number>(3);   // replays the last 3 values to new subscribers
new AsyncSubject<number>();     // emits ONLY the final value, and only on complete()
```

## Choosing

```
data from an API              →  Observable      (HttpClient gives you one)
an event with no state        →  Subject         ("refresh clicked", "modal closed")
state something can read      →  BehaviorSubject (current user, cart, filters)
state, modern Angular         →  signal()        ← simpler than BehaviorSubject
```

## Interview answer

> *"An Observable is read-only — the producer is inside it, and each subscriber triggers its own execution, so two subscribers to an HTTP call means two requests. A Subject is both an Observable and an Observer: you can call `.next()` to push values in, and all subscribers share one execution. But it has no memory, so anything emitted before you subscribe is lost. A BehaviorSubject is a Subject that stores the current value — it requires an initial value, gives every new subscriber that value immediately on subscribe, and exposes `.value` for a synchronous read. That's why it's the standard state container: a component that loads after the data arrived still gets it, and a route guard can check the current value synchronously. In modern Angular a signal does the same job more simply."*

<a name="reference"></a>
# 11. Quick reference

```
SERVICE returns, COMPONENT subscribes

subscribe({ next, error, complete })     error & complete are TERMINAL
shorthand subscribe(fn)                  = next only, errors go unhandled

.then    ≈ next        .catch ≈ error / catchError
.finally ≈ finalize    await  ≈ firstValueFrom()

CONSUMING
  async pipe / toSignal   →  display only, auto-cleanup
  subscribe + finalize    →  need loading & error state

CLEANUP
  HTTP completes → no leak, but callbacks can still fire after destroy
  infinite streams (Subject, interval, fromEvent) → MUST clean up
  takeUntilDestroyed() is the default answer

NEVER nest subscribes → switchMap / concatMap / mergeMap / exhaustMap

Observable      listen only, cold, one execution per subscriber
Subject         listen + push, hot, NO memory
BehaviorSubject listen + push, hot, current value + .value
```
