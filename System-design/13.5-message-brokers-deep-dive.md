<a name="queuevslog"></a>
# 1. Queue vs Log — the distinction that decides everything

Part 13 notes that Kafka "isn't really a queue." Here's the distinction sharpened into a **decision rule**, because almost every broker choice follows from it.

```
   QUEUE (RabbitMQ, SQS, BullMQ)          LOG (Kafka, Kinesis, Redis Streams, Pulsar)
   ───────────────────────────            ──────────────────────────────────────────
   A pile of WORK to be done              A HISTORY of things that happened
   Each message consumed ONCE,            Each message read by MANY consumers,
     then deleted                           independently, and RETAINED
   Consumer competes for messages         Consumer has its own cursor (offset)
   "Send this email"                      "An order was placed"
   Gone after ack                         Replayable — rewind and reprocess
```

**The rule:**

> **Ask: do multiple independent consumers need the *same* message, and might a *future* consumer need it too?**
> - **Yes → log.** Analytics, search indexing, and a recommender all need every order event; a new service added next year needs the history.
> - **No, it's a work item to be done once → queue.** "Resize this image." Once it's done, nobody needs it again.

**Why this matters practically:** picking a queue when you needed a log means that when a second team asks for the same events, you can't give them any — the messages are gone. Picking a log when you needed a job queue means writing retries, backoff, delays, and priorities yourself, because a log doesn't have them.

> **Interview line:** *"The question I'd ask first is whether this is work distribution or a shared event history. Work that must happen once goes on a queue. Events that several independent consumers care about — and that a future consumer might need to replay — go on a log. That single question decides Kafka versus RabbitMQ more reliably than throughput numbers do."*

<a name="semantics"></a>
# 2. Delivery semantics — at-most / at-least / "exactly" once

Three possible guarantees. **Know which one you have, because it dictates whether your consumer must be idempotent.**

| Semantic | Means | You lose | You get duplicates | Used for |
|---|---|---|---|---|
| **At-most-once** | Ack *before* processing | ✅ Yes, on crash | ❌ No | Metrics, logs — where losing one is fine |
| **At-least-once** | Ack *after* processing | ❌ No | ✅ Yes, on retry | **The default. Almost everything.** |
| **Exactly-once** | Neither loss nor duplication | ❌ No | ❌ No | Billing, payments |

### The mechanism is just *when you ack*

```
AT-MOST-ONCE            AT-LEAST-ONCE
─────────────           ─────────────
receive msg             receive msg
ACK  ←── here           process  ← crash here?
process ← crash here?   ACK  ←── here
  → message gone          → no ack → redelivered → duplicate
```

That's the whole difference. **Ack before work = risk losing it. Ack after work = risk doing it twice.** There is no third option, which is why:

### ⭐ "Exactly-once" is not a delivery guarantee

**Exactly-once delivery does not exist over a network.** What you build is:

```
   at-least-once DELIVERY   +   idempotent PROCESSING   =   exactly-once EFFECT
```

The broker retries freely; the consumer makes the *second* execution a no-op. Mechanisms:
- **A dedup key** carried on the message + a store of processed keys (bounded window).
- **A unique constraint** in the database — the DB, not your code, enforces "once."
- **An upsert keyed by a natural ID**, so reprocessing rewrites the same row rather than adding one.

Kafka *does* offer "exactly-once semantics" via **idempotent producers + transactions**, and that's real — but it's scoped to *Kafka-to-Kafka* processing (read → process → write, committed atomically). The moment your consumer calls an external API or writes to another database, you're back to at-least-once + idempotence.

> **Say this:** *"I'd treat exactly-once as at-least-once delivery plus idempotent writes rather than as something the broker gives me. Kafka's transactional exactly-once is genuine but only within Kafka — as soon as a consumer touches an external system, the guarantee ends at the boundary."*

*(Same principle worked in detail in [Problem 16 §4a](Problems/problem-16-payment-system-upi.md#core) and [Problem 19 §5](Problems/problem-19-ad-click-aggregator.md#exactlyonce).)*

<a name="ordering"></a>
# 3. Ordering — the per-partition truth

**The single most misunderstood fact about Kafka:**

> ### Kafka guarantees ordering **within a partition**. There is **no global ordering** across partitions.

```
 Topic: orders  (3 partitions)

 P0: [ order-A-created ][ order-A-paid ][ order-A-shipped ]   ← ordered ✅
 P1: [ order-B-created ][ order-B-paid ]                      ← ordered ✅
 P2: [ order-C-created ]                                      ← ordered ✅

 Across P0/P1/P2 → NO ordering guarantee whatsoever.
```

That's fine, because **you almost never need global ordering** — you need ordering *per entity*. Order A's events must be ordered relative to each other; they need no relationship to order B's.

### The partition key is how you get the ordering you need

```
   partition = hash(key) % numPartitions
```

**Same key → same partition → ordered.** So set the key to the entity whose ordering matters:

| Use case | Partition key | Result |
|---|---|---|
| Order lifecycle events | `orderId` | All events for one order stay ordered |
| Per-user activity stream | `userId` | One user's actions stay ordered |
| Per-device telemetry | `deviceId` | One device's readings stay ordered |
| **No key set** | round-robin | Even spread, **no ordering at all** |

### ⚠️ Two traps to name unprompted

**① Adding partitions permanently breaks key-based ordering.** The mapping is `hash(key) % numPartitions` — change `numPartitions` and the same key now hashes to a *different* partition. Messages for that key exist in the old partition *and* the new one, with no ordering between them.

> There is no clean fix, only mitigations: **over-provision partitions up front** (they're cheap; you can't remove them either), or accept a controlled cutover where you drain before repartitioning. **Never quietly add partitions to a keyed topic in production and assume ordering survived.**

**② A hot key destroys parallelism.** If one `userId` is 30% of traffic, its partition is 30% of the load while others idle. The fix is **two-phase aggregation with key salting** — worked in [Problem 19 §9](Problems/problem-19-ad-click-aggregator.md#scaling).

### Ordering elsewhere
- **SQS Standard** — best-effort ordering only. No guarantee.
- **SQS FIFO** — strict ordering *within a **message group ID***, which is exactly Kafka's partition-key idea under a different name. Lower throughput.
- **RabbitMQ** — ordered per queue, but **multiple competing consumers on one queue break it** (consumer 2 may finish before consumer 1). One consumer per queue if order matters.

<a name="consumergroups"></a>
# 4. Consumer groups & the scaling ceiling

**How do you scale consumers?** The answer has a hard limit people miss.

```
 Topic: orders (4 partitions)      Consumer Group: "billing"

   P0 ──────▶ Consumer 1
   P1 ──────▶ Consumer 2
   P2 ──────▶ Consumer 3
   P3 ──────▶ Consumer 4
              Consumer 5   ← IDLE. Does nothing. Ever.
```

### The rules
1. **Each partition is assigned to exactly one consumer** in a group.
2. A consumer may hold **many** partitions; a partition is **never** split across consumers.
3. ⭐ **Therefore: parallelism is capped by partition count.** Consumers beyond that sit idle.
4. **Different groups are independent** — group "billing" and group "analytics" each read *all* partitions, at their own offsets. That's what makes a log support many consumers.

> **The answer to "how do you scale consumers?"** — *"Add consumers up to the partition count. Beyond that they're idle, because a partition is only ever assigned to one consumer in a group. So the real scaling decision is partition count, and it's made when you create the topic — a rough rule is one partition per expected consumer thread, then roughly double it for headroom, since you can add partitions but it breaks key ordering and you can't remove them at all."*

### Rebalancing — and why it hurts
When a consumer joins, leaves, or dies, partitions are reassigned. Classically this is a **stop-the-world** event: *every* consumer stops, the group re-assigns, everyone resumes. Under a deploy that rolls 10 consumers, you can trigger 10 rebalances back to back.

Mitigations worth naming:
- **Incremental cooperative rebalancing** (Kafka 2.4+): consumers that keep their partitions **keep processing** throughout, instead of everyone halting.
- **Static group membership**, so a consumer restarting during a deploy doesn't trigger reassignment at all.
- **Tune the session timeout** so a brief GC pause isn't mistaken for a dead consumer.

**And don't assume a consumer keeps its partitions across a rebalance** — it usually won't. Any state your consumer caches per-partition must be rebuildable.

<a name="lag"></a>
# 5. Consumer lag — the metric that matters

```
   Producer writes to offset ─────────────▶ 1,000,000
   Consumer has committed up to ──▶ 987,000
                                    ─────────────────
                                    LAG = 13,000 messages
```

**Consumer lag is the single best health signal for any async pipeline**, and it's better than CPU or memory for two reasons:

1. **It measures unserved demand directly.** CPU tells you a machine is busy; lag tells you *work is piling up*, which is what you actually care about.
2. **It's a leading indicator.** Lag grows *before* anything downstream looks wrong — dashboards go stale, emails arrive late, and by then you're minutes behind.

**Use it for:**
- **Alerting** — alert on *growing* lag, not absolute lag. A steady 10K is fine; 1K climbing steadily is not.
- **Autoscaling** — scale consumers on lag (up to the partition ceiling from §4). This is exactly the mechanism used in [Problem 10 DD4](Problems/problem-10-uber-ride-sharing.md#dd4) and [Problem 19](Problems/problem-19-ad-click-aggregator.md).
- **Deploy safety** — a spike after a deploy means the new consumer is slower. Roll back before the backlog becomes unrecoverable.

> **Watch for lag that never recovers.** If consumers can't drain faster than producers write, lag grows forever and retention eventually deletes unread messages — **silent data loss**. That's the failure mode to name: the pipeline doesn't error, it just quietly falls off the end of the retention window.

<a name="outbox"></a>
# 6. The dual-write problem & the Outbox pattern 🎯

**This is the most commonly asked question in this whole area, and it has a name.**

### The problem

```js
await db.orders.insert(order);        // ① database write
await kafka.publish('order-created'); // ② publish event
```

Looks fine. It isn't — **these are two systems with no shared transaction**:

| Failure | Result |
|---|---|
| ① succeeds, ② fails | Order exists, **no event ever published.** Downstream services never learn about it. Silent, permanent inconsistency. |
| ② succeeds, ① rolls back | **Phantom event** — consumers react to an order that doesn't exist. |
| Process dies between them | Same as case 1. |

Swapping the order doesn't help; it just changes which failure you get. **And 2PC across a database and a broker is not a real option** — the coordinator-blocking problem from [Problem 16 §5](Problems/problem-16-payment-system-upi.md#saga).

### The solution: write the event to the *same database*, in the *same transaction*

```
 ┌─────────── ONE LOCAL TRANSACTION ────────────┐
 │  INSERT INTO orders  (...)                    │
 │  INSERT INTO outbox  (aggregate_type='Order', │
 │                       aggregate_id=42,        │
 │                       payload='{...}')        │
 └───────────────────────────────────────────────┘
                    │ commit (atomic — both or neither)
                    ▼
          ┌───────────────────┐
          │  outbox table     │
          └───────────────────┘
                    │  a RELAY reads new rows
                    ▼
          ┌───────────────────┐
          │  Kafka / broker   │
          └───────────────────┘
```

**Why it works:** the event and the business data are in **one database**, so one ordinary local transaction makes them atomic. There is no distributed transaction anywhere. Either both rows commit or neither does — **a phantom event becomes impossible, and a lost event becomes impossible.**

### Two ways to run the relay

| | **Polling publisher** | **CDC (Debezium)** ⭐ |
|---|---|---|
| How | A worker polls `SELECT * FROM outbox WHERE published = false` | Reads the DB's **transaction log** directly |
| Load on DB | Constant polling queries | **None** — the log is already being written |
| Latency | Poll interval | **Milliseconds** after commit |
| Ordering | Needs care | **Exactly the commit order**, for free |
| Complexity | Trivial | New infrastructure to run |

**CDC is the better answer where the scale justifies it.** Debezium tails the replication/transaction log — an append-only file the database writes anyway — so it adds no query load, sees changes within milliseconds, and inherits the exact order in which transactions committed.

**The routing convention worth knowing:** Debezium's Outbox Event Router uses `aggregate_type` to pick the **topic** (`Order` → `Order-events`) and `aggregate_id` as the **Kafka message key** — which, per [§3](#ordering), means all events for one order land on the same partition and stay ordered. The pattern and the ordering model fit together deliberately.

### Still at-least-once
The relay can publish and then crash before marking the row published → the event is sent twice. **The outbox fixes the dual-write problem, not duplication.** Consumers still need to be idempotent ([§2](#semantics)).

> **Interview answer:** *"That's the dual-write problem — two systems, no shared transaction, so any failure between them leaves you with either a lost event or a phantom one, and 2PC across a database and a broker isn't practical. I'd use the transactional outbox: write the event into an outbox table in the **same local transaction** as the business data, so they commit atomically, then have a separate relay publish from that table. At small scale the relay polls; at real scale I'd use CDC with something like Debezium reading the transaction log, which adds no load on the database and preserves commit order for free. It's still at-least-once, so consumers stay idempotent."*

<a name="failure"></a>
# 7. Production failure handling — DLQ, redrive, poison messages

Part 13 covers retry → DLQ → alert. Three things it leaves out:

### ① Poison messages
A message that **fails every time** — malformed payload, references a deleted record, hits a bug. Without a retry cap it's retried forever, and worse, **on an ordered partition it blocks everything behind it**. That's a queue-wide outage caused by one bad message.

**Fix:** cap retries (typically 3–5), then move it aside so the pipeline keeps flowing.

### ② The DLQ is not a graveyard — it needs redrive
A DLQ that nobody drains is just a slow data-loss mechanism. The operational loop:

```
   DLQ fills → ALERT → engineer inspects → fix root cause
                                              │
                                              ▼
                                    REDRIVE: replay messages
                                    from DLQ back to the main queue
```

**"Redrive" is the word** (SQS uses it literally). Two things it requires: the DLQ must retain **enough context to diagnose** — original payload, failure reason, attempt count, timestamps — and consumers must be **idempotent**, since redriven messages may have partially processed.

### ③ Retry with backoff *and jitter*
Exponential backoff alone (1s, 2s, 4s, 8s) still synchronizes clients — a downstream outage means every consumer retries at the *same* moments, hammering the service in waves exactly as it tries to recover. **Add randomized jitter** so retries spread out. Also pair with a **circuit breaker**: if a dependency is down, fail fast rather than burning retries.

### ④ Retry in a separate topic, not in place
On an ordered log, retrying in place blocks the partition. The pattern is **tiered retry topics**: a failed message moves to `orders-retry-5s`, then `orders-retry-1m`, then the DLQ — so the main partition keeps flowing and the retry delay doesn't stall live traffic.

<a name="landscape"></a>
# 8. The landscape — transports vs job queues

⭐ **The framing that clears up most confusion:**

> **A message *transport* moves bytes between processes and leaves job semantics to you. A *job queue* gives you a job record with retries, backoff, delays, priorities, and concurrency limits built in.**
>
> Comparing BullMQ to Kafka is a category error — they solve different problems.

### Transports

| | Model | Superpower | Watch out for |
|---|---|---|---|
| **Kafka** | Log, partitioned, retained | Massive throughput + **replay**; many independent consumers | Heavy to operate; overkill for most apps; ordering only per-partition |
| **RabbitMQ** | Queue + smart broker | **Flexible routing** (direct/topic/fanout); mature | Moderate throughput; no replay once acked |
| **AWS SQS** | Managed queue | **Zero ops**; Lambda integration | No replay; Standard = no ordering; FIFO = lower throughput |
| **AWS SNS** | Pub/Sub fanout | **SNS→SQS fanout**: one publish → many queues, each with its own consumer + DLQ | SNS alone has no durability — pair it with SQS |
| **AWS Kinesis** | Log (Kafka-like) | Managed streaming on AWS | Shard-based scaling; AWS-only |
| **Redis Streams** | Log, in-memory | **Very low latency**, consumer groups, already in your stack | Memory-bound; retention costs RAM |
| **Redis Pub/Sub** | Fire-and-forget | Trivially simple, instant | ⚠️ **No durability at all** — offline subscriber misses the message permanently |
| **NATS / JetStream** | Both | Extremely lightweight and fast | Smaller ecosystem |
| **Apache Pulsar** | Log + queue | Multi-tenancy, tiered storage, both models | More moving parts (needs BookKeeper) |

### Job queues (application-level)

| | Backed by | Best for |
|---|---|---|
| **BullMQ** ⭐ | Redis | **The Node.js default.** Retries, backoff, delayed & repeatable jobs, priorities, rate limiting, job flows/dependencies, dashboard |
| **pg-boss** | PostgreSQL | You already have Postgres and don't want another dependency — *and the job lives in the same DB, so [§6's](#outbox) dual-write problem disappears* |
| **Celery** | Redis/RabbitMQ | The Python equivalent |
| **Sidekiq** | Redis | The Ruby equivalent |

> **For a Node.js backend, the honest default is BullMQ**, and the common trajectory is: start with BullMQ → move to RabbitMQ if you outgrow it or need cross-language consumers → adopt Kafka only when you genuinely need replay, retention, or many independent consumers on the same stream. *(See [`nodejs/`](../nodejs/) for the runtime side.)*

<a name="decision"></a>
# 9. Decision tree — which one do I pick?

```
START: what are you actually moving?

├─ Background work for MY app, one consumer, needs retries/delays/priorities
│     → JOB QUEUE.  Node → BullMQ.  Already on Postgres → pg-boss.
│
├─ Events several INDEPENDENT services consume — and a future one may need history
│     │
│     ├─ Need replay / retention / very high throughput?
│     │     → KAFKA   (or Kinesis / Pulsar if managed-on-cloud matters)
│     │
│     └─ Just fanout, no replay needed?
│           → SNS → SQS   (each subscriber gets its own durable queue + DLQ)
│
├─ Decoupling services, complex ROUTING rules (topic/pattern/fanout)
│     → RABBITMQ
│
├─ On AWS, want zero ops, simple decoupling
│     → SQS   (FIFO only if you truly need ordering — it costs throughput)
│
└─ Ultra-low-latency, already running Redis, can tolerate memory-bound retention
      → REDIS STREAMS   (never plain Redis Pub/Sub if the message matters)
```

**Then ask these four regardless of choice:**
1. **Do I need ordering?** → partition/group key, and accept the parallelism cost. ([§3](#ordering))
2. **Is my consumer idempotent?** → it must be; you're on at-least-once. ([§2](#semantics))
3. **Am I dual-writing a DB and a broker?** → outbox. ([§6](#outbox))
4. **What happens to a message that always fails?** → retry cap → DLQ → alert → redrive. ([§7](#failure))

> **The most common mistakes, in order:** reaching for **Kafka when a job queue would do** (heavy ops burden for no benefit); using **Redis Pub/Sub for anything that matters** (zero durability); and **dual-writing without an outbox** (silent, permanent inconsistency).

<a name="interview"></a>
# 10. Interview questions & answers

### Q: "Kafka or RabbitMQ?"
> *"I'd decide on shape rather than throughput. The first question is whether this is work distribution or shared event history. If it's work that must happen once — resize this image, send this email — that's a queue, and RabbitMQ's routing is genuinely useful there. If several independent consumers need the same events, and a service I add next year might need to replay that history, that's a log, and that's Kafka: retained, partitioned, each consumer group at its own offset. Picking a queue when I needed a log is the expensive mistake, because once the messages are acked they're gone and I can't give a second team the data."*

### Q: "How does Kafka guarantee ordering?"
> *"It doesn't guarantee global ordering — only ordering within a partition, and that distinction is the whole thing. In practice you don't need global order, you need per-entity order, so I set the partition key to the entity whose ordering matters — orderId, or userId. Same key hashes to the same partition, so those events stay ordered relative to each other. Two traps: adding partitions later permanently breaks that, because the key now modulo-hashes somewhere else and the same key exists in two partitions with no ordering between them — so I over-provision partitions up front since you also can't remove them. And a hot key concentrates load on one partition, which needs salted two-phase aggregation."*

### Q: "How do you scale consumers?"
> *"Add consumers up to the partition count. Beyond that they sit completely idle, because a partition is assigned to exactly one consumer within a group and is never split. So the real scaling decision is the partition count, made when you create the topic — rule of thumb, one partition per expected consumer thread and then roughly double for headroom. Different consumer groups are independent though: billing and analytics each read all partitions at their own offsets, which is what makes a log support many consumers where a queue can't."*

### Q: "You write to your database and publish to Kafka. What if the publish fails?" ⭐
> *"That's the dual-write problem, and it has no good ad-hoc fix — the database write and the publish are two systems with no shared transaction, so if the write succeeds and the publish fails you have an order nobody downstream knows about, and if you reverse the order you can emit a phantom event for an order that rolled back. 2PC across a database and a broker isn't practical because of the coordinator-blocking problem. The answer is the transactional outbox: write the event into an outbox table in the same local transaction as the business data, so they commit atomically, then a separate relay publishes from that table. At small scale the relay polls the table; at real scale I'd use change data capture with Debezium tailing the transaction log, which puts no query load on the database and preserves the exact commit ordering. It's still at-least-once — the relay can publish then crash before marking the row — so consumers stay idempotent."*

### Q: "Is exactly-once delivery possible?"
> *"Not as a delivery guarantee — not over a network. What you actually build is at-least-once delivery plus idempotent processing, which produces an exactly-once effect. The broker is free to retry; the consumer makes the second execution a no-op, usually via a dedup key with a bounded window, a unique constraint in the database, or an upsert keyed by a natural ID so reprocessing rewrites the same row. Kafka does offer transactional exactly-once and it's real, but it's scoped to Kafka-to-Kafka — read, process, write, committed atomically. The moment a consumer calls an external API or writes to another database, the guarantee ends at that boundary."*

### Q: "What's your primary metric for an async pipeline?"
> *"Consumer lag — the gap between the latest produced offset and the last committed one. It beats CPU because it measures unserved demand directly rather than proxying it, and it's a leading indicator: lag grows before anything downstream visibly breaks. I'd alert on lag that's growing rather than on an absolute number, since a steady backlog is fine and a small one climbing is not, and I'd autoscale consumers on it — up to the partition ceiling. The failure mode I'd watch for is lag that never recovers: if consumers can't drain faster than producers write, retention eventually deletes unread messages, and that's silent data loss with no error anywhere."*

### Q: "A message fails every single time. What happens?"
> *"That's a poison message, and the danger is that on an ordered partition it blocks everything behind it — one bad payload becomes a pipeline outage. So I cap retries, typically three to five, then move it aside. I'd retry in separate tiered retry topics rather than in place, so the main partition keeps flowing while the delayed retries happen elsewhere. After the cap it goes to a dead-letter queue with enough context to actually diagnose it — original payload, failure reason, attempt count — and the DLQ raises an alert. The part people skip is that a DLQ nobody drains is just slow data loss, so there has to be a redrive path to replay messages back once the root cause is fixed, which is another reason consumers must be idempotent."*

### Q: "Why not just use Redis Pub/Sub? We already run Redis."
> *"Because Redis Pub/Sub is fire-and-forget with no durability whatsoever — if a subscriber is offline or restarting when a message is published, that message is gone permanently, with no error. It's fine for genuinely disposable signals like a live presence indicator. If the message matters I'd use Redis Streams instead, which is an actual retained log with consumer groups and is still in-process fast, or BullMQ if what I really want is a job queue with retries and backoff. Same Redis dependency, actual delivery guarantees."*

<a name="cheatsheet"></a>
# 11. Cheat Sheet — everything on one page

### The decision that comes first
- **Work distribution → QUEUE** (RabbitMQ/SQS/BullMQ). Consumed once, deleted.
- **Shared event history → LOG** (Kafka/Kinesis/Redis Streams). Many consumers, own offsets, **replayable**.
- Test: *"do multiple independent consumers need this, and might a future one?"*

### Delivery semantics
- Ack **before** work = at-most-once (**may lose**). Ack **after** work = at-least-once (**may duplicate**). No third option.
- **Default is at-least-once → consumers MUST be idempotent.**
- ⭐ **"Exactly-once" = at-least-once delivery + idempotent writes.** Kafka's transactional EOS is real but **Kafka-to-Kafka only** — it ends at any external system.
- Idempotence via: dedup key (bounded window) · DB unique constraint · upsert on natural ID.

### Ordering
- ⭐ **Kafka orders within a partition. NO global ordering.**
- `partition = hash(key) % numPartitions` → **same key = same partition = ordered**. Key by the entity that needs order (`orderId`, `userId`). No key → round-robin → **no ordering**.
- ⚠️ **Adding partitions permanently breaks key ordering** (key rehashes elsewhere; and you can't remove partitions) → **over-provision up front**.
- ⚠️ **Hot key kills parallelism** → salted two-phase aggregation.
- SQS FIFO = same idea via **message group ID**. RabbitMQ = ordered per queue, but **competing consumers break it**.

### Consumer groups
- Partition → **exactly one** consumer per group; never split. Consumer can hold many.
- ⭐ **Parallelism is capped by partition count** — extra consumers are **idle**.
- Different **groups are independent** (each reads everything at its own offset) ← this is what a log buys you.
- Sizing: ~1 partition per consumer thread, **×2 for headroom**.
- **Rebalance** = stop-the-world classically → use **incremental cooperative rebalancing** (2.4+) + **static membership** + tuned session timeout. Don't assume a consumer keeps its partitions.

### Consumer lag
- **The primary metric.** Beats CPU: measures unserved demand, and **leads** visible failure.
- Alert on **growing** lag, not absolute. Autoscale on it (up to the partition ceiling).
- ⚠️ **Lag that never recovers → retention deletes unread messages → silent data loss.**

### The Outbox pattern 🎯
- **Dual-write problem:** DB write + broker publish = two systems, no shared transaction. Either **lost event** or **phantom event**. 2PC isn't practical.
- **Fix:** `INSERT business row` + `INSERT outbox row` **in ONE local transaction** → a relay publishes from the outbox.
- Relay: **polling** (simple) or ⭐ **CDC/Debezium** — tails the transaction log, **no DB query load**, ms latency, **commit order preserved for free**.
- Convention: `aggregate_type` → topic, `aggregate_id` → **message key** (so per-entity ordering holds, §3).
- **Still at-least-once** — outbox fixes dual-write, not duplication.

### Production failure handling
- **Poison message** → blocks the partition behind it → **cap retries (3–5)**.
- **Retry in tiered retry topics, not in place** (in-place retry stalls an ordered partition).
- **Backoff + JITTER** (plain exponential still synchronizes clients into waves) + **circuit breaker**.
- **DLQ needs REDRIVE** — a DLQ nobody drains is slow data loss. Store payload + failure reason + attempt count.

### Landscape — the framing
- ⭐ **Transport** (Kafka/Rabbit/SQS/NATS/Redis) moves bytes. **Job queue** (BullMQ/pg-boss/Celery/Sidekiq) gives you retries, backoff, delays, priorities, concurrency limits. *Comparing them is a category error.*
- **Node default = BullMQ.** Path: BullMQ → RabbitMQ (outgrown / cross-language) → Kafka (replay, retention, many consumers).
- **pg-boss bonus:** job lives in Postgres → **the dual-write problem disappears**.
- **SNS→SQS** = fanout with a durable queue + DLQ per subscriber.
- ⚠️ **Redis Pub/Sub has NO durability** — offline subscriber misses it forever. Use **Redis Streams** if it matters.

### Top 3 mistakes
1. **Kafka when a job queue would do** — big ops burden, no benefit.
2. **Redis Pub/Sub for something that matters** — zero durability.
3. **Dual-writing without an outbox** — silent, permanent inconsistency.
