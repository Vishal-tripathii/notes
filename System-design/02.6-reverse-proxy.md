<a name="core"></a>
# 1. Core idea + forward vs reverse proxy

**A reverse proxy is a server that sits in front of your backend servers and forwards client requests to them — so clients talk to the proxy, never directly to your servers.**

## Forward proxy vs Reverse proxy
```
FORWARD PROXY (in front of CLIENTS — acts for the client):
[Clients] ──▶ [Forward Proxy] ──▶ [Internet / Servers]
   e.g. corporate proxy, VPN — hides WHO the client is from the server.

REVERSE PROXY (in front of SERVERS — acts for the server):
[Clients] ──▶ [Reverse Proxy] ──▶ [Your backend servers]
   hides your SERVERS from the client — client thinks the proxy IS the server.
```
- **Forward proxy** = represents/hides the **client** (you browsing via a VPN).
- **Reverse proxy** = represents/hides the **servers** (the front desk of your system).

> **Mnemonic:** *forward* proxy protects **clients**; *reverse* proxy protects **servers**. System design cares about the **reverse** proxy.

## Analogy: the front desk 🏢
A reverse proxy is the **front desk of an office building**. Visitors don't wander in and find employees — they check in at the desk, which **routes** them to the right department, **handles security** (they never see the internal layout), **checks credentials** (SSL, auth), and turns away troublemakers (rate limiting).
> Same receptionist as the load balancer (Part 2.5) — that's *why* they get confused. The difference is **scope** (§7).

<a name="jobs"></a>
# 2. What a reverse proxy actually does (its jobs)

A Swiss Army knife at your system's edge:
1. **SSL/TLS termination** — decrypt HTTPS here so backends don't (§5).
2. **Load balancing** — distribute across backends (the Part 2.5 job, optionally).
3. **Caching** — cache static content/responses (Part 5).
4. **Compression** — gzip responses to save bandwidth.
5. **Serving static files** — deliver images/CSS/JS directly, freeing app servers.
6. **Security / hiding the backend** — clients never learn servers' real IPs; only the proxy is exposed.
7. **Request routing** — `/api`→one group, `/images`→another (path-based).
8. **Rate limiting & filtering** — block abusive traffic at the edge (Part 5.5).

```
                       ┌─ decrypts HTTPS (SSL termination)
                       ├─ caches static content
[Clients] ──▶ [Reverse ┼─ compresses responses      ──▶ [App Server 1]
              Proxy]   ├─ routes /api vs /images     ──▶ [App Server 2]
                       ├─ hides backend IPs          ──▶ [App Server 3]
                       └─ rate limits abusers
```

<a name="one-server"></a>
# 3. Concrete example: a reverse proxy in front of ONE server

Forget "many servers." You built **one Node.js app** on **one server**, listening on port 3000. Nothing to load balance — yet you'd *still* put Nginx in front. Here's why, problem by problem.

## Problem 1: HTTPS/SSL is a pain in the app
Without a proxy, the Node app itself must load the TLS cert, encrypt/decrypt every request (CPU work), and you update the cert in app code on every renewal.
**With Nginx:**
```
[Users] ──HTTPS──▶ [Nginx :443] ──plain HTTP──▶ [Node.js :3000]
                    ▲ handles ALL the SSL here
```
Node speaks simple HTTP on :3000, never touches certs. Cert lives in Nginx, one place. → **SSL termination**, useful with just one server.

## Problem 2: The app wastes time serving images/CSS
Without a proxy, every request for `logo.png` goes to Node (meant for logic, not files).
**With Nginx:**
```
/logo.png   → Nginx serves it directly from disk (app never sees it)
/api/orders → Nginx forwards to Node.js (real work)
```
→ **static file serving + caching**; the one server does less work.

## Problem 3: The server's real address is exposed
Without a proxy, Node on :3000 is directly reachable — attackers hit the real IP/port.
**With Nginx:**
```
[Internet] ──▶ [Nginx] (ONLY thing exposed, :80/:443)
                  │ (private network)
                  ▼
              [Node.js :3000]  ← not reachable from outside
```
→ **security / hiding the backend**; only hardened Nginx faces the internet.

## Problem 4: No protection against abuse
Without a proxy, 10,000 req/s drowns the single Node server.
**With Nginx:** add a rate-limit rule ("100 req/min per IP") — abuse is blocked **at the door** (Part 5.5/11).

## The picture: one server, still worth a reverse proxy
```
                        ┌─ terminates HTTPS (SSL)         ┐
[Users] ──HTTPS──▶ [Nginx] ─ serves /logo.png directly     ├──HTTP──▶ [ONE Node.js server]
                        ├─ blocks abusive traffic          │
                        └─ hides the app from the internet ┘
```
> **None of these four is load balancing** — there's only one server. The reverse proxy is the smart, protective **front door**. Load balancing is just one *extra* thing it can do once you have multiple servers.

## And this is the reverse-proxy-vs-load-balancer distinction
- A **load balancer** with one server = pointless (nothing to distribute).
- A **reverse proxy** with one server = useful (SSL, caching, security, rate limiting).
- Add a 2nd server later → tell the same Nginx "also balance across both" → now it's *also* a load balancer.
```
Day 1 (1 server):    Nginx = reverse proxy (SSL, cache, security)
Day 100 (5 servers): Nginx = reverse proxy AND load balancer
```

<a name="nginx"></a>
# 4. Nginx (the most popular reverse proxy)

**Nginx** ("engine-x") is a high-performance web server most commonly used as a **reverse proxy** — fast, lightweight, handles tens of thousands of concurrent connections. Engineers use it to terminate SSL, reverse-proxy to backend app servers (Node/Python/Java), load balance (Part 2.5), cache + serve static files, gzip, and rate limit.

Conceptual config (don't memorize — just recognize):
```nginx
server {
    listen 443 ssl;                          # handle HTTPS here (SSL termination)
    server_name myapp.com;

    location /api {
        proxy_pass http://backend_servers;   # forward /api to the app servers
    }
    location /images {
        root /var/www/static;                # serve images directly (no backend)
    }
}

upstream backend_servers {                   # the pool it load-balances across
    least_conn;
    server 10.0.0.1;
    server 10.0.0.2;
}
```
> Alternatives: **HAProxy, Envoy, Traefik, Apache, Caddy**.

<a name="ssl"></a>
# 5. SSL termination

Recall Part 7: HTTPS encrypts traffic with TLS; decryption is CPU work. **SSL termination** = the reverse proxy handles all HTTPS encryption/decryption, then talks to backends over plain HTTP inside the private network.
```
[Client] ──HTTPS (encrypted)──▶ [Reverse Proxy] ──HTTP (plain, internal)──▶ [App Servers]
                                  ▲ decrypts here (SSL terminates)
```
**Why:**
1. **Offloads CPU** — expensive TLS decryption done once at the proxy; app servers freed for app work.
2. **Centralized certs** — install/renew the TLS cert in **one place** (the proxy), not on every backend.
3. **Simpler backends** — apps don't deal with certs/encryption.

> **Nuance:** **SSL passthrough** (proxy forwards encrypted traffic untouched; backend decrypts) and **SSL re-encryption / end-to-end** (proxy decrypts, then re-encrypts to backend — for zero-trust like banking) also exist. Termination is the common default.

<a name="gateway"></a>
# 6. API Gateway (reverse proxy on steroids)

An **API Gateway is a specialized reverse proxy for microservices** — everything a reverse proxy does *plus* API management. The **single entry point** for many services.
```
                          ┌──▶ [User Service]
[Clients] ──▶ [API Gateway]──▶ [Order Service]
                          └──▶ [Payment Service]
   one door for the whole system of microservices
```
Extras beyond a plain reverse proxy:
- **Auth & authorization** — validate JWTs (Part 6) centrally, so each service doesn't re-implement.
- **Rate limiting & throttling** — per-client quotas (Part 5.5 / 11).
- **Request routing to services** — `/users`→User Service, `/orders`→Order Service.
- **Response aggregation** — combine results from several services (what GraphQL also tackles — Part 12).
- **Protocol translation, logging, monitoring, API versioning** (Part 11).

> **The hierarchy:** *Load balancer distributes traffic → reverse proxy does that + SSL/caching/routing/security → API gateway does all that + API-level concerns (auth, rate limiting, aggregation).* Examples: **Kong, AWS API Gateway, Apigee**, or Nginx configured as one.

<a name="vs-lb"></a>
# 7. Reverse Proxy vs Load Balancer (the interview showdown)

Honest answer: they **overlap heavily**, and the same tool (Nginx) often does both — but they're conceptually different.

## Core difference
- A **load balancer's** primary job: **distributing traffic across multiple servers**. Answers *"which of my identical servers gets this request?"* Implies **multiple backends**.
- A **reverse proxy's** job: broader — **the intermediary in front of your backend(s)** doing SSL, caching, routing, security, *and optionally* load balancing. Can front **even a single server**.

```
LOAD BALANCER:                        REVERSE PROXY:
"Spread requests across               "Be the front door — SSL, cache, route,
 my many identical servers."           hide backend, secure — and maybe balance."
Needs multiple servers.               Works with one OR many servers.
One primary job.                      Many jobs (a superset).
```

## Key relationships (say these out loud)
1. A **load balancer with one server makes no sense**; a **reverse proxy with one server is useful** (SSL, caching, security).
2. **Every load balancer effectively acts as a reverse proxy** (sits in front, forwards). But **not every reverse proxy is a load balancer** (one fronting a single server balances nothing).
3. In practice, **the same software does both** — Nginx/HAProxy are reverse proxies that *include* load balancing. The labels describe *which function you're using*.

## Comparison
| | **Load Balancer** | **Reverse Proxy** |
|---|---|---|
| Primary purpose | Distribute traffic across servers | Intermediary/front door for backends |
| Backends | **Multiple** (required) | One **or** multiple |
| Core function | Balancing + health checks | SSL, caching, routing, security, compression (+ balancing) |
| Scope | One job | Superset (broader) |
| Example | AWS NLB | Nginx |
| Relationship | *A kind of* reverse-proxy function | Can *include* load balancing |

> **Best one-liner:** *"A load balancer is a specific job — spreading traffic across multiple servers. A reverse proxy is the broader concept of an intermediary in front of your servers doing SSL termination, caching, routing, and security, with load balancing as just one of its features. Tools like Nginx are reverse proxies that include load balancing, so in practice they're often the same box doing both."*

<a name="interview"></a>
# 8. Interview questions & answers

### Q: "What is a reverse proxy?"
> *"A reverse proxy is a server that sits in front of your backend servers and forwards client requests to them, so clients only ever talk to the proxy, not the servers directly. It hides and protects the backend, and typically also handles SSL termination, caching, compression, request routing, and load balancing. Nginx is the most common example. It's 'reverse' because, unlike a forward proxy that represents the client, it represents the server."*

### Q: "Forward proxy vs reverse proxy?"
> *"A forward proxy sits in front of clients and acts on their behalf — it hides who the client is from the server, like a corporate proxy or VPN. A reverse proxy sits in front of servers and acts on their behalf — it hides the servers from the client, who thinks the proxy is the actual server. Forward protects the client; reverse protects the server."*

### Q: "What is SSL termination and why do it at the proxy?"
> *"SSL termination means the reverse proxy handles the HTTPS encryption and decryption, then talks to the backend over plain HTTP inside the private network. You do it there for three reasons: it offloads expensive TLS decryption from the app servers, it centralizes certificate management in one place instead of on every server, and it keeps the backends simple. For end-to-end encryption I'd use re-encryption, where the proxy decrypts then re-encrypts to the backend."*

### Q: "Difference between a reverse proxy and a load balancer?"
> *"They overlap a lot. A load balancer's specific job is distributing traffic across multiple identical servers, so it requires multiple backends. A reverse proxy is the broader concept — an intermediary in front of your backends that does SSL termination, caching, routing, and security, and can also load balance. So a reverse proxy can sit in front of even a single server, whereas a load balancer implies many. Every load balancer effectively acts as a reverse proxy, but not every reverse proxy is load balancing. And in practice a tool like Nginx is a reverse proxy that includes load balancing, so it's often the same component doing both."*

### Q: "What is an API Gateway and how is it different from a reverse proxy?"
> *"An API Gateway is a specialized reverse proxy for microservices. It does everything a reverse proxy does — routing, SSL, and so on — plus API-level concerns: centralized authentication and authorization, rate limiting, routing to different microservices, response aggregation across services, and monitoring. It's the single entry point to a whole system of services — a superset of a reverse proxy focused on managing APIs. Examples are Kong, AWS API Gateway, and Apigee."*

### Q: "Why put a reverse proxy in front of a single server?"
> *"Even with one server it adds value: it terminates SSL so the app doesn't handle certs, caches and serves static content to reduce load, compresses responses, hides the server's real IP for security, and gives me a place to add rate limiting. And when I later add more servers, I just enable load balancing on the proxy I already have."*

# 9. Cheat Sheet — everything on one page

### Core
- **Reverse proxy** = server in front of backends; clients talk to it, not the servers.
- **Forward proxy** fronts/hides **clients** (VPN); **reverse proxy** fronts/hides **servers** (front desk).

### Jobs
SSL termination · load balancing · caching · compression · static file serving · hiding/securing backend · request routing · rate limiting.

### Single-server example (why it's useful even with 1 server)
- SSL termination (app never touches certs).
- Serves /logo.png directly (app does less work).
- Hides app's real IP (only Nginx exposed).
- Rate limits abuse at the door.
→ None of these is load balancing.

### Nginx
Most common reverse proxy ("engine-x"). Terminates SSL, forwards to backends, load balances, caches, gzips, rate limits. Alt: HAProxy, Envoy, Traefik, Caddy.

### SSL termination
Proxy decrypts HTTPS, talks HTTP internally. Why: offload CPU · centralize certs · simpler backends. (Also: passthrough, re-encryption for zero-trust.)

### API Gateway
Reverse proxy for microservices + auth, rate limiting, routing to services, response aggregation. Single entry point. Kong, AWS API Gateway, Apigee.

### Hierarchy
Load balancer (distribute) ⊂ Reverse proxy (+ SSL/cache/route/security) ⊂ API Gateway (+ auth/rate limit/aggregation).

### Reverse proxy vs Load balancer
| | Load balancer | Reverse proxy |
|---|---|---|
| Job | Distribute across servers | Front door (SSL/cache/route/security + balancing) |
| Backends | Multiple (required) | One or multiple |
| Scope | One job | Superset |
- Every LB acts as a reverse proxy; not every reverse proxy is an LB. Nginx does both.
