<a name="why-servers"></a>
# 1. Why multiple servers? (the foundation)

A single server has three fatal problems:
1. **Capacity limit** — one machine handles only so many req/sec; traffic grows → CPU/RAM max out → slow, then fail (the throughput ceiling, Part 3).
2. **Single point of failure** — it crashes → **entire app down**. No redundancy.
3. **No room to scale** — you can only make one box so big (vertical scaling ceiling, Part 2).

So you run **many servers** (horizontal scaling, Part 2). New problem: **which server handles each request?** Hand users different addresses → one server drowns while others idle, and a dead server strands its users.

> **The gap a load balancer fills:** it sits in front of many servers and intelligently distributes incoming traffic across them.

<a name="analogy"></a>
# 2. Analogy + what a load balancer is

## Analogy: the receptionist at a busy clinic 🏥
A clinic with **10 doctors** and no receptionist → patients wander, some doctors swamped, others idle, and a doctor on break strands their patients. The **receptionist (load balancer)**:
- Greets every patient (receives every request).
- Sends each to an **available** doctor, spreading load.
- Knows who's **on break/sick** and stops routing to them (health checks).
- The patient never needs to know *which* doctor — they just talk to the receptionist.

## Definition
**A load balancer sits between clients and your servers, distributing incoming traffic across multiple servers so no single one is overwhelmed.**

Core purposes:
1. **Distribute load** — even spread → better throughput, no hotspots.
2. **High availability** — server fails → route around it → no downtime.
3. **Scalability** — add/remove servers freely; LB includes them in rotation.
4. **Health monitoring** — detect & avoid dead servers.
5. **(Often) SSL termination** — handle HTTPS decryption centrally (Part 7).

```
                        ┌──▶ [Server 1] ✅
[Clients] ──▶ [Load     │──▶ [Server 2] ✅
             Balancer]  │──▶ [Server 3] ❌ (down — LB skips it)
                        └──▶ [Server 4] ✅
        one entry point       many workers
```

<a name="how"></a>
# 3. How a load balancer actually works (interview level)

## The request flow
```
1. Client sends a request to the LB's address (e.g. api.myapp.com → LB's IP).
   The LB is the public face of the system.
2. The LB receives it. Behind it is a POOL of servers it knows about.
3. The LB picks a server via its ALGORITHM — only from servers marked HEALTHY
   by health checks.
4. The LB FORWARDS the request to that server.
5. The server processes it, returns the response to the LB
   (or, in some modes, directly to the client).
6. The LB passes the response back to the client.

The client only ever "sees" the load balancer — no idea how many servers exist
or which one served it. (Layered system — Part 11's REST constraint.)
```

<a name="l4-l7"></a>
# 4. Layer 4 vs Layer 7 (key interview distinction)

| | **Layer 4 (Transport)** | **Layer 7 (Application)** |
|---|---|---|
| Routes based on | IP + port (TCP/UDP) | Request *content*: URL, headers, cookies |
| Sees content? | ❌ No (just packets) | ✅ Yes (reads the HTTP request) |
| Speed | Faster (less inspection) | Slightly slower |
| Smart routing? | No | Yes — `/images/*`→image servers, `/api/*`→API servers |
| Example | AWS NLB | AWS ALB, Nginx |

> **Insight:** **L4** = fast, dumb traffic splitter (forwards packets). **L7** = smart router that *reads* the request — route by URL path, A/B testing, SSL termination. Most web apps use **L7**.

<a name="algorithms"></a>
# 5. The algorithms (with examples)

### 1. Round Robin — rotate in order
```
Req 1→S1, Req 2→S2, Req 3→S3, Req 4→S1 ...
```
Simple, even. Ignores server busyness. **Good for:** uniform requests + equal servers.

### 2. Weighted Round Robin — bigger servers get more
```
S1 (weight 3), S2 (weight 1) → S1,S1,S1,S2,S1,S1,S1,S2 ...
```
**Good for:** servers of unequal power.

### 3. Least Connections — send to least busy
```
S1: 2 active, S2: 8, S3: 5 → new request → S1
```
Adapts to real load. **Good for:** varying request durations.

### 4. Weighted Least Connections
Least connections adjusted for server capacity.

### 5. Least Response Time — fastest-responding server
Lowest latency + fewest connections. **Good for:** latency-sensitive apps.

### 6. IP Hash — same client → same server
```
hash(client_IP) % num_servers → a fixed server per client
```
**Good for:** session stickiness (see below).

### 7. Random (+ "Power of Two Choices")
Pick randomly; a variant picks two at random → sends to the less busy. Cheap & effective.

> **Interview move:** match algorithm to situation — "round robin for uniform load; least connections for varied durations; weighted for unequal servers; IP hash for stickiness."

<a name="health"></a>
# 6. Health checks (what makes it fault-tolerant)

## Active health checks
LB **proactively pings** each server on a schedule.
```
Every 5s:  LB → GET /health → Server
   200 OK      → HEALTHY (keep in rotation)
   no response → UNHEALTHY (remove from rotation)
```
Apps expose a lightweight **`/health` endpoint** (200 if server + dependencies OK). Recovered servers that pass checks are **re-added automatically**.

## Passive health checks
LB **watches real traffic** — if a server errors/times out on actual requests, mark it unhealthy. No extra pings; learns from live traffic.

> **Why it matters:** health checks turn "multiple servers" into "high availability." Without them, the LB keeps routing to a dead server. This is the mechanism behind the fault tolerance claimed since Part 2.

```
[LB] ──check──▶ [S1] ✅ in rotation
     ──check──▶ [S2] ❌ failed → REMOVED (no user hits it)
     ──check──▶ [S3] ✅ in rotation
        (S2 recovers → passes checks → re-added automatically)
```

<a name="sticky"></a>
# 7. Sticky sessions (and why stateless is better)

If a server stores a user's session in its **own memory** (Part 2), that user must keep hitting the **same** server. **Sticky sessions (session affinity)** make the LB route a given user consistently to one server (via cookie or IP hash).
- ✅ Works with stateful servers.
- ❌ **Fragile** — server dies → user loses session; also unbalances load.

> **Better answer (Part 2):** make servers **stateless** — sessions in shared Redis (Part 5.5) or JWTs (Part 6). Then *any* server handles *any* request, no stickiness, LB balances freely. **In interviews:** mention sticky sessions exist but say you'd prefer stateless servers + shared session store.

---

<a name="spof"></a>
# 8. The LB as a single point of failure

All traffic through *one* LB → if it dies, everything is down. Make the **LB itself highly available**:
- Run **multiple LBs** (active-passive or active-active).
- **Floating/virtual IP** fails over to a standby LB if the primary dies.
- Or **DNS-level load balancing** across multiple LBs.

> Always flag this: "and I'd make the load balancer itself redundant, so it's not a single point of failure." Shows end-to-end thinking.

<a name="implement"></a>
# 9. Where to use & how to implement (the "techie" view)

## Where LBs sit — between every tier
```
[Clients] → [LB] → [Web servers] → [LB] → [App servers] → [DB (primary + read replicas)]
```
Load-balance the web tier, app tier, even DB reads (across read replicas — Part 2).

## How engineers implement them
| Type | Examples | When |
|---|---|---|
| **Software LB** | **Nginx**, **HAProxy**, Envoy, Traefik | Self-managed, cheap, flexible; run on your own servers |
| **Cloud LB (managed)** | **AWS ELB** — ALB (L7), NLB (L4); GCP LB; Azure LB | Most common today; auto-scales, managed |
| **Hardware LB** | F5 BIG-IP, Citrix ADC | Enterprise/on-prem, expensive, very high performance |

**In practice:** most teams use a **cloud LB** (AWS ALB is the default for web apps) or **Nginx/HAProxy** self-hosted. You configure the backend pool (which servers), the algorithm, the health check endpoint, and SSL — a few lines of config or a console setting. **Auto-scaling groups** (Part 2) auto-register/deregister servers with the LB as they spin up/down.

<a name="interview"></a>
# 10. Interview questions & answers

### Q: "What is a load balancer and why do you need one?"
> *"A load balancer sits between clients and a pool of servers and distributes incoming traffic across them. You need it for three reasons: to spread load so no single server is overwhelmed, to provide high availability by routing around failed servers, and to enable horizontal scaling by letting you add or remove servers freely behind it. It's the single entry point that makes many servers look like one to the client."*

### Q: "How does a load balancer know a server is down?"
> *"Health checks. With active health checks, the load balancer periodically pings a health endpoint like GET /health; if the server doesn't return a 200, it's marked unhealthy and taken out of rotation, then re-added automatically when it recovers. There are also passive health checks, where the load balancer watches real traffic and marks a server unhealthy if it starts erroring or timing out."*

### Q: "Layer 4 vs Layer 7 load balancing?"
> *"Layer 4 operates at the transport layer — routes based on IP and port without looking at content, so fast but not smart. Layer 7 operates at the application layer — reads the HTTP request, so it can route based on URL path, headers, or cookies, send /api and /images to different pools, and terminate SSL. L4 is a fast dumb splitter; L7 is a smart content-aware router. Most web apps use L7."*

### Q: "Which load balancing algorithm would you use?"
> *"It depends. Round robin for uniform requests and equal servers. Least connections when request durations vary, so busy servers don't get piled on. Weighted round robin when servers have different capacities. And IP hash when I need the same client to reach the same server for stickiness — though I'd prefer stateless servers with a shared session store."*

### Q: "Isn't the load balancer itself a single point of failure?"
> *"Yes, if you run only one. So in production I'd make it redundant — run multiple in active-passive or active-active with a floating IP that fails over to a standby, or use a managed cloud load balancer which is highly available by design. That way there's no single point of failure."*

### Q: "How do sticky sessions work and would you use them?"
> *"Sticky sessions route a given user consistently to the same server, usually via a cookie or IP hash. They're needed if servers store session state in their own memory. But I'd generally avoid them — they're fragile, because if that server dies the user loses their session, and they unbalance load. I'd prefer stateless servers that store sessions in shared Redis or use JWTs, so any server can handle any request."*

<a name="cheatsheet"></a>
# 11. Cheat Sheet — everything on one page

### Why multiple servers
Capacity limit · single point of failure · no room to scale → run many (horizontal, Part 2) → need something to route → **load balancer**.

### What it is
Receptionist between clients and a server pool. Purposes: distribute load · high availability · scalability · health monitoring · SSL termination.

### How it works
Client → LB (public face) → picks a HEALTHY server via algorithm → forwards → response back. Client never sees the servers (layered system).

### L4 vs L7
- **L4** — IP/port, no content, fast, dumb splitter (AWS NLB).
- **L7** — reads HTTP (URL/headers/cookies), smart routing + SSL termination (AWS ALB, Nginx). Most web apps.

### Algorithms
| Algorithm | Use for |
|---|---|
| Round robin | Uniform requests, equal servers |
| Weighted round robin | Unequal server capacity |
| Least connections | Varying request durations |
| Least response time | Latency-sensitive |
| IP hash | Session stickiness |
| Random / power-of-two | Cheap + effective |

### Health checks
- **Active** — ping `/health` on a schedule; non-200 → remove; recovered → re-add.
- **Passive** — watch real traffic for errors/timeouts.
→ This is what delivers **high availability**.

### Sticky sessions
Route a user to the same server (cookie/IP hash). Fragile (server dies → lost session; unbalanced). **Prefer stateless servers + shared Redis / JWT.**

### LB single point of failure
Make the LB redundant — multiple LBs (active-passive/active-active) + floating IP failover, or a managed cloud LB.

### Implementation
- **Software:** Nginx, HAProxy, Envoy.
- **Cloud (common):** AWS ALB (L7) / NLB (L4), GCP, Azure.
- **Hardware:** F5, Citrix.
- Sits between every tier; auto-scaling groups register/deregister servers automatically.

### Golden lines
- "Health checks turn multiple servers into high availability."
- "L4 = fast dumb splitter; L7 = smart content router."
- "Prefer stateless servers over sticky sessions."
- "Make the LB itself redundant — no single point of failure."
