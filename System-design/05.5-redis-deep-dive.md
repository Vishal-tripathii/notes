<a name="what"></a>
# 1. What is Redis?

**Redis (REmote DIctionary Server) is an in-memory, key-value data store** — often called a **data structure server** because it stores rich structures (lists, sets, sorted sets, hashes), not just simple values.

Two defining traits drive *everything*:
1. **In-memory** → data lives in RAM → **blazing fast** (microseconds).
2. **Key-value** → simple `key → value` lookups → **O(1)** access, dead simple model.

---

<a name="in-memory"></a>
# 2. In-memory database — why it's so fast

Most databases (PostgreSQL, MongoDB — Part 8) store data on **disk**. Redis keeps its data in **RAM**.
```
Disk read:  ~10,000,000 nanoseconds (milliseconds)   🐌
RAM read:   ~100 nanoseconds                          ⚡ ~100,000x faster
```
Reading from RAM is ~**100,000× faster** than disk → Redis serves requests in **microseconds** and handles **100,000+ ops/sec** on a single node.

## The trade-off: RAM is limited and volatile
- **Limited** — RAM is smaller/pricier than disk. Keep only the **hot, small** data in Redis.
- **Volatile** — RAM is wiped on restart/crash. By default, restart = data gone.

## Persistence — avoiding total data loss
- **RDB (snapshots)** — periodic full dump to disk (e.g. every 5 min). Fast, compact; can lose the last few minutes on a crash.
- **AOF (Append-Only File)** — logs *every write*, replays on restart. More durable; larger/slower.

> **Interview key:** even with persistence, Redis is **memory-first**. Not your primary source of truth for critical data (Part 4: Redis is **AP-leaning**, can lose acknowledged writes). It's a **fast layer**, not the system of record. Bank balance → Postgres; cache of it → Redis.

<a name="kv"></a>
# 3. Key-value store + the data structures

At core, Redis is a giant dictionary: `key → value`.
```
SET user:1:name "Alice"      →   stores "Alice" under key "user:1:name"
GET user:1:name              →   returns "Alice"
```
The **value** can be one of several **data structures** — picking the right one is what makes Redis powerful per use case:

| Structure | Holds | Key commands | Powers |
|---|---|---|---|
| **String** | Text/number/binary | `SET`, `GET`, `INCR` | Cache, counters, OTP |
| **Hash** | Field-value pairs (an object) | `HSET`, `HGET` | Storing objects (a user) |
| **List** | Ordered list | `LPUSH`, `RPOP` | Queues, recent items |
| **Set** | Unique unordered items | `SADD`, `SISMEMBER` | Tags, unique visitors |
| **Sorted Set (ZSet)** | Unique items **with a score, kept sorted** | `ZADD`, `ZREVRANGE` | **Leaderboards**, rankings |
| **TTL (on any key)** | Auto-expiry | `EXPIRE`, `SET ... EX` | Sessions, OTP, rate limiting |

> **TTL (expiry)** isn't a structure — it's a superpower on *any* key: "delete automatically after N seconds." The backbone of sessions, OTP, and rate limiting.

Every use case below = "the right data structure + TTL."

<a name="usecases"></a>
# 4. Use cases (with real-life mechanics)

## A. Cache (the #1 use — Part 5 expanded)
Store slow DB query / computation results so most reads skip the DB.
```
GET product:123        → HIT? return instantly (~1ms)
                       → MISS? query Postgres, then SET product:123 <data> EX 3600
```
**Real life:** Amazon/Flipkart product pages, Instagram feeds, any read-heavy data.
**Why Redis:** microsecond reads + TTL for auto-freshness.

## B. Sessions (Part 2 expanded)
Store logged-in sessions so all stateless servers share them.
```
SET session:a3f9x7 '{"userId":42,"role":"rider"}' EX 1800   (30-min expiry)
GET session:a3f9x7   → who is this user?
DEL session:a3f9x7   → logout (instant revocation)
```
**Real life:** every large web app's login system.
**Why Redis:** fast (looked up on *every* request), shared across servers, TTL auto-expires idle sessions.

## C. Leaderboard (the showcase — Sorted Sets)
Each member has a **score**; Redis keeps them **auto-sorted** → instant ranking.
```
ZADD leaderboard 1500 "alice"      → add/update Alice's score
ZADD leaderboard 2300 "bob"
ZADD leaderboard 900  "carol"

ZREVRANGE leaderboard 0 9 WITHSCORES   → top 10, already sorted! ⚡
ZREVRANK leaderboard "alice"           → Alice's exact rank
```
**Real life:** gaming leaderboards, trading apps (top gainers), any "top N."
**Why Redis:** sorted set does inserts *and* ranking in **O(log n)**. SQL would need an expensive `ORDER BY` over millions of rows every request.

## D. OTP (One-Time Password)
Store a temporary code that **auto-expires** — TTL does the work.
```
SET otp:+9199xxxx 483920 EX 300     → OTP valid for 5 minutes
GET otp:+9199xxxx                   → verify what the user typed
DEL otp:+9199xxxx                   → delete once used (one-time)
```
**Real life:** login/signup verification, 2FA.
**Why Redis:** OTP *should* disappear after 5 min — TTL expires it automatically (no cleanup cron). Ephemeral; never needs the main DB.

## E. Rate Limiting
Limit requests per user (e.g. "100/minute") to prevent abuse. Uses **atomic INCR + TTL**.
```
INCR rate:user42        → increment counter (returns new count)
EXPIRE rate:user42 60   → set 60s window (only on first request)

if count > 100:  reject (429 Too Many Requests)
```
**How:** first request creates the counter + 60s expiry; each request increments; over the limit → block; after 60s the key expires and count resets.
**Real life:** API rate limits (Twitter/GitHub), login-attempt throttling, DDoS protection.
**Why Redis:** `INCR` is **atomic** (safe under thousands of concurrent requests — isolation idea from Part 8's ACID), and fast enough to check on *every* request.

## Bonus (name-drop in interviews)
- **Pub/Sub** — `PUBLISH`/`SUBSCRIBE` for real-time notifications, chat.
- **Queues** — Lists (`LPUSH`/`RPOP`) as a simple job queue.
- **Distributed locks** — coordinate across servers (`SETNX`).

> **Pattern:** Redis wins wherever you need **speed + the right built-in structure + auto-expiry**, for **hot, ephemeral, or real-time** data.

<a name="strategies"></a>
# 5. Cache strategies with use cases

From Part 5 — here mapped to **when you'd actually use each** (the interview-valuable part).

## Read strategies
### Cache-Aside (Lazy Loading) — the default
App checks cache; on miss, loads DB and populates cache.
```
Read: cache miss → fetch DB → SET into cache → return
```
- **Use when:** general read-heavy data; not everything needs caching.
- **Real life:** **product catalog, user profiles, Instagram feed.** Go-to ~90% of the time.

### Read-Through
Cache layer itself loads from DB on a miss (app talks only to cache).
- **Use when:** you want caching logic centralized in the cache layer.
- **Real life:** managed caching layers / CDN-style setups.

## Write strategies
### Write-Through — write to cache + DB together
- **Use when:** cache must be **always fresh**; reads never stale.
- **Real life:** **profile settings** — after update, next read must show the new value. Slower writes OK.

### Write-Back (Write-Behind) — write to cache now, DB later
- **Use when:** **write-heavy**, high-throughput, slight loss tolerable.
- **Real life:** **view counts, like counts, analytics** — millions of increments, batched to DB later (eventual-consistent — Part 4/5). Fast writes > perfect durability.

### Write-Around — write to DB only, cache filled on read
- **Use when:** data is **written but rarely re-read soon**; caching on write wastes memory.
- **Real life:** **logs / audit records, old orders** — write straight to DB; cache only if read later.

## Strategy → use case quick map
| Strategy | Best for | Real-life example |
|---|---|---|
| **Cache-aside** | General read-heavy (default) | Product catalog, feeds |
| **Read-through** | Centralized cache logic | Managed cache layers |
| **Write-through** | Must-be-fresh reads | Profile settings |
| **Write-back** | Write-heavy, loss-tolerant | Like/view counters |
| **Write-around** | Written, rarely re-read | Logs, audit records |

> **Interview move:** don't just name strategies — **tie each to a use case.** "Write-back for view counts (frequent writes, loss tolerable), write-through for profile settings (reads must be fresh)." Shows judgment.

<a name="interview"></a>
# 6. Interview questions & answers

### Q: "Why Redis?"
> *"Redis is an in-memory key-value store, so it's extremely fast — microsecond reads because data lives in RAM instead of on disk. It also has purpose-built data structures like sorted sets for leaderboards and atomic operations like INCR for counters and rate limiting, plus built-in TTL for auto-expiring data like sessions and OTPs. So I'd reach for it whenever I need speed and the right data structure for hot, ephemeral, or real-time data — caching, sessions, leaderboards, rate limiting."*

### Q: "Why not just use MongoDB for these?"
> *"Because they solve different problems. MongoDB is a disk-based primary database — the durable source of truth for large, persistent, queryable data. Redis is an in-memory speed layer. For a leaderboard, Redis's sorted set gives ranking in O(log n), whereas MongoDB would need an expensive sort on every request. For sessions, OTPs, and rate limits, Redis's built-in TTL auto-expires the data — MongoDB has no equally elegant, fast way to do that at that speed. And for caching, MongoDB is on disk, so it's simply too slow. So it's not 'Redis instead of MongoDB' — it's 'Redis alongside MongoDB': MongoDB for durable data, Redis for the fast, ephemeral layer."*

### Q: "What happens to Redis data if the server restarts?"
> *"By default it's lost, because it's in memory. Redis offers persistence — RDB takes periodic snapshots, and AOF logs every write and replays it on restart. But it's still memory-first, so I wouldn't treat it as my primary source of truth for critical data. It's a fast layer in front of a durable database."*

### Q: "How would you build rate limiting with Redis?"
> *"A counter per user with a TTL. On each request I INCR a key like rate:user42, and on the first request set a 60-second expiry. If the count exceeds the limit, say 100, I reject with a 429. After 60 seconds the key expires and the count resets. INCR is atomic, so it's safe under high concurrency, and fast enough to run on every request."*

### Q: "How does a Redis leaderboard work?"
> *"With a sorted set. Each player is a member with their score, and Redis keeps them automatically sorted. ZADD adds or updates a score, ZREVRANGE gets the top N already in order, and ZREVRANK gives a player's rank. All O(log n), so it stays fast even with millions of players — which a SQL ORDER BY couldn't match at that scale."*

### Q: "Is Redis single-threaded? Isn't that slow?"
> *"Redis is single-threaded for command execution, but still extremely fast because everything is in memory and there's no lock contention — commands run atomically one after another. That single-threaded model is actually why operations like INCR are safely atomic without extra locking. It scales out via clustering and replicas when one node isn't enough."*

<a name="cheatsheet"></a>
# 7. Cheat Sheet — everything on one page

### Core
- **Redis** = in-memory, key-value **data structure server**. Microsecond-fast (RAM).
- **In-memory** → ~100,000× faster than disk → 100k+ ops/sec.
- **Memory-first** → not a source of truth. Persistence: **RDB** (snapshots) + **AOF** (write log).
- **AP-leaning** (Part 4) — can lose acknowledged writes. Fast layer, not system of record.

### Data structures → use case
| Structure | Command | Use case |
|---|---|---|
| String | `SET`/`GET`/`INCR` | Cache, counters, OTP |
| Hash | `HSET`/`HGET` | Objects (user) |
| List | `LPUSH`/`RPOP` | Queues, recent items |
| Set | `SADD` | Unique items, tags |
| Sorted Set | `ZADD`/`ZREVRANGE` | Leaderboards (O(log n)) |
| TTL (any key) | `EXPIRE`/`EX` | Sessions, OTP, rate limit |

### Use cases (structure + TTL)
- **Cache** — `SET key val EX 3600`; skip the slow DB.
- **Sessions** — `SET session:id ... EX 1800`; shared across servers, auto-expire.
- **Leaderboard** — Sorted Set; `ZADD` + `ZREVRANGE`; instant ranking.
- **OTP** — `SET otp:phone code EX 300`; auto-expires, one-time (`DEL`).
- **Rate limit** — `INCR` + `EXPIRE 60`; atomic, block over limit.
- **Bonus** — Pub/Sub, queues (Lists), distributed locks (`SETNX`).

### Cache strategies → use case
| Strategy | Use case |
|---|---|
| Cache-aside | General read-heavy (default) — catalog, feeds |
| Read-through | Centralized cache logic |
| Write-through | Must-be-fresh — profile settings |
| Write-back | Write-heavy, loss-OK — like/view counters |
| Write-around | Written, rarely re-read — logs |

### Why Redis vs MongoDB
- **MongoDB** = disk-based durable primary DB (large, queryable, persistent).
- **Redis** = in-memory fast layer (hot, ephemeral, real-time).
- **Use together**, not instead: Mongo/Postgres = source of truth; Redis = speed layer.

### Interview one-liners
- "Redis wins on **speed + right data structure + auto-expiry**."
- "Sorted set → O(log n) ranking, beats SQL ORDER BY at scale."
- "INCR is atomic → safe rate limiting under high concurrency."
- "Memory-first → fast layer, not source of truth."
