<a name="types"></a>
## 1. Lock types: shared vs exclusive, row vs table

| Lock | Who can also hold it | Taken by |
|---|---|---|
| **Shared (S)** | other shared locks — many readers at once | `SELECT ... FOR SHARE` |
| **Exclusive (X)** | nobody — blocks other S and X locks on the same row | `UPDATE`, `DELETE`, `SELECT ... FOR UPDATE` |

**Granularity:** modern engines (Postgres, InnoDB) lock **rows** for normal DML, so two transactions updating *different* rows of the same table don't block each other. **Table-level** locks come mostly from DDL (`ALTER TABLE`, `DROP`, `TRUNCATE`) — which is why a schema migration can freeze a whole table ([Part 21](21-schema-validation-and-migrations.md)).

**Plain `SELECT` takes no row lock** in Postgres or InnoDB — thanks to MVCC ([Part 15 §3](15-mongodb-transactions-and-concurrency.md), [Part 22](22-storage-internals.md)) it reads a snapshot. That's great for throughput, and it's also exactly why "read, check in code, then write" is racy: the read reserved nothing.

**InnoDB gotcha — it locks the index entries it *scans*, not just the rows it changes.** `UPDATE orders SET x = 1 WHERE status = 'pending'` with no index on `status` scans (and locks) every row in the table under Repeatable Read. A missing index turns a row lock into an effective table lock — and into deadlocks.

<a name="for-update"></a>
## 2. `SELECT ... FOR UPDATE` and friends

`FOR UPDATE` turns a read into a **reservation**: the selected rows are X-locked until the transaction ends, so anyone else trying to update or `FOR UPDATE` them waits.

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- row locked from here
-- application checks balance >= 100
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;                                                -- lock released
```

| Variant | Behaviour |
|---|---|
| `FOR UPDATE` | exclusive row lock; waits if someone else holds it |
| `FOR SHARE` | shared lock — others can read-lock too, nobody can update (MySQL ≤5.7 syntax: `LOCK IN SHARE MODE`) |
| `FOR NO KEY UPDATE` (Postgres) | weaker exclusive lock that doesn't block inserts of rows *referencing* this one via FK — what a plain `UPDATE` takes |
| `... NOWAIT` | fail immediately instead of waiting if the row is locked |
| `... SKIP LOCKED` | silently skip locked rows (§7) |

**Rules that matter:**
- Locks only last as long as the transaction — `FOR UPDATE` in autocommit mode is pointless (it locks and immediately unlocks).
- Keep the transaction **short**. Never hold a row lock across a network call (payment gateway, email, another microservice) — every other request touching that row queues behind it.

<a name="lost-update"></a>
## 3. Lost update

Two transactions do **read → modify in application code → write** on the same row; the second write silently overwrites the first.

```
balance = 100
T1: SELECT balance → 100
T2: SELECT balance → 100
T1: UPDATE accounts SET balance = 150   (100 + 50 deposit)    COMMIT
T2: UPDATE accounts SET balance = 70    (100 - 30 withdrawal) COMMIT
Final: 70   — should be 120. T1's deposit is lost.
```

No dirty read happened, nothing uncommitted was seen — so the textbook anomaly list in Part 04 doesn't even name it. It is the most common concurrency bug in CRUD apps ("save the whole form object back").

**Fixes, best first:**
1. **Atomic update — let the DB do the arithmetic:** `UPDATE accounts SET balance = balance + 50 WHERE id = 1`. The row's current value is read and written under the row lock; no gap.
2. **Pessimistic lock:** `SELECT ... FOR UPDATE` before the read (§2).
3. **Optimistic lock:** `UPDATE ... SET balance = 150, version = version + 1 WHERE id = 1 AND version = 7` → 0 rows affected means someone else won; reload and retry ([Part 15 §2](15-mongodb-transactions-and-concurrency.md)).
4. **Isolation level:** Postgres **Repeatable Read** detects it — T2's `UPDATE` fails with `could not serialize access due to concurrent update`, and the app retries. ⚠️ **MySQL Repeatable Read does *not* detect it** — InnoDB's `UPDATE` just writes over the latest committed value. Don't rely on isolation level alone if the code may run on MySQL.

<a name="write-skew"></a>
## 4. Write skew

Two transactions read the **same set of rows**, each decides based on it, and each writes a **different** row. Neither overwrote the other, yet together they break an invariant.

The classic example — hospital rule: *at least one doctor must stay on call*:

```
on_call: alice = true, bob = true
T1 (alice): SELECT count(*) FROM doctors WHERE on_call → 2   → "ok, someone else covers"
T2 (bob):   SELECT count(*) FROM doctors WHERE on_call → 2   → "ok, someone else covers"
T1: UPDATE doctors SET on_call = false WHERE name = 'alice';  COMMIT
T2: UPDATE doctors SET on_call = false WHERE name = 'bob';    COMMIT
Result: nobody on call.
```

Other real shapes of the same bug: two bookings for overlapping time slots in the same room; two users claiming the same username when the check is `SELECT ... WHERE username = ?` followed by an insert; spending limits checked across several rows.

**Why it's nasty:** **snapshot isolation (Postgres Repeatable Read, InnoDB Repeatable Read) allows it**, because the two transactions wrote different rows — there's no row-level conflict to detect.

**Fixes:**
- **`SERIALIZABLE` isolation** — Postgres's SSI detects the read/write dependency and aborts one transaction (`40001 serialization_failure`); the app retries.
- **Lock the rows you read:** `SELECT ... FROM doctors WHERE on_call FOR UPDATE` — now T2 blocks on T1's locked rows and re-reads after T1 commits.
- **Turn it into a constraint the DB can enforce:** a unique index (usernames), a Postgres **exclusion constraint** for overlapping ranges (`EXCLUDE USING gist (room WITH =, during WITH &&)`), or a single "counter" row that every transaction must update (materializing the conflict).

<a name="matrix"></a>
## 5. What each isolation level actually prevents

The SQL standard's table (Part 04 §3) only lists three anomalies, and engines deviate from it. The real behaviour of the two engines you'll be asked about:

| Anomaly | PG Read Committed *(default)* | PG Repeatable Read | PG Serializable | MySQL Read Committed | MySQL Repeatable Read *(default)* | MySQL Serializable |
|---|---|---|---|---|---|---|
| Dirty read | ✅ prevented | ✅ | ✅ | ✅ | ✅ | ✅ |
| Non-repeatable read | ❌ allowed | ✅ | ✅ | ❌ | ✅ | ✅ |
| Phantom read | ❌ | ✅ (snapshot) | ✅ | ❌ | ✅ for plain reads (snapshot); locking reads use next-key locks | ✅ |
| **Lost update** | ❌ | ✅ (aborts) | ✅ | ❌ | ❌ **allowed** | ✅ |
| **Write skew** | ❌ | ❌ **allowed** | ✅ (aborts) | ❌ | ❌ | ✅ (via locking) |

Notes:
- Postgres has no real Read Uncommitted — asking for it gives you Read Committed.
- MySQL `SERIALIZABLE` works by silently turning every plain `SELECT` into `SELECT ... FOR SHARE`, so it blocks (and deadlocks) more rather than aborting.
- "Aborts" means the **application must catch the serialization error and retry the whole transaction** — not just the failed statement. Code that runs at Repeatable Read/Serializable without a retry loop just turns race conditions into 500 errors.

<a name="deadlocks"></a>
## 6. Deadlocks

### How one happens

Two transactions each hold a lock the other needs:

```
T1: UPDATE accounts SET ... WHERE id = 1;   -- T1 locks row 1
T2: UPDATE accounts SET ... WHERE id = 2;   -- T2 locks row 2
T1: UPDATE accounts SET ... WHERE id = 2;   -- waits for T2
T2: UPDATE accounts SET ... WHERE id = 1;   -- waits for T1  → cycle → deadlock
```

That's just a transfer from 1→2 running at the same time as a transfer from 2→1.

### What the database does

Neither engine lets them wait forever. Each keeps a **wait-for graph** and looks for cycles:
- **InnoDB** detects immediately and rolls back the transaction that's cheapest to undo — error `1213 Deadlock found when trying to get lock; try restarting transaction`.
- **Postgres** waits `deadlock_timeout` (default 1s) before checking, then aborts one — error `40P01 deadlock detected`.

The victim's whole transaction is rolled back. **So deadlocks are not data corruption — they're a retryable error.** They become a problem when they're frequent (throughput) or when the app doesn't retry (user-facing failures).

### How to prevent them

1. **Acquire locks in a consistent order.** For the transfer: always lock the lower account id first, whatever the direction. When updating many rows, sort them first (`... WHERE id IN (...) ORDER BY id FOR UPDATE`). This removes the cycle entirely — the #1 answer.
2. **Keep transactions short** and touch as few rows as possible; no network calls inside.
3. **Index the columns in your `WHERE` clauses** — in InnoDB, an unindexed update locks far more rows than it changes (§1), multiplying overlap.
4. **Set a lock timeout** (`lock_timeout` in Postgres, `innodb_lock_wait_timeout` in MySQL) so a stuck wait fails fast instead of piling up connections.
5. **Retry on deadlock/serialization errors** with a small randomized backoff — always, as a safety net, even after doing 1–4.

**How you'd find them in production:** MySQL `SHOW ENGINE INNODB STATUS` prints the latest deadlock (both statements and the locks held); Postgres logs both queries when `log_lock_waits` is on. [Part 25](25-database-observability.md) covers this.

<a name="skip-locked"></a>
## 7. `SKIP LOCKED` — a job queue in plain SQL

Multiple workers want to grab the next pending job without two of them getting the same one and without blocking each other:

```sql
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;        -- rows another worker has locked are skipped, not waited on

UPDATE jobs SET status = 'processing', worker = 'w3' WHERE id = :id;
COMMIT;
```

Without `SKIP LOCKED`, every worker queues behind the first one's lock on the same "next" row. Postgres 9.5+ and MySQL 8.0+ support it. Good enough for modest job volumes before you reach for a real queue ([System-design Part 13](../System-design/13-message-queues.md)).

<a name="advisory"></a>
## 8. Advisory locks

A lock on an **application-chosen number** rather than a row — useful for "only one instance of this cron job may run" or "serialize work per customer" without a dedicated lock table.

```sql
SELECT pg_try_advisory_lock(42);   -- true if acquired, false if someone else holds it
-- ... do the exclusive work ...
SELECT pg_advisory_unlock(42);
```

Postgres has session- and transaction-scoped variants (`pg_advisory_xact_lock` releases automatically at commit); MySQL has `GET_LOCK('name', timeout)`. Caveat: session-scoped advisory locks don't work through a PgBouncer in transaction mode ([Part 12 §4](12-connection-pooling.md)).

<a name="mongo"></a>
## 9. MongoDB's equivalent

- WiredTiger uses **document-level** concurrency. Single-document updates are atomic and the conditional-update pattern (`updateOne({ _id, stock: { $gt: 0 } }, { $inc: { stock: -1 } })`) prevents lost updates — [Part 15 §4](15-mongodb-transactions-and-concurrency.md).
- There is **no `SELECT ... FOR UPDATE`**. Inside a transaction, two transactions writing the same document cause a **`WriteConflict`**; the loser is aborted with the `TransientTransactionError` label and must be retried — `session.withTransaction()` does that retry for you.
- To lock a document you only *read* (the write-skew case), write a dummy field to it inside the transaction (e.g. `$set: { lockedAt: new Date() }`) — a deliberate write conflict that serializes the two transactions.
- Mongo transactions run at **snapshot isolation**, so write skew is possible there too.

<a name="interview"></a>
## 10. Interview Questions & Answers

**Q: What's a lost update, and how do you prevent it?**
A: Two transactions read the same row, modify it in application code, and write it back — the second write overwrites the first, even though nobody read uncommitted data. Best fix is an atomic update (`SET balance = balance + 50`) so the DB does read-and-write under the row lock. Otherwise `SELECT ... FOR UPDATE`, or optimistic locking with a version column. Postgres Repeatable Read detects it and aborts one transaction; MySQL Repeatable Read does not.

**Q: What's write skew? Give an example Repeatable Read still allows.**
A: Two transactions read the same set of rows, each makes a decision from it, and each updates a *different* row — together they violate an invariant. The on-call doctors example: both see two doctors on call, both go off call, now nobody is. Snapshot isolation allows it because there's no conflicting write on the same row. Fix with `SERIALIZABLE`, `FOR UPDATE` on the rows you read, or turning the invariant into a constraint the DB enforces.

**Q: What does `SELECT ... FOR UPDATE` do, and when would you use it?**
A: It takes an exclusive lock on the selected rows until the transaction ends, so concurrent writers and other `FOR UPDATE`s wait. Use it when you must read a value, decide in code, and then write — so the read becomes a reservation. Keep the transaction short and never hold the lock across a network call.

**Q: What's a deadlock, and what does the database do about it?**
A: A cycle of transactions each waiting for a lock the other holds — e.g. transfer 1→2 and transfer 2→1 at the same time. The DB detects the cycle in its wait-for graph and rolls back one victim with a deadlock error (MySQL 1213, Postgres 40P01). It's a retryable error, not corruption.

**Q: How do you prevent deadlocks?**
A: Acquire locks in a consistent order (always lock the lower id first, sort rows before locking them), keep transactions short, index the `WHERE` columns so fewer rows get locked, set a lock timeout, and always retry on deadlock errors as a safety net.

**Q: Your app runs at `SERIALIZABLE`. What must the code do?**
A: Catch serialization failures (and deadlocks) and retry the **whole** transaction from the start, usually with a small randomized backoff. Without a retry loop, stronger isolation just turns races into user-facing errors.

**Q: How would you build a job queue on a SQL table with several workers?**
A: `SELECT ... WHERE status = 'pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`, then mark the row as processing in the same transaction. `SKIP LOCKED` lets each worker take a different row instead of queuing behind the same one.

<a name="cheatsheet"></a>
## 11. Cheat Sheet

- Shared lock = many readers; exclusive lock = one writer. Row locks for DML, table locks mostly from DDL. Plain `SELECT` locks nothing (MVCC snapshot).
- `FOR UPDATE` = read becomes a reservation until commit. Variants: `FOR SHARE`, `NOWAIT`, `SKIP LOCKED`.
- **Lost update** = read-modify-write overwrites another write. Fix: `SET x = x + n`, `FOR UPDATE`, or version column. PG RR catches it; **MySQL RR doesn't**.
- **Write skew** = both read the same rows, write different rows, invariant breaks. Snapshot isolation allows it. Fix: `SERIALIZABLE`, `FOR UPDATE` on what you read, or a DB constraint.
- Deadlock = lock cycle; DB kills one victim (MySQL 1213, PG 40P01). Prevent: **consistent lock order**, short transactions, indexed `WHERE`s, lock timeouts, retry.
- Stronger isolation ⇒ the app **must retry** serialization failures.
- InnoDB locks every index entry it scans — a missing index = far more locking.
- Mongo: no `FOR UPDATE`; write conflicts abort with `TransientTransactionError` → `withTransaction()` retries.
