<a name="null"></a>
## 1. NULL and three-valued logic

`NULL` means **unknown**, not "empty" or "zero." Any comparison with an unknown is itself unknown, so SQL logic has three values: `TRUE`, `FALSE`, `UNKNOWN`.

```sql
SELECT NULL = NULL;      -- NULL (unknown), not TRUE
SELECT NULL <> 5;        -- NULL
SELECT NULL + 10;        -- NULL — arithmetic with NULL is NULL
```

**`WHERE` keeps only rows where the condition is `TRUE`** — `UNKNOWN` rows are dropped just like `FALSE` ones.

```sql
-- users: 100 rows, 12 have country = NULL
SELECT count(*) FROM users WHERE country = 'IN';     -- say 40
SELECT count(*) FROM users WHERE country <> 'IN';    -- 48, not 60 — the 12 NULLs are in neither
SELECT count(*) FROM users WHERE country <> 'IN' OR country IS NULL;   -- 60
```

The tools:
- `IS NULL` / `IS NOT NULL` — the only correct way to test for NULL (`= NULL` is never true).
- `COALESCE(a, b, c)` — first non-NULL argument: `COALESCE(nickname, first_name, 'Guest')`.
- `NULLIF(a, b)` — NULL if equal; classic use is avoiding divide-by-zero: `total / NULLIF(count, 0)`.
- `IS DISTINCT FROM` (Postgres, standard) — NULL-safe comparison: `NULL IS DISTINCT FROM NULL` is `FALSE`. MySQL: `<=>`.

NULLs elsewhere:
- **Aggregates skip NULLs** ([Part 00 §5](00-sql-basics.md)). `AVG(rating)` averages only rated rows.
- **`UNIQUE` allows multiple NULLs** in Postgres and MySQL (NULLs aren't equal to each other). Postgres 15+ can opt out with `UNIQUE NULLS NOT DISTINCT`.
- **Sorting:** Postgres sorts NULLs **last** in `ASC` (first in `DESC`); MySQL sorts them **first** in `ASC`. Be explicit with `NULLS FIRST` / `NULLS LAST` (Postgres).
- **Joins:** `ON a.x = b.x` never matches NULL to NULL.

<a name="not-in"></a>
## 2. The `NOT IN` + NULL trap

```sql
-- "employees who are not managers"
SELECT name FROM employees
WHERE id NOT IN (SELECT manager_id FROM employees);   -- returns ZERO rows
```

The CEO's `manager_id` is NULL, so the subquery returns `(3, 7, NULL, ...)`. `id NOT IN (3, 7, NULL)` means `id <> 3 AND id <> 7 AND id <> NULL` — and `id <> NULL` is UNKNOWN, so the whole condition is never TRUE. **A single NULL in a `NOT IN` list makes it return nothing.**

Fixes:
```sql
-- NOT EXISTS — NULL-safe, and the idiomatic anti-join
SELECT e.name FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM employees m WHERE m.manager_id = e.id);

-- or filter the NULLs out of the subquery
WHERE id NOT IN (SELECT manager_id FROM employees WHERE manager_id IS NOT NULL);
```

**Default to `NOT EXISTS` over `NOT IN` with subqueries.** (`IN` — without `NOT` — is not affected: a NULL in the list just never matches.)

<a name="subqueries"></a>
## 3. Subqueries — scalar, `IN`, correlated, derived tables

```sql
-- Scalar subquery: returns exactly one value
SELECT name, salary, (SELECT AVG(salary) FROM employees) AS company_avg FROM employees;

-- IN subquery: a list
SELECT * FROM orders WHERE customer_id IN (SELECT id FROM customers WHERE city = 'Pune');

-- Correlated subquery: references the outer row → logically runs once per outer row
SELECT e.name, e.salary FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees x WHERE x.dept_id = e.dept_id);

-- Derived table (subquery in FROM) — must have an alias
SELECT dept_id, avg_sal FROM (
  SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id
) d WHERE avg_sal > 50000;
```

**Correlated subqueries aren't automatically slow** — optimizers often rewrite them into joins. But when they aren't rewritten (complex expressions, older MySQL), they genuinely execute per row; `EXPLAIN` shows `DEPENDENT SUBQUERY` (MySQL) or `SubPlan` (Postgres). The rewrite is usually a join against a grouped derived table or a window function:

```sql
SELECT name, salary FROM (
  SELECT name, salary, AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg FROM employees
) t WHERE salary > dept_avg;
```

A scalar subquery that returns more than one row is a runtime error.

<a name="exists"></a>
## 4. `EXISTS` vs `IN` vs `JOIN`

```sql
-- customers who have at least one order — three ways
SELECT * FROM customers c WHERE c.id IN (SELECT customer_id FROM orders);
SELECT * FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
SELECT DISTINCT c.* FROM customers c JOIN orders o ON o.customer_id = c.id;
```

- **`IN` and `EXISTS`** both express a **semi-join** ("keep the left row if a match exists, once"). Modern Postgres and MySQL 8 usually plan them identically. `EXISTS` can stop at the first match per row.
- **`JOIN` is not the same thing** — a customer with 5 orders appears 5 times, so you'd need `DISTINCT`, which costs a sort/hash. Use `JOIN` when you need columns *from* the orders; use `EXISTS`/`IN` when you're only filtering.
- The real difference is **`NOT IN` vs `NOT EXISTS`** — the NULL trap (§2).

The old folk rule "`EXISTS` for big subqueries, `IN` for small lists" mostly dates from older optimizers; say that you'd check `EXPLAIN` rather than rely on it.

<a name="anti-join"></a>
## 5. Anti-joins — "rows with no match"

"Customers who never ordered" — two standard forms:

```sql
-- NOT EXISTS
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- LEFT JOIN ... IS NULL
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;              -- test a column that's never NULL in a real match, e.g. the PK
```

Both are planned as an anti-join and are equally fast with an index on `orders.customer_id`. The common bug in the `LEFT JOIN` form is putting a filter on the right table in `WHERE` instead of `ON`:

```sql
-- "customers with no orders in 2026"
LEFT JOIN orders o ON o.customer_id = c.id AND o.created_at >= '2026-01-01'   -- ✅ filter in ON
WHERE o.id IS NULL;

LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= '2026-01-01' AND o.id IS NULL;   -- ❌ always empty: the WHERE needs o to exist AND not exist
```

General rule: **a `WHERE` condition on the right-hand table of a `LEFT JOIN` silently turns it into an `INNER JOIN`** (unmatched rows have NULLs there, and NULL fails the condition).

<a name="union"></a>
## 6. `UNION` vs `UNION ALL`

```sql
SELECT email FROM customers
UNION                      -- removes duplicates → extra sort/hash step
SELECT email FROM newsletter_subscribers;

SELECT email FROM customers
UNION ALL                  -- keeps everything → just appends, cheaper
SELECT email FROM newsletter_subscribers;
```

Use `UNION ALL` unless you actually need deduplication — it's a frequent hidden cost. Both sides must have the same number of columns with compatible types; column names come from the first query; `ORDER BY` applies to the combined result. Related set operators: `INTERSECT` (rows in both), `EXCEPT` (rows in the first but not the second; MySQL 8.0.31+).

<a name="case"></a>
## 7. `CASE` and conditional aggregation

```sql
-- labelling
SELECT id, amount,
       CASE WHEN amount >= 10000 THEN 'high'
            WHEN amount >= 1000  THEN 'medium'
            ELSE 'low' END AS bucket
FROM orders;
```

**Conditional aggregation** — several counts/sums in one pass, the standard way to **pivot** rows into columns:

```sql
SELECT customer_id,
       COUNT(*)                                              AS total_orders,
       SUM(CASE WHEN status = 'paid'     THEN amount ELSE 0 END) AS paid_amount,
       COUNT(CASE WHEN status = 'refunded' THEN 1 END)           AS refunds     -- no ELSE → NULL → not counted
FROM orders
GROUP BY customer_id;

-- Postgres shorthand
SELECT customer_id, COUNT(*) FILTER (WHERE status = 'refunded') AS refunds FROM orders GROUP BY customer_id;
```

One scan instead of three separate `GROUP BY` queries joined together. `CASE` also works in `ORDER BY` (custom sort orders) and inside `UPDATE ... SET`.

<a name="ranking"></a>
## 8. `ROW_NUMBER` vs `RANK` vs `DENSE_RANK`

For salaries `100, 100, 90, 80`:

| salary | `ROW_NUMBER()` | `RANK()` | `DENSE_RANK()` |
|---|---|---|---|
| 100 | 1 | 1 | 1 |
| 100 | 2 | 1 | 1 |
| 90 | 3 | **3** | **2** |
| 80 | 4 | 4 | 3 |

- **`ROW_NUMBER`** — unique sequence, ties broken arbitrarily (add a tie-breaker column to `ORDER BY` to make it deterministic). Use for **de-duplication** ("keep one row per email") and **top-N rows** per group.
- **`RANK`** — ties share a rank, then it **skips** (1, 1, 3). Sports-style ranking.
- **`DENSE_RANK`** — ties share a rank, **no gaps** (1, 1, 2). Use for **"Nth highest value"** — the 2nd highest *salary* is 90, which is `DENSE_RANK = 2`.

Other window functions you'll use in answers: `LAG(col)` / `LEAD(col)` (previous/next row — month-over-month change), `SUM(col) OVER (ORDER BY ...)` (running total), `NTILE(4)` (quartiles), `FIRST_VALUE` / `LAST_VALUE`.

⚠️ **Running-total frame trap:** with `ORDER BY` and no explicit frame, the default is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which includes **all rows tied** with the current one. Two orders on the same date both get the day's full total. Use `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for a true row-by-row running total.

<a name="window-filter"></a>
## 9. Filtering on a window function

Window functions are computed in the `SELECT` step, after `WHERE` and `HAVING` ([Part 00 §1](00-sql-basics.md)) — so you can't filter on them directly:

```sql
SELECT *, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
FROM employees
WHERE rn <= 3;            -- ❌ error: rn doesn't exist yet

WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn <= 3;   -- ✅ wrap in a CTE or subquery
```

(Some warehouses like Snowflake/BigQuery offer `QUALIFY rn <= 3`; Postgres and MySQL don't.)

<a name="group-by"></a>
## 10. `GROUP BY` strictness

```sql
SELECT dept_id, name, MAX(salary) FROM employees GROUP BY dept_id;   -- ❌ which `name`?
```

Every selected column must be either in `GROUP BY` or inside an aggregate. Postgres rejects this; MySQL with `ONLY_FULL_GROUP_BY` (default since 5.7) rejects it; old MySQL returned an **arbitrary** `name` — not the one with the max salary, a classic silent bug. "The name of the highest-paid person per department" is a ranking problem (§8), not a `GROUP BY` problem. (Exception: Postgres allows other columns of a table whose primary key is in the `GROUP BY`.)

<a name="params"></a>
## 11. Parameterized queries

Never build SQL by string-concatenating user input:

```js
db.query(`SELECT * FROM users WHERE email = '${email}'`);          // ❌ SQL injection
db.query('SELECT * FROM users WHERE email = $1', [email]);          // ✅ value sent separately from the SQL
```

Parameters are sent separately from the SQL text, so input can never change the query's structure. Table/column names can't be parameters — whitelist them. Full coverage, including NoSQL injection like `{ "$ne": null }` in a Mongo filter: [nodejs Part 07](../nodejs/07-authentication-and-security.md).

<a name="interview"></a>
## 12. Interview Questions & Answers

**Q: What does `NULL = NULL` return?**
A: `NULL` (unknown), not true. SQL uses three-valued logic, and `WHERE` keeps only rows where the condition is true, so unknown rows are dropped. Test with `IS NULL`, or use `IS DISTINCT FROM` for a NULL-safe comparison.

**Q: `WHERE id NOT IN (SELECT manager_id FROM employees)` returns zero rows. Why?**
A: The subquery contains a NULL (the CEO has no manager). `NOT IN` expands to `id <> a AND id <> b AND id <> NULL`, and `id <> NULL` is unknown, so the condition is never true. Use `NOT EXISTS`, or filter NULLs out of the subquery.

**Q: `IN` vs `EXISTS` — which is faster?**
A: On modern optimizers usually neither — both become a semi-join and get the same plan; I'd confirm with `EXPLAIN`. The difference that matters is semantic: `NOT IN` breaks with NULLs, `NOT EXISTS` doesn't. And a `JOIN` isn't equivalent because it duplicates left rows for multiple matches.

**Q: How do you find rows in A with no matching row in B?**
A: `NOT EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id)` or `LEFT JOIN b ... WHERE b.id IS NULL`. Index `b.a_id`. With the LEFT JOIN form, put extra conditions on B in the `ON` clause, not `WHERE`, or it becomes an inner join.

**Q: `UNION` vs `UNION ALL`?**
A: `UNION` removes duplicates, which costs a sort or hash; `UNION ALL` just appends. Default to `UNION ALL` unless you need dedup.

**Q: `ROW_NUMBER` vs `RANK` vs `DENSE_RANK`?**
A: For 100, 100, 90: ROW_NUMBER gives 1, 2, 3; RANK gives 1, 1, 3; DENSE_RANK gives 1, 1, 2. ROW_NUMBER for de-duplication and exact top-N rows, DENSE_RANK for "Nth highest value."

**Q: Why can't I put a window function in `WHERE`?**
A: Window functions are computed in the SELECT step, after WHERE runs. Compute it in a CTE or subquery and filter in the outer query.

**Q: How do you count paid and refunded orders per customer in one query?**
A: Conditional aggregation — `SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END)` and `COUNT(CASE WHEN status = 'refunded' THEN 1 END)` grouped by customer (or `COUNT(*) FILTER (WHERE ...)` in Postgres). One scan.

<a name="cheatsheet"></a>
## 13. Cheat Sheet

- NULL = unknown. `NULL = NULL` → NULL. `WHERE` keeps only TRUE. Use `IS NULL`, `COALESCE`, `NULLIF`, `IS DISTINCT FROM`.
- `<> 'x'` excludes NULL rows too. UNIQUE allows many NULLs. NULL sort order differs (PG last, MySQL first).
- **`NOT IN` + a NULL in the subquery = zero rows** → use `NOT EXISTS`.
- `IN`/`EXISTS` = semi-join (same plan usually). `JOIN` duplicates rows.
- Anti-join: `NOT EXISTS` or `LEFT JOIN ... WHERE b.pk IS NULL`; filters on B go in `ON`.
- `WHERE` on the right table of a `LEFT JOIN` = inner join.
- `UNION ALL` by default; `UNION` dedupes (costly).
- Conditional aggregation: `SUM(CASE WHEN ... THEN x ELSE 0 END)` / `FILTER (WHERE ...)` — pivots in one pass.
- ROW_NUMBER 1,2,3 · RANK 1,1,3 · DENSE_RANK 1,1,2. Nth highest → DENSE_RANK.
- Running total: use `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` (default RANGE lumps ties).
- Filter window results via CTE/subquery. Non-grouped columns in SELECT = error (or arbitrary value in old MySQL).
- Always parameterize.
