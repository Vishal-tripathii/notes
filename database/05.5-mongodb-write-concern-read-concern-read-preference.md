<a name="replica-set"></a>
## 1. The replica set, briefly

A MongoDB **replica set** is one **primary** (takes all writes) plus **secondaries** that copy the primary's **oplog** (an ordered log of every write) and replay it. Usually 3 members. Every write lands on the primary first; secondaries are always some milliseconds to seconds behind.

The three knobs answer three different questions:

| Knob | Question it answers | Set on |
|---|---|---|
| **Write concern** | How many members must have a write before the client is told "success"? | writes |
| **Read concern** | How durable/consistent must the data a read returns be? | reads |
| **Read preference** | *Which member* should serve this read? | reads |

<a name="write-concern"></a>
## 2. Write concern — when is a write "done"?

```js
db.orders.insertOne(doc, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } })
```

| Setting | Meaning | Trade-off |
|---|---|---|
| `w: 0` | fire and forget — no acknowledgement at all | fastest; you don't even learn about errors |
| `w: 1` | primary has applied it (in memory) | fast; **can be rolled back** if the primary dies before replicating (§3) |
| `w: "majority"` | a majority of voting members have it | survives failover; adds replication latency to every write |
| `w: <n>` | n members have it | rarely used; "majority" adapts to the set size automatically |
| `j: true` | acknowledged only after the write is in the on-disk **journal** | survives a crash of the acknowledging node |
| `wtimeout` | give up waiting after N ms | ⚠️ a timeout does **not** undo the write — it may still replicate. Treat as "unknown," not "failed" |

**Default:** since MongoDB 5.0 the implicit default is **`w: "majority"`** (it was `w: 1` before; arbiters in the set can change this). Interviewers sometimes still assume `w: 1` — say which version you're talking about.

<a name="rollback"></a>
## 3. Rollback — what `w:1` can lose

```
1. Client writes order #77 with w:1. Primary P applies it, replies "ok".
2. P crashes before any secondary copied #77.
3. Secondary S is elected primary — S has never seen #77.
4. New writes go to S.
5. P comes back as a secondary, finds it has writes S never had,
   and ROLLS BACK #77 (saved to a rollback file, removed from the data).
```

The client was told "success" for an order that no longer exists. **A write acknowledged with `w: "majority"` cannot be rolled back**, because any member that can win an election must already have it. That's the core reason to use `majority` for anything you care about (payments, orders, user signups), and accept `w: 1` only for data that's fine to lose (analytics events, logs).

<a name="read-concern"></a>
## 4. Read concern — which data may a read return?

| Read concern | Returns | Use for |
|---|---|---|
| `"local"` *(default)* | the node's latest data, even if not yet majority-replicated — could later be rolled back | most reads |
| `"available"` | like local; on sharded clusters may return orphaned documents during migrations | lowest latency, rarely chosen deliberately |
| `"majority"` | only data acknowledged by a majority — **never rolled back** | reads that drive decisions (balances, "was this paid?") |
| `"linearizable"` | majority data *and* reflects all writes that completed before the read started; primary only, slow | single-document reads that must be absolutely current (e.g. a lock document) |
| `"snapshot"` | a consistent point-in-time view across documents | inside multi-document transactions |

**Read concern ≠ read preference.** `readConcern: "majority"` on a secondary still returns *majority-committed* data — it's just possibly older than the primary's. Read concern is about **rollback safety**; read preference is about **which node**.

---

<a name="read-preference"></a>
## 5. Read preference — which node serves the read?

| Mode | Reads go to |
|---|---|
| `primary` *(default)* | primary only — always sees the latest writes |
| `primaryPreferred` | primary, or a secondary if no primary is available (e.g. during an election) |
| `secondary` | secondaries only |
| `secondaryPreferred` | secondaries, or the primary if none are available |
| `nearest` | lowest-latency member, primary or secondary |

Extras: **`maxStalenessSeconds`** (min 90) skips secondaries lagging more than that; **tag sets** route to members in a specific region or role (e.g. a dedicated analytics node).

```js
// Mongoose — per connection or per query
mongoose.connect(uri, { readPreference: "secondaryPreferred" });
await Report.find(filter).read("secondary");
```

**When reading from secondaries is right:** analytics/reporting queries you don't want competing with production traffic; geo-distributed reads (`nearest`); data where seconds of staleness are fine.

**When it's wrong:** anything a user just wrote and expects to see; anything that drives a correctness decision. And note it doesn't add write capacity at all — that's sharding ([Part 14](14-sharding.md)).

<a name="causal"></a>
## 6. Causal consistency — read-your-writes on secondaries

The Part 13 bug — update profile, read from a lagging secondary, see the old value — has a MongoDB-native fix besides "read from primary": a **causally consistent session**.

```js
const session = client.startSession({ causalConsistency: true });   // true is the default for sessions

await users.updateOne({ _id }, { $set: { name: "New" } },
  { session, writeConcern: { w: "majority" } });

const u = await users.findOne({ _id },
  { session, readConcern: { level: "majority" }, readPreference: "secondary" });
// guaranteed to see "New" — the driver sends afterClusterTime, and the
// secondary waits until it has replicated up to that point before answering
```

Within one session you get **read-your-writes, monotonic reads, and writes-follow-reads** — even across different members. The guarantee only holds with **`majority` write concern and `majority` read concern**, and only **within the session** (another user's session won't see it any sooner).

<a name="elections"></a>
## 7. Elections & failover

- Members send **heartbeats every 2s**. If the primary isn't heard from for **`electionTimeoutMillis` (10s default)**, a secondary calls an election (Raft-style protocol).
- A candidate needs votes from a **majority of voting members**. That's why replica sets have an **odd number** of voters — 3 members tolerate 1 failure, 5 tolerate 2. With 2 members, losing 1 means no majority and **no primary** at all.
- Max 50 members, max 7 voting.
- During the election (typically a few seconds to ~12s) **there is no primary, so writes fail**. Drivers ship **retryable writes** (`retryWrites=true`, on by default in modern drivers; needs server 3.6+) that retry a failed write once after a new primary appears — safe even for `$inc`, because the server deduplicates by transaction number.
- **Network partition:** the side with the majority elects a primary; an old primary on the minority side **steps down** once it can't see a majority. That prevents two primaries accepting majority-acknowledged writes (split brain) — but `w: 1` writes it accepted just before stepping down are the ones that get rolled back (§3).
- **Arbiters** vote but hold no data. They make 2 data-bearing nodes + 1 arbiter "work," but with one data node down, `w: "majority"` writes can't be satisfied. Prefer 3 data-bearing members.

<a name="configs"></a>
## 8. Putting it together — common configurations

| Use case | Write concern | Read concern | Read preference |
|---|---|---|---|
| Orders, payments, signups | `majority` | `majority` for decision reads, `local` otherwise | `primary` |
| User profile with read-your-writes on replicas | `majority` | `majority` | `secondaryPreferred` **inside a causal session** |
| Analytics / dashboards | n/a | `local` | `secondary` with a tag for an analytics node |
| Click/telemetry events (loss acceptable) | `w: 1` | `local` | `primary` |
| Global app, regional users | `majority` | `local` | `nearest` (+ `maxStalenessSeconds`) |

The pattern to say out loud: **stronger guarantees cost latency**; pick per operation, not one global setting.

<a name="interview"></a>
## 9. Interview Questions & Answers

**Q: What's the difference between write concern, read concern and read preference?**
A: Write concern is how many members must have a write before it's acknowledged. Read concern is how durable the returned data must be — e.g. `majority` means it can never be rolled back. Read preference is which member serves the read — primary, secondary, nearest. Read concern is about rollback safety; read preference is about routing.

**Q: Why would a write that returned success disappear?**
A: It was acknowledged with `w: 1`: the primary applied it and replied, then crashed before any secondary replicated it. A secondary without that write became primary, and when the old primary rejoined, it rolled the write back. `w: "majority"` prevents this, because any electable member already has the write.

**Q: A user updates their profile and immediately sees old data. You read from secondaries. How do you fix it in MongoDB?**
A: Either read that data from the primary, or use a causally consistent session with `w: "majority"` writes and `readConcern: "majority"` reads — the driver passes the write's cluster time, and the secondary waits until it has caught up before answering. Within that session the user always sees their own write.

**Q: What happens when the primary goes down?**
A: Secondaries stop getting heartbeats, and after ~10s one calls an election and needs a majority of voting members. During the election there's no primary, so writes fail for a few seconds; retryable writes in the driver retry once against the new primary. That's why you need an odd number of voters, usually 3.

**Q: What's the default write concern?**
A: `w: "majority"` since MongoDB 5.0 (it was `w: 1` before). Default read concern is `local`, default read preference is `primary`.

**Q: `wtimeout` fired. Did the write fail?**
A: Not necessarily — it only means not enough members confirmed in time. The write may still be on the primary and may still replicate. Treat it as unknown and make the operation idempotent so it can be retried safely.

<a name="cheatsheet"></a>
## 10. Cheat Sheet

- **Write concern** = how many members before "ok". `w:1` fast but rollback-able; `w:"majority"` survives failover (default since 5.0). `j:true` = journaled. `wtimeout` ≠ rolled back.
- **Read concern** = how safe the returned data is. `local` (default) may be rolled back; `majority` never; `linearizable` = majority + most recent, primary only; `snapshot` in transactions.
- **Read preference** = which node. `primary` (default), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest`; `maxStalenessSeconds`, tags.
- Read-your-writes on secondaries = **causal session + majority write + majority read**.
- Elections: heartbeat 2s, timeout 10s, need majority of voters → odd number (3). No writes during election; retryable writes retry once.
- Pick per operation: stronger guarantee = more latency.
