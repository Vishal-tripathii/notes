<a name="multikey"></a>
## 1. Multikey indexes (indexes on arrays)

Index a field that holds an array and MongoDB creates **one index entry per array element** — automatically, no special syntax. The index is then called *multikey*.

```js
// { _id: 1, title: "...", tags: ["db", "mongo", "perf"] }
db.posts.createIndex({ tags: 1 })      // 3 index entries for this one document

db.posts.find({ tags: "mongo" })       // ✅ IXSCAN — "any element equals mongo"
```

Costs and limits:
- **Index size grows with array length.** A document with 1,000 tags = 1,000 index entries, and every `$push` adds entries. Unbounded arrays hurt the index as well as the document ([Part 09](09-embedding-vs-referencing.md)).
- **At most one array field per compound index.** `{ tags: 1, categories: 1 }` where both are arrays fails with *"cannot index parallel arrays"* — the entry count would be the cross-product.
- **Multikey indexes can't cover queries on the array field** — the index doesn't store the full array, so MongoDB must fetch the document.
- Range queries on arrays match if *different* elements satisfy each bound: `{ scores: { $gt: 10, $lt: 20 } }` matches `[5, 25]`. Use `$elemMatch` when one element must satisfy both: `{ scores: { $elemMatch: { $gt: 10, $lt: 20 } } }`.

<a name="sort"></a>
## 2. Using an index for sorting — direction rules

An index can return results already in order, avoiding a blocking in-memory `SORT` stage.

- **Single-field index:** works for either direction. `{ createdAt: 1 }` serves `.sort({ createdAt: -1 })` by walking backwards.
- **Compound index:** works for the index's directions **or their exact inverse**, nothing else.

```js
db.orders.createIndex({ customerId: 1, createdAt: -1 })

.sort({ customerId: 1,  createdAt: -1 })   // ✅ same as index
.sort({ customerId: -1, createdAt: 1 })    // ✅ exact inverse
.sort({ customerId: 1,  createdAt: 1 })    // ❌ mixed — needs in-memory SORT
```

- The sort must follow the index's **prefix** after any equality fields. With an equality match on `customerId`, `.find({ customerId: "a" }).sort({ createdAt: -1 })` uses the index for sorting — this is the "S" in ESR ([Part 06 §3](06-mongodb-indexes.md)).
- A blocking sort over **100MB** spills to disk (default since 6.0) or errors — either way it's a sign the index is wrong.

<a name="explain"></a>
## 3. Reading `explain("executionStats")` properly

```js
db.orders.find({ customerId: "a", status: "paid" }).sort({ createdAt: -1 }).explain("executionStats")
```

The three numbers that matter:

| Field | Meaning |
|---|---|
| `nReturned` | documents returned |
| `totalKeysExamined` | index entries scanned |
| `totalDocsExamined` | documents fetched from storage |

**The ideal ratio is roughly 1 : 1 : 1.** How to read deviations:

| Symptom | Diagnosis |
|---|---|
| `totalDocsExamined` ≫ `nReturned`, stage `COLLSCAN` | no usable index |
| `totalKeysExamined` ≫ `nReturned` | index used but not selective enough, or a range field placed before equality fields — fix the field order |
| `totalDocsExamined` ≫ `nReturned` with `IXSCAN` | index finds candidates, then a `FETCH` filters most out — a filtered field is missing from the index |
| `totalDocsExamined: 0` | covered query ✅ (`PROJECTION_COVERED`) |
| a `SORT` stage present | the sort isn't served by the index — check ESR and directions |

**Stages to recognise:** `COLLSCAN`, `IXSCAN`, `FETCH` (load documents after an index scan), `SORT` (in-memory), `PROJECTION_COVERED`, `SHARDING_FILTER`, `LIMIT`, `SKIP`.

**Plan selection:** when several indexes could serve a query, MongoDB races candidate plans briefly, picks a winner (`winningPlan`, the losers are in `rejectedPlans`) and **caches** it for that query shape. A cached plan that was right for one parameter value can be bad for another — `explain("allPlansExecution")` shows the race, and `hint({ ... })` forces an index when you need to test.

<a name="bad-shapes"></a>
## 4. Query shapes that use indexes badly

| Shape | Problem | Better |
|---|---|---|
| `$regex: /smith/` or `/.*smith/` | no fixed prefix → scans every index key | anchored prefix `/^smith/` (case-sensitive) uses bounds; real search → Atlas Search / text index ([System-design Part 25](../System-design/25-search-and-inverted-index.md)) |
| `$regex: /^smith/i` | case-insensitive regex can't use bounds efficiently | collation index (§5) or store a lowercased copy |
| `$ne`, `$nin`, `$not` | match almost everything → scan most of the index | query the positive set instead (`status: { $in: [...] }`) |
| `$or: [{ a }, { b }]` | each clause needs **its own** index, or the whole query is a COLLSCAN | index both `a` and `b` |
| low-cardinality field alone (`isActive: true`) | 50% of docs match — index barely helps | put it after a selective equality field, or use a partial index ([Part 17](17-advanced-indexing-and-partitioning.md)) |
| `$where`, `$expr` with computed values | evaluated per document | store the computed value as a field and index it |
| big `skip()` | keys still scanned and discarded | cursor pagination ([Part 10](10-pagination.md)) |

<a name="collation"></a>
## 5. Case-insensitive search & collation

```js
db.users.createIndex({ email: 1 }, { collation: { locale: "en", strength: 2 } })   // strength 2 = ignore case

db.users.find({ email: "Alice@X.com" }).collation({ locale: "en", strength: 2 })   // ✅ uses the index
```

The query must specify the **same collation** as the index, or the index isn't used. Many teams simply normalise on write (`email: email.toLowerCase()`) — simpler, and works with a plain unique index.

<a name="intersection"></a>
## 6. Index intersection — why compound usually wins

MongoDB *can* combine two single-field indexes (`AND_SORTED` / `AND_HASH` stages), but the planner rarely chooses it and it's slower than one compound index that matches the query. **Design compound indexes for your main query shapes** instead of one index per field. A compound index `{ a: 1, b: 1 }` also serves queries on `a` alone, so a separate `{ a: 1 }` index is redundant — drop it.

<a name="ops"></a>
## 7. Operating indexes in production

**Building an index on a big live collection:**
- Since 4.2 MongoDB uses an optimized build that takes an exclusive lock only briefly at the start and end; reads and writes continue during the build. It still consumes CPU, I/O and cache — build off-peak.
- On a replica set (4.4+) the build runs on all data-bearing members simultaneously and commits once a quorum finishes (`commitQuorum`). For very large collections teams still do **rolling builds**: one secondary at a time out of the set, then step down the primary and build there.
- A **unique** index build fails if duplicates already exist — find them first with an aggregation (`$group` + `$match: { count: { $gt: 1 } }`).

**Finding indexes to drop:**
```js
db.orders.aggregate([{ $indexStats: {} }])   // per-index usage count since last restart
```
Indexes with `accesses.ops: 0` over a representative period (and across all members) are candidates.

**Dropping safely — hide first (4.4+):**
```js
db.orders.hideIndex("status_1")    // planner ignores it, but it's still maintained
// watch latency for a few days...
db.orders.dropIndex("status_1")    // or unhideIndex() instantly if something got slow
```
Rebuilding a dropped index on a huge collection can take hours; un-hiding takes milliseconds.

**Memory:** indexes are only fast while the parts you use fit in the WiredTiger cache (default ~50% of RAM minus 1GB). `db.collection.stats().indexSizes` shows their size; if total index size outgrows RAM, every query starts hitting disk ([Part 22](22-storage-internals.md)).

**Other index types to recognise by name:** `2dsphere` (geo queries — [System-design Uber problem](../System-design/Problems/problem-10-uber-ride-sharing.md)), `hashed` (hashed shard keys), wildcard `{ "attrs.$**": 1 }` (arbitrary sub-fields — useful for the Attribute pattern, [Part 09.5](09.5-normalization-and-mongodb-schema-patterns.md)), and clustered collections (5.3+, documents stored in `_id` order).

<a name="interview"></a>
## 8. Interview Questions & Answers

**Q: What's a multikey index, and what are its limits?**
A: An index on an array field — MongoDB makes one entry per element, so you can query "any element equals X" with an index. Limits: index size grows with array length, a compound index can include at most one array field ("cannot index parallel arrays"), and it can't cover queries on the array field.

**Q: Index `{ a: 1, b: -1 }`. Which sorts can it serve?**
A: `{ a: 1, b: -1 }` and its exact inverse `{ a: -1, b: 1 }`. Not `{ a: 1, b: 1 }` — mixed directions need an in-memory sort. A single-field index serves either direction.

**Q: How do you read `explain()` output to judge an index?**
A: Compare `nReturned`, `totalKeysExamined` and `totalDocsExamined` — ideally about equal. Many more docs than returned with a COLLSCAN means no index; many more keys than returned means poor selectivity or wrong field order; many more docs examined than returned with an IXSCAN means a filtered field isn't in the index. A `SORT` stage means the sort isn't using the index. Zero docs examined means a covered query.

**Q: Why can an `$or` query do a full collection scan when most of its fields are indexed?**
A: Each `$or` clause is planned separately and needs its own usable index. If even one clause has no index, the whole query falls back to a collection scan.

**Q: Why doesn't `/smith/` use the index well?**
A: The index is sorted from the first character, and an unanchored regex has no prefix to seek to, so it scans every key. `/^smith/` gives a prefix range. Case-insensitive search needs a collation index or a normalised lowercase field.

**Q: How would you safely remove an index you think is unused?**
A: Check `$indexStats` on every member over a representative period, then `hideIndex` it and watch latency — if nothing degrades after a few days, drop it; if something does, `unhideIndex` restores it instantly instead of a multi-hour rebuild.

**Q: How do you add an index to a 200M-document collection in production?**
A: Modern MongoDB builds without blocking reads/writes except briefly at start and end, so it can be done online — off-peak, watching replication lag and cache pressure. For very large collections, do a rolling build one member at a time. For a unique index, check for duplicates first or the build fails.

<a name="cheatsheet"></a>
## 9. Cheat Sheet

- Multikey = one entry per array element; max one array field per compound index; can't cover array queries; use `$elemMatch` for "one element satisfies all conditions."
- Sort via index: same directions or exact inverse; after equality prefix (ESR). In-memory `SORT` > 100MB spills/errors.
- `explain("executionStats")`: `nReturned` : `totalKeysExamined` : `totalDocsExamined` ≈ 1:1:1. Docs ≫ returned → missing field in index; keys ≫ returned → bad order/selectivity; `SORT` stage → sort not indexed.
- Bad shapes: unanchored/case-insensitive regex, `$ne`/`$nin`, `$or` with an unindexed clause, low-cardinality fields alone, big `skip`.
- Case-insensitive: collation index (query must use same collation) or store lowercase.
- Prefer compound indexes over intersection; `{a,b}` makes `{a}` redundant.
- Production: online builds (brief locks), rolling builds for huge collections, `$indexStats` to find unused, `hideIndex` before `dropIndex`, indexes must fit in RAM.
