<a name="reshape"></a>
## 1. `$addFields` / `$set`, `$replaceRoot`, `$count`

```js
{ $set: { total: { $multiply: ["$price", "$qty"] } } }   // add/overwrite fields, keep everything else
                                                         // ($set is an alias of $addFields)
{ $replaceRoot: { newRoot: "$customer" } }               // promote an embedded doc to the top level
{ $count: "n" }                                          // → { n: 1234 }
```

`$project` *includes only* what you list (plus `_id`); `$set`/`$addFields` *adds to* what's already there. Use `$set` when you want to keep the document and add a computed field.

<a name="facet"></a>
## 2. `$facet` — several results from one pass

Runs multiple sub-pipelines on the **same input** and returns them in one document. The classic use: a search page needing results **and** the total count **and** filter counts.

```js
db.products.aggregate([
  { $match: { category: "laptops", price: { $lte: 80000 } } },   // shared, index-backed filter
  { $facet: {
      results:  [{ $sort: { price: 1 } }, { $skip: 0 }, { $limit: 20 }],
      total:    [{ $count: "n" }],
      byBrand:  [{ $group: { _id: "$brand", n: { $sum: 1 } } }, { $sort: { n: -1 } }]
  }}
])
// → { results: [...20], total: [{ n: 312 }], byBrand: [{ _id: "Dell", n: 80 }, ...] }
```

Caveats:
- Sub-pipelines inside `$facet` **can't use indexes** — put the selective `$match` *before* `$facet`.
- The output is **one document**, so it's subject to the **16MB** limit — always `$limit` the result facet.
- Counting every match on each request is expensive at scale; for huge result sets, show "1,000+" or cache the count.

<a name="bucket"></a>
## 3. `$bucket` / `$bucketAuto` — histograms

```js
{ $bucket: {
    groupBy: "$price",
    boundaries: [0, 20000, 50000, 100000],      // [0,20k), [20k,50k), [50k,100k)
    default: "100000+",
    output: { count: { $sum: 1 }, avgRating: { $avg: "$rating" } }
}}
```

`$bucketAuto: { groupBy: "$price", buckets: 5 }` picks boundaries itself so buckets are roughly equal in size. Used for "price range" filters and analytics charts.

<a name="lookup-pipeline"></a>
## 4. `$lookup` with a sub-pipeline

The basic `localField`/`foreignField` form (Part 08) only does an equality join and returns **every** matching document. The pipeline form lets you filter, sort, limit and project the joined side:

```js
// Each customer with only their 3 most recent paid orders, and only two fields of each
db.customers.aggregate([
  { $match: { tier: "gold" } },
  { $lookup: {
      from: "orders",
      localField: "_id",
      foreignField: "customerId",            // equality part — uses an index on orders.customerId
      pipeline: [
        { $match: { status: "paid" } },
        { $sort: { createdAt: -1 } },
        { $limit: 3 },
        { $project: { total: 1, createdAt: 1 } }
      ],
      as: "recentOrders"
  }}
])
```

Combining `localField`/`foreignField` with `pipeline` needs MongoDB 5.0+; on older versions (and for non-equality join conditions) use `let` + `$expr` inside the pipeline (`{ $match: { $expr: { $gte: ["$amount", "$$minAmount"] } } }`).

**Performance rules:**
- `$lookup` runs **once per input document**. Run `$match` / `$limit` first so it runs as few times as possible.
- The `foreignField` **must be indexed**, or every lookup scans the foreign collection — the aggregation version of an N+1 ([Part 07](07-populate-and-n-plus-1.md)).
- The joined array becomes part of the document → 16MB limit. Unbounded joins need `$limit` in the sub-pipeline.
- `$lookup` into a **sharded** collection is supported since 5.1.

<a name="graphlookup"></a>
## 5. `$graphLookup` — recursive lookups

Follows references repeatedly — org charts, category trees, "friends of friends," the MongoDB counterpart of a recursive CTE ([Part 16 §2](16-advanced-sql.md)).

```js
db.employees.aggregate([
  { $match: { name: "Dana" } },
  { $graphLookup: {
      from: "employees",
      startWith: "$managerId",
      connectFromField: "managerId",
      connectToField: "_id",
      as: "chainOfCommand",
      maxDepth: 10,
      depthField: "level"
  }}
])
```

Always set `maxDepth` and index `connectToField`. It's limited to 100MB of memory and can't spill to disk.

<a name="topn"></a>
## 6. Top-N per group: `$topN` and friends

The Part 19 approach (`$sort` → `$group` with `$push` → `$slice`) works but pushes **every** document of the group into an array first — large groups can blow the memory and 16MB limits. Since 5.2 there are accumulators that keep only N:

```js
db.orders.aggregate([
  { $group: {
      _id: "$customerId",
      top3: { $topN: { n: 3, sortBy: { amount: -1 }, output: { orderId: "$_id", amount: "$amount" } } },
      latest: { $top: { sortBy: { createdAt: -1 }, output: "$$ROOT" } }
  }}
])
```

Also `$bottomN`, `$firstN`, `$lastN`, `$maxN`, `$minN`. On older versions, `$sort` + `$group` with `$first` for top-1 is still fine.

<a name="window"></a>
## 7. `$setWindowFields` — window functions (5.0+)

MongoDB's version of SQL `OVER (PARTITION BY ... ORDER BY ...)` ([Part 16 §1](16-advanced-sql.md)): every document stays, and gains a value computed over its partition.

```js
db.sales.aggregate([
  { $setWindowFields: {
      partitionBy: "$storeId",
      sortBy: { day: 1 },
      output: {
        runningTotal: { $sum: "$amount", window: { documents: ["unbounded", "current"] } },
        movingAvg7d:  { $avg: "$amount", window: { range: [-6, 0], unit: "day" } },
        rank:         { $rank: {} }
      }
  }}
])
```

Running totals, moving averages, rank within a group, previous/next values (`$shift`) — all without collapsing documents the way `$group` does.

<a name="merge"></a>
## 8. `$merge` / `$out` — materializing results

Write the pipeline's output to a collection — MongoDB's way of building a **materialized view** ([Part 24](24-views-triggers-stored-procedures.md)):

```js
// nightly: recompute daily revenue per store, upserting into a summary collection
db.orders.aggregate([
  { $match: { createdAt: { $gte: yesterday, $lt: today } } },
  { $group: { _id: { store: "$storeId", day: yesterday }, revenue: { $sum: "$total" } } },
  { $merge: { into: "dailyRevenue", on: "_id", whenMatched: "replace", whenNotMatched: "insert" } }
])
```

| | `$out` | `$merge` |
|---|---|---|
| Target | **replaces** the whole collection | inserts / merges / replaces per document |
| Incremental updates | no | yes — recompute only the changed day |
| Must be | the last stage | the last stage |

Dashboards then read the small summary collection instead of aggregating millions of orders per request — the Computed pattern ([Part 09.5](09.5-normalization-and-mongodb-schema-patterns.md)) done in batch.

<a name="limits"></a>
## 9. Limits that break pipelines in production

| Limit | What happens | Fix |
|---|---|---|
| **100MB memory per stage** (`$group`, `$sort`, `$bucket`...) | exceeds → error, unless the stage can spill to disk | `allowDiskUse: true` (default since 6.0 via `allowDiskUseByDefault`); better: `$match` earlier, index-backed `$sort` |
| **16MB per output document** | `$push` of a huge group, `$facet` output, unbounded `$lookup` arrays → error | `$limit` inside, `$topN`, don't build giant arrays |
| `$graphLookup` 100MB | can't spill | `maxDepth`, `restrictSearchWithMatch` |
| Only the **start** of the pipeline can use indexes | a `$match`/`$sort` after `$group`/`$project`/`$unwind` can't | keep raw-field `$match` and `$sort` first ([Part 08 §4](08-aggregation-pipeline.md)) |
| Long-running pipelines hog the primary | latency for normal traffic | run reports on a secondary (`readPreference: "secondary"`, [Part 05.5](05.5-mongodb-write-concern-read-concern-read-preference.md)), or materialize with `$merge` |
| No timeout by default | a bad pipeline runs for minutes | `maxTimeMS` on every user-triggered aggregation |

A `$sort` immediately followed by `$limit` is optimised into a **top-k sort** that only keeps k documents in memory — so `$sort` + `$limit: 20` on an unindexed field is far cheaper than `$sort` alone.

<a name="interview"></a>
## 10. Interview Questions & Answers

**Q: How would you return a page of results and the total count in one query?**
A: `$match` first (index-backed), then `$facet` with one sub-pipeline doing `$sort`/`$skip`/`$limit` and another doing `$count`. The sub-pipelines can't use indexes and the result must fit in 16MB, so the selective `$match` must come before `$facet`.

**Q: `$lookup` with `localField/foreignField` vs with a `pipeline`?**
A: The basic form is an equality join returning every match. The pipeline form lets you filter, sort, limit and project the joined documents — e.g. "only the 3 most recent paid orders." Either way, index the foreign field and reduce input documents first, since `$lookup` runs once per input document.

**Q: Top 3 orders per customer — how, and what's the memory concern?**
A: `$group` with `$topN: { n: 3, sortBy: { amount: -1 } }` (5.2+). The older `$sort` → `$group` + `$push` → `$slice` approach pushes every order into an array first, which can exceed 100MB per stage or 16MB per document for big customers.

**Q: Running total per store in MongoDB?**
A: `$setWindowFields` with `partitionBy: "$storeId"`, `sortBy: { day: 1 }`, and `$sum` over a window of `["unbounded", "current"]` — MongoDB's equivalent of a SQL window function.

**Q: The dashboard aggregation takes 8 seconds. What do you do?**
A: Check `explain()` that the first `$match` uses an index and that `$sort` is index-backed or followed by `$limit`. If it's still slow because it has to scan millions of documents, precompute: a scheduled `$merge` into a summary collection (or `$inc` counters on write), run heavy reports on a secondary, and set `maxTimeMS`.

**Q: What limits make aggregations fail?**
A: 100MB memory per blocking stage (spills to disk with `allowDiskUse`, default since 6.0), the 16MB output document limit (huge `$push`, `$facet`, unbounded `$lookup`), and `$graphLookup`'s 100MB limit that can't spill.

<a name="cheatsheet"></a>
## 11. Cheat Sheet

- `$set`/`$addFields` add fields; `$project` keeps only listed fields; `$replaceRoot` promotes a sub-document.
- `$facet` = many sub-pipelines on one input (results + count + filters). No indexes inside; 16MB output.
- `$bucket`/`$bucketAuto` = histograms.
- `$lookup` pipeline form = filter/sort/limit/project the joined side. Index `foreignField`; `$match` first.
- `$graphLookup` = recursive (org chart); set `maxDepth`.
- Top-N per group: `$topN`/`$top` (5.2+), not giant `$push` arrays.
- `$setWindowFields` = window functions (running total, moving avg, rank).
- `$merge` (incremental) / `$out` (replace) = materialized summaries.
- Limits: 100MB/stage (`allowDiskUse`), 16MB/document, only leading stages use indexes, add `maxTimeMS`. `$sort` + `$limit` = cheap top-k.
