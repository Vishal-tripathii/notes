<a name="anomalies"></a>
## 1. Why normalize — the three anomalies

One wide table that stores everything together:

| order_id | customer_id | customer_name | customer_city | product_id | product_name | unit_price | qty |
|---|---|---|---|---|---|---|---|
| 1 | 10 | Asha | Pune | P1 | Keyboard | 1500 | 1 |
| 1 | 10 | Asha | Pune | P2 | Mouse | 700 | 2 |
| 2 | 10 | Asha | Pune | P1 | Keyboard | 1500 | 1 |

- **Update anomaly:** Asha moves to Mumbai → you must update every row she appears in; miss one and the data contradicts itself.
- **Insert anomaly:** you can't record a new product until someone orders it (there's no row for it to live in).
- **Delete anomaly:** delete order 2 and the last order of some product, and you lose the fact that the product exists and what it costs.

Normalization removes these by making **each fact live in exactly one place**.

<a name="normal-forms"></a>
## 2. 1NF, 2NF, 3NF on one worked example

**1NF — atomic values, no repeating groups.** Each column holds one value; no `products = "P1,P2"` strings, no `phone1, phone2, phone3` columns. The table above is already 1NF (one row per order line), with key `(order_id, product_id)`.

**2NF — 1NF + no partial dependency.** Every non-key column must depend on the **whole** key, not part of it. Here:
- `product_name`, `unit_price` depend only on `product_id` (part of the key) ✗
- `customer_id`, `customer_name`, `customer_city` depend only on `order_id` ✗
- only `qty` depends on the whole `(order_id, product_id)` ✓

Split:
```
orders(order_id PK, customer_id, customer_name, customer_city)
products(product_id PK, product_name, unit_price)
order_items(order_id, product_id, qty, PK(order_id, product_id))
```

**3NF — 2NF + no transitive dependency.** Non-key columns must depend on the key **directly**, not via another non-key column. In `orders`, `customer_name` and `customer_city` depend on `customer_id`, which depends on `order_id` — transitive ✗. Split again:
```
customers(customer_id PK, name, city)
orders(order_id PK, customer_id FK → customers)
products(product_id PK, name, unit_price)
order_items(order_id FK, product_id FK, qty, PK(order_id, product_id))
```

The one-line memory aid: **every non-key column depends on the key, the whole key, and nothing but the key.**

**⚠️ The trap in this example:** `unit_price` in `products` is the *current* price. An order must record the price **at the time of purchase**, so `order_items` should also carry `unit_price`. That's not a normalization violation — it's a different fact ("price paid on this order") that happens to have the same value today. Interviewers like this one.

<a name="bcnf"></a>
## 3. BCNF, briefly

**Boyce–Codd Normal Form:** for every functional dependency `X → Y`, `X` must be a candidate key. It's a stricter 3NF that only differs in unusual tables with overlapping candidate keys (e.g. `(student, course, instructor)` where each instructor teaches one course). Knowing the definition is enough; 3NF is the practical target for application schemas. 4NF/5NF exist and almost never come up.

<a name="denormalize"></a>
## 4. Denormalization — when and how to do it deliberately

Normalization optimises for **write correctness**. Denormalization trades some of that back for **read speed**. Do it deliberately, for a measured reason:

| Denormalization | Why | Cost |
|---|---|---|
| Stored counter (`posts.comment_count`) | avoid `COUNT(*)` on every page view | must update on every comment insert/delete |
| Copied field (`orders.customer_name`) | avoid a join on a hot list page | stale if the source changes — or intentionally a snapshot |
| Precomputed totals (`orders.total`) | avoid summing items on read | must recompute on item change |
| Reporting tables / materialized views ([Part 24](24-views-triggers-stored-procedures.md)) | heavy analytics off the hot path | refresh lag |

The rule of thumb to say in an interview: **normalize the source of truth, denormalize read models** — and for each duplicated field, decide whether it must stay in sync (then you need a mechanism, §6) or is a point-in-time snapshot (then it must *never* be synced).

<a name="patterns"></a>
## 5. MongoDB schema patterns

MongoDB modeling starts from **access patterns**, not entities — "what queries run, how often, with what latency" decides the shape. These named patterns come from MongoDB's own guidance; knowing them by name signals real experience.

### Extended Reference
Reference another document **and** copy the few fields you always display with it.
```js
// order: reference the customer, but copy what the order list page shows
{ _id, customerId, customer: { name: "Asha", city: "Pune" }, items: [...], total }
```
Avoids a `$lookup`/`populate()` on every order list. The copied fields should be ones that rarely change — or, like a shipping address, ones that *should* be frozen at order time.

### Subset
Embed only the **most-used part** of a large related set; keep the full set in its own collection.
```js
// product page shows the 10 newest reviews; "see all" queries the reviews collection
{ _id, name, price, recentReviews: [ /* 10 newest */ ], reviewCount: 4812 }
```
Maintain with `$push: { recentReviews: { $each: [r], $sort: { at: -1 }, $slice: 10 } }` ([Part 05.6 §4](05.6-mongodb-atomic-writes-upsert-bulk.md)).

### Bucket
Group many small records into one document per time window or per fixed count.
```js
// IoT readings: one document per sensor per hour instead of one per reading
{ sensorId, hour: ISODate("2026-11-23T10:00Z"), count: 360, readings: [{ t, v }, ...], sum: 8123.4 }
```
Fewer documents, smaller indexes, pre-aggregated `sum`/`count`. Also how chat messages can be stored in pages of ~100. For time-series data, MongoDB **time-series collections** (5.0+) apply bucketing automatically — prefer them over hand-rolled buckets.

### Computed
Calculate on write what's expensive to calculate on every read: counters (`$inc: { likeCount: 1 }`), totals, averages (`sum` + `count`, so `avg = sum / count`). Batch variant: scheduled `$merge` into summary collections ([Part 08.5 §8](08.5-aggregation-advanced.md)).

### Outlier
Design for the common case and handle the rare huge one separately.
```js
// 99.9% of books have < 1000 buyers → embed. A bestseller overflows into extra docs.
{ _id: "book1", buyers: [ ...1000 ids ], hasOverflow: true }
{ bookId: "book1", page: 2, buyers: [ ...1000 more ] }
```
The app checks `hasOverflow` and fetches the extra documents only for outliers. Avoids designing everything around the celebrity case (the same problem as Twitter fan-out, [System-design Problem 04](../System-design/Problems/problem-04-twitter-news-feed.md)).

### Attribute
Many sparse, varying fields (product specs differ per category) → store them as an array of key/value pairs so **one** index covers them all.
```js
{ name: "Laptop X", attrs: [ { k: "ram_gb", v: 16 }, { k: "cpu", v: "M3" }, { k: "weight_kg", v: 1.3 } ] }
db.products.createIndex({ "attrs.k": 1, "attrs.v": 1 })
db.products.find({ attrs: { $elemMatch: { k: "ram_gb", v: { $gte: 16 } } } })
```
Alternative: a wildcard index on an `attrs` sub-document ([Part 06.5 §7](06.5-mongodb-indexing-deep-dive.md)).

### Polymorphic
Different shapes in one collection, distinguished by a type field — e.g. `payments` with `card`, `upi` and `wallet` variants sharing `amount`, `status`, `userId`. Queries across all types stay simple. In Mongoose: **discriminators**.

### Schema Versioning
Add `schemaVersion: 2` to documents; application code handles both shapes, and documents are migrated lazily on write or by a background job — no big-bang migration ([Part 21](21-schema-validation-and-migrations.md)).

### Archive
Move old, rarely-read data (orders older than 2 years) to a separate collection or cheaper storage so the hot collection and its indexes stay small enough for RAM. TTL indexes ([Part 06](06-mongodb-indexes.md)) or partition-like collections per year help.

<a name="consistency"></a>
## 6. Keeping duplicated data consistent

Every pattern above duplicates something. For each copy, decide:

1. **Is it a snapshot?** (price paid, shipping address on an order, author name on a published invoice) → never update it. Copying it is the *correct* model.
2. **Must it follow the source?** (a user's display name copied into their posts) → choose a sync mechanism:
   - **Same request:** update source and copies together, in a transaction if they must be atomic ([Part 15](15-mongodb-transactions-and-concurrency.md)). Fine when copies are few.
   - **Background:** `updateMany({ "author.id": uid }, { $set: { "author.name": newName } })` triggered by a **change stream** or a queue event ([System-design Part 14](../System-design/14-event-driven-architecture.md)). Eventually consistent; good when copies are many.
   - **Accept staleness:** with a TTL'd cache or periodic rebuild, if the business allows.
3. **How often does the source change vs how often is the copy read?** Copy fields that are read constantly and change rarely. A field that changes every minute and is copied into 10,000 documents is a bad candidate.

<a name="likes"></a>
## 7. Worked example: a post with 50,000 likes

**Wrong:** `post.likes: [userId, ...]` — unbounded array → document growth toward 16MB, every like rewrites a growing document, a multikey index with 50k entries for one post.

**Right — combine three patterns:**
```js
// likes: one small document per like (reference)
{ _id, postId, userId, at }
db.likes.createIndex({ postId: 1, userId: 1 }, { unique: true })   // can't like twice; "did I like this?" is an index lookup

// post: computed counter + optional subset
{ _id, text, likeCount: 50213, recentLikers: [ /* 3 names for "Asha, Ravi and 50,210 others" */ ] }
```

Like flow: `insertOne` into `likes` (a duplicate-key error means already liked → no-op) → `$inc: { likeCount: 1 }` on the post. If the two must never disagree, do both in a transaction; most apps accept the rare drift and run a periodic recount. For a viral post, `likeCount` on one document becomes a **hot document** — buffer increments (e.g. in Redis, flushed every few seconds) or shard the counter across N documents and sum them.

<a name="interview"></a>
## 8. Interview Questions & Answers

**Q: What problems does normalization solve?**
A: Update, insert and delete anomalies — the same fact stored in many rows can contradict itself, you can't store a fact without an unrelated one, and deleting one fact deletes another. Normalization puts each fact in one place.

**Q: Explain 1NF, 2NF and 3NF.**
A: 1NF: atomic values, no repeating groups. 2NF: no column depends on only part of a composite key. 3NF: no column depends on another non-key column (no transitive dependency). In short: every non-key column depends on the key, the whole key, and nothing but the key.

**Q: When would you denormalize?**
A: When a measured read path is too slow or too expensive with joins — counters instead of `COUNT(*)`, copied display fields on hot list pages, precomputed totals, reporting tables. Normalize the source of truth, denormalize read models, and for each copy decide whether it's a snapshot or needs a sync mechanism.

**Q: Should `order_items` store the product price if `products` already has it?**
A: Yes. `products.price` is the current price; the order needs the price actually paid. It's a different fact — a snapshot — so it's not duplication in the normalization sense, and it must never be synced.

**Q: Name some MongoDB schema design patterns and when you'd use them.**
A: Extended reference (copy frequently displayed fields of a referenced doc, avoid `$lookup`), Subset (embed the 10 newest reviews, keep the rest separate), Bucket (group time-series readings per hour), Computed (maintain counters/totals on write), Outlier (overflow documents for the rare huge case), Attribute (key/value array for sparse varying fields), Polymorphic (several shapes in one collection), Schema Versioning (migrate lazily).

**Q: How would you model likes on posts that can go viral?**
A: Not as an array on the post. A separate `likes` collection with a unique index on `(postId, userId)`, plus a `likeCount` maintained with `$inc`, optionally a small subset of recent likers embedded. For a viral post, the counter is a hot document — buffer increments or split the counter.

**Q: You copied the user's name into 10,000 of their posts. They change their name. Now what?**
A: Decide if it's a snapshot (leave it) or must follow the source. If it must follow, update copies in the background — a change stream or queue event running `updateMany` — and accept brief inconsistency. If it changes often and is copied widely, it shouldn't have been copied; look it up instead.

<a name="cheatsheet"></a>
## 9. Cheat Sheet

- Anomalies: update, insert, delete. Normalization = each fact in one place.
- 1NF atomic · 2NF whole key · 3NF nothing but the key. BCNF = every determinant is a candidate key. Target 3NF.
- Price-at-purchase on `order_items` = snapshot, not duplication.
- Denormalize read models for measured reasons; each copy is either a **snapshot** or needs a **sync mechanism**.
- Mongo patterns: **Extended reference**, **Subset**, **Bucket** (or time-series collections), **Computed**, **Outlier**, **Attribute**, **Polymorphic**, **Schema versioning**, **Archive**.
- Sync copies: same transaction (few copies) or change stream / queue + `updateMany` (many copies).
- Likes: separate collection + unique `(postId, userId)` + `$inc` counter; hot counter → buffer or split.
