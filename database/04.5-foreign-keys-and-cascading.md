## 1. What a foreign key actually enforces

A **foreign key** is a constraint that says: the value in this column must exist as a primary key (or unique key) value in another table. It's the database-level mechanism for **referential integrity** — guaranteeing that a relationship a row claims to have actually points at something real.

```sql
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT,
  FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```

Without this constraint, nothing stops an `orders` row from having `customer_id = 9999` when no such customer exists — an **orphaned reference**, silently wrong, discoverable only when something later tries to join and gets nothing back. The foreign key makes that insert/update fail immediately at write time instead of producing silent bad data.

<a name="cascade-options"></a>
## 2. The cascading options

`ON DELETE` / `ON UPDATE` define what happens to the *child* row when the *parent* row it references is deleted or its key is updated:

| Option | Behavior |
|---|---|
| `CASCADE` | delete (or update) the child rows automatically along with the parent |
| `SET NULL` | set the child's foreign key column to `NULL` instead of deleting the child |
| `RESTRICT` (or default in most DBs) | **block** the parent delete/update entirely if child rows still reference it |
| `NO ACTION` | similar to `RESTRICT` — check happens at the end of the statement, not immediately (subtle timing difference, rarely matters in practice) |

```sql
FOREIGN KEY (customer_id) REFERENCES customers(id)
  ON DELETE CASCADE   -- deleting a customer deletes all their orders too
  ON UPDATE CASCADE   -- if customer.id ever changes, orders.customer_id updates to match
```

<a name="worked"></a>
## 3. `ON DELETE CASCADE` — the worked example

```sql
DELETE FROM customers WHERE id = 42;
-- with ON DELETE CASCADE: every row in `orders` (and any other table referencing
-- customer 42, transitively) is automatically deleted too, in the same statement.
```

This is genuinely useful for **true parent-owns-child, nothing-makes-sense-without-the-parent** relationships — e.g. deleting a `blog_post` should reasonably delete its `comments`, since a comment orphaned from its post is meaningless data taking up space with no valid reference.

<a name="danger"></a>
## 4. Why cascading is dangerous, and when to avoid it

**The core risk: a single `DELETE` can silently ripple through many tables, deleting far more than the person running it realizes** — especially once cascades chain (A cascades into B, which itself cascades into C). There's no confirmation step, no dry-run by default; the deletion just happens, in full, as part of the original statement.

**When to avoid `CASCADE` in favor of `RESTRICT`:**
- **Financial/audit data** — deleting a customer should probably *not* silently delete their historical order records; those often need to be retained for compliance regardless of whether the customer account still exists. `RESTRICT` (or `SET NULL` combined with a soft-delete pattern) is usually the safer default here.
- **Any relationship where the child data has value independent of the parent** — deleting a `product` shouldn't necessarily cascade-delete every historical `order_item` referencing it; the order history is valid data on its own.

**A common safer pattern in practice:** soft deletes (an `is_deleted`/`deleted_at` column instead of an actual `DELETE`) sidestep the cascading-delete danger entirely, at the cost of every query needing to filter out soft-deleted rows.

<a name="mongo"></a>
## 5. MongoDB has no equivalent — what replaces it

MongoDB has **no foreign key constraint mechanism at all** — referencing another document's `_id` (Part 05, Part 09) is purely a convention enforced by application code, not the database. Nothing stops you from inserting an order with a `customerId` that doesn't exist; nothing automatically deletes or nulls out child documents when a parent is deleted.

**What replaces cascading in Mongo:**
- **Application-level cascade logic** — explicitly deleting related documents in the application (or via a multi-document transaction, Part 15, for atomicity) when a parent is deleted.
- **Leaning on embedding (Part 09) specifically to sidestep this problem** — if child data is embedded in the parent document, "deleting the parent" *is* deleting the children, with no separate cascade step needed at all, because there's only one document.
- **Change streams / triggers** (Atlas Triggers or a self-managed change-stream listener) to react to a parent deletion and clean up references elsewhere, for referenced (not embedded) relationships.

This is a genuine, honest trade-off of choosing MongoDB's document model over a relational one — referential integrity becomes the application's responsibility, not something the database guarantees for you.

<a name="interview"></a>
## 6. Interview Questions & Answers

**Q: What does a foreign key actually enforce, and what happens without one?**
A: It guarantees a column's value must exist as a key in the referenced table — enforced at write time. Without it, nothing stops an orphaned reference (a row pointing at a parent that doesn't exist), which stays silently wrong until something tries to join against it and gets nothing.

**Q: `CASCADE` vs `RESTRICT` — when would you choose each?**
A: `CASCADE` for true parent-owns-child relationships where child data is meaningless without the parent (comments on a deleted post). `RESTRICT` (or `SET NULL` + soft deletes) for relationships where the child data has independent value that should survive the parent's deletion — order history when a customer account is deleted, for compliance/audit reasons.

**Q: Why is `ON DELETE CASCADE` risky in production?**
A: A single delete can silently ripple through many related tables, especially once cascades chain across multiple relationships — deleting far more data than intended, in one statement, with no confirmation step.

**Q: How does MongoDB handle what a foreign key + cascade would handle in SQL?**
A: It doesn't, at the database level — there's no FK constraint at all, so referential integrity is entirely the application's responsibility. Embedding related data (Part 09) sidesteps the problem for owned relationships, since deleting the parent document deletes the "children" with it automatically. For referenced relationships, cascading has to be done explicitly in application code, a transaction, or via change streams.

---

<a name="cheatsheet"></a>
## 7. Cheat Sheet

- Foreign key = enforced-at-write-time guarantee that a referenced value actually exists — prevents orphaned references.
- `ON DELETE CASCADE`/`UPDATE CASCADE` = child rows automatically follow the parent. `SET NULL` = child's FK column nulled instead. `RESTRICT`/`NO ACTION` = blocks the parent delete/update if children still reference it.
- Prefer `CASCADE` only for true parent-owns-child data; prefer `RESTRICT`/soft-deletes for data with independent value (audit/financial records).
- Risk: cascades can chain and delete far more than intended in one statement, with no confirmation.
- MongoDB has **no FK/cascade mechanism at all** — embedding (Part 09) sidesteps the need for owned data; referenced data needs explicit app-level cleanup, a transaction, or change streams.
