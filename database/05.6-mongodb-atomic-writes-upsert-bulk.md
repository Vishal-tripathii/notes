<a name="upsert"></a>
## 1. Upsert — and its race condition

"Update the matching document, or insert one if none matches" — in one call:

```js
await db.dailyStats.updateOne(
  { userId, day: "2026-11-23" },                     // filter
  {
    $inc: { pageViews: 1 },                          // applied on update AND insert
    $setOnInsert: { createdAt: new Date() }          // only applied when inserting
  },
  { upsert: true }
);
```

On insert, the new document gets the **equality fields from the filter** (`userId`, `day`) plus the update's effects. `$setOnInsert` is for fields that should be set once and never overwritten.

**The race:** two concurrent upserts with the same filter can **both** find nothing and **both** insert — you now have two `dailyStats` documents for the same user/day. The only real fix is a **unique index on the filter fields**:

```js
db.dailyStats.createIndex({ userId: 1, day: 1 }, { unique: true })
```

Now the second insert fails with `E11000 duplicate key`. Since MongoDB 4.2 the server **retries that upsert internally** as an update when the filter is an equality match on the unique index's fields; otherwise, catch `E11000` in the app and retry once (the retry will take the update path). Without the unique index, upsert is not "create if not exists" under concurrency — it's "probably."

<a name="foau"></a>
## 2. `findOneAndUpdate` — update and get the document back, atomically

`updateOne` returns counts (`matchedCount`, `modifiedCount`). `findOneAndUpdate` returns **the document itself**, from the same atomic operation — no separate `find` that could see someone else's change.

```js
// Claim the next pending job — exactly one worker gets each job
const job = await db.jobs.findOneAndUpdate(
  { status: "pending" },
  { $set: { status: "processing", worker: "w3", startedAt: new Date() } },
  { sort: { createdAt: 1 }, returnDocument: "after" }   // Mongoose: { new: true }
);
if (!job) { /* queue empty */ }
```

Classic uses:
- **Job claiming** (above) — MongoDB's version of `FOR UPDATE SKIP LOCKED` ([Part 04.6 §7](04.6-locking-deadlocks-and-anomalies.md)).
- **Sequence / counter generation:** `findOneAndUpdate({ _id: "invoice" }, { $inc: { seq: 1 } }, { upsert: true, returnDocument: "after" })` → a gap-free-ish invoice number.
- **"Decrement and tell me what's left":** `findOneAndUpdate({ _id, stock: { $gte: qty } }, { $inc: { stock: -qty } }, { returnDocument: "after" })`.

⚠️ Gotchas:
- **Default returns the document *before* the update.** Driver: `returnDocument: "after"`; Mongoose: `{ new: true }`. Forgetting this is a very common bug.
- **Mongoose doesn't run schema validators on update queries** unless you pass `runValidators: true` ([Part 21](21-schema-validation-and-migrations.md)).
- `findOneAndReplace` / `findOneAndDelete` follow the same pattern.

<a name="operators"></a>
## 3. Update operators worth knowing

| Operator | Does | Typical use |
|---|---|---|
| `$set` / `$unset` | set / remove fields | normal partial updates |
| `$inc` | add to a number atomically | counters, stock, balances |
| `$min` / `$max` | set only if the new value is smaller / larger | "lowest price seen," "last activity time" without a read |
| `$mul` | multiply | price adjustments |
| `$rename` | rename a field | migrations |
| `$setOnInsert` | set only when an upsert inserts | `createdAt` |
| `$currentDate` | set to the server's current date | `updatedAt` (server clock, not app clock) |

**Pipeline updates (4.2+):** the update can be an aggregation pipeline, so a field can be computed from other fields **in the same atomic operation**:

```js
db.orders.updateOne({ _id }, [
  { $set: { total: { $multiply: ["$price", "$qty"] }, updatedAt: "$$NOW" } }
]);
```

<a name="arrays"></a>
## 4. Updating inside arrays

```js
// add / remove
{ $push: { tags: "vip" } }                       // append (allows duplicates)
{ $addToSet: { tags: "vip" } }                   // append only if absent — set semantics
{ $pull: { tags: "trial" } }                     // remove all matching elements

// capped array: keep only the 50 most recent items (the Subset pattern, Part 09.5)
{ $push: { recentViews: { $each: [view], $sort: { at: -1 }, $slice: 50 } } }

// update THE matched element — positional $
db.orders.updateOne(
  { _id, "items.productId": pid },
  { $set: { "items.$.qty": 3 } }                 // $ = first element matched by the filter
)

// update ALL elements
{ $inc: { "items.$[].qty": 1 } }

// update elements matching a condition — arrayFilters
db.orders.updateOne(
  { _id },
  { $set: { "items.$[it].status": "shipped" } },
  { arrayFilters: [{ "it.warehouse": "BLR" }] }
)
```

All of these are atomic within the document — no read-modify-write of the whole array in application code, which would reintroduce the lost-update race ([Part 04.6 §3](04.6-locking-deadlocks-and-anomalies.md)).

<a name="bulk"></a>
## 5. `bulkWrite` — ordered vs unordered

Send many writes in one round trip instead of N:

```js
await db.products.bulkWrite([
  { updateOne: { filter: { sku: "A1" }, update: { $inc: { stock: -2 } } } },
  { updateOne: { filter: { sku: "B7" }, update: { $set: { price: 499 } }, upsert: true } },
  { deleteOne: { filter: { sku: "OLD" } } }
], { ordered: false });
```

| | `ordered: true` *(default)* | `ordered: false` |
|---|---|---|
| Execution | in sequence | the server may run them in any order / in parallel |
| On an error | **stops** at the first failure; later ops never run | continues; reports every failure at the end |
| Use when | later ops depend on earlier ones | ops are independent — faster, e.g. importing data |

**`bulkWrite` is not a transaction.** If op 3 of 10 fails, ops 1–2 (ordered) or all the others (unordered) are already applied. For all-or-nothing, wrap it in a transaction ([Part 15](15-mongodb-transactions-and-concurrency.md)). The driver splits very large batches automatically (the server limit is 100,000 ops per batch); still, for huge imports, send chunks of ~1,000 so a failure is easy to resume from.

`insertMany` behaves the same way: `ordered: false` + a unique index is the standard "import and skip duplicates" approach.

<a name="retryable"></a>
## 6. Retryable writes & idempotency

With `retryWrites=true` (default in modern drivers), if a single write hits a network error or a failover, the driver retries it **once**, and the server uses a transaction number to make sure it's applied **at most once** — so even `$inc` doesn't double-apply.

That protects you from **driver-level** retries only. A user double-clicking "Pay," or your own HTTP client retrying a request, are new writes as far as the database knows. For those you still need an **idempotency key + unique index** ([Part 18](18-production-scenario-practice.md)), or operations that are naturally idempotent (`$set` to a value, `$addToSet`).

<a name="sql"></a>
## 7. SQL equivalents

| MongoDB | Postgres | MySQL |
|---|---|---|
| `updateOne(..., { upsert: true })` | `INSERT ... ON CONFLICT (key) DO UPDATE SET ...` | `INSERT ... ON DUPLICATE KEY UPDATE ...` |
| insert-or-ignore | `INSERT ... ON CONFLICT DO NOTHING` | `INSERT IGNORE` |
| `findOneAndUpdate(..., returnDocument: "after")` | `UPDATE ... RETURNING *` | no `RETURNING` — use a transaction + `SELECT` |
| `$inc` | `SET x = x + 1` | same |
| `bulkWrite` | multi-row `INSERT`, `COPY`, or batched statements | multi-row `INSERT`, `LOAD DATA` |

Note the SQL upserts need a **unique constraint** to conflict on — the same requirement as Mongo's race fix, just enforced by the syntax.

<a name="interview"></a>
## 8. Interview Questions & Answers

**Q: What's an upsert, and is it safe under concurrency?**
A: Update the matching document or insert one if none matches, in one call — `updateOne(filter, update, { upsert: true })`, with `$setOnInsert` for insert-only fields. It's only safe with a unique index on the filter fields; without it, two concurrent upserts can both insert. With the index, the second hits a duplicate-key error, which the server (4.2+) or the app retries as an update.

**Q: `updateOne` vs `findOneAndUpdate`?**
A: `updateOne` returns match/modify counts; `findOneAndUpdate` returns the document from the same atomic operation, before or after the change (`returnDocument: "after"` / Mongoose `new: true`). Use it when you need the result — claiming a job, generating a sequence number, getting the remaining stock.

**Q: How would you have multiple workers pull jobs from a MongoDB collection without two taking the same job?**
A: `findOneAndUpdate({ status: "pending" }, { $set: { status: "processing", worker } }, { sort: { createdAt: 1 } })`. The match and the status change are one atomic operation, so only one worker can flip each job. Add a `startedAt` and a sweeper that resets jobs stuck in processing too long.

**Q: How do you update one element inside an array?**
A: Positional `$` for the first element matched by the filter (`"items.$.qty"`), `$[]` for all elements, `arrayFilters` with `$[name]` for elements matching a condition. `$addToSet` / `$pull` to add/remove. All atomic within the document — never read the array, modify it in code, and write it back.

**Q: Ordered vs unordered `bulkWrite`?**
A: Ordered runs in sequence and stops at the first error; unordered may run in parallel and continues past errors, reporting them all. Neither is a transaction — earlier successes stay applied.

**Q: Retryable writes are on. Do I still need idempotency keys?**
A: Yes. Retryable writes only dedupe the driver's own automatic retry of one operation. A user double-submit or an upstream HTTP retry is a new request — you need an idempotency key with a unique index for that.

<a name="cheatsheet"></a>
## 9. Cheat Sheet

- Upsert = `upsert: true` + `$setOnInsert`; **needs a unique index** on the filter fields to be race-free.
- `findOneAndUpdate` = atomic update + return the document. Default returns **before** → `returnDocument: "after"` / `{ new: true }`.
- Job claim = `findOneAndUpdate({status:"pending"}, {$set:{status:"processing"}}, {sort})`.
- Operators: `$inc`, `$min`/`$max`, `$setOnInsert`, `$currentDate`, pipeline updates for computed fields.
- Arrays: `$push` (+ `$each/$sort/$slice` to cap), `$addToSet`, `$pull`, `$`, `$[]`, `arrayFilters`.
- `bulkWrite`: ordered stops at first error; unordered continues. **Not a transaction.**
- Retryable writes ≠ idempotency for user/HTTP retries.
- SQL: `ON CONFLICT DO UPDATE` / `ON DUPLICATE KEY UPDATE`, `UPDATE ... RETURNING`.
