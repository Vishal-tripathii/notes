<a name="stackheap"></a>
# 1. Stack vs Heap

```
┌──────────────── STACK ────────────────┐  ┌────────── HEAP ──────────┐
│  function frames, LIFO                │  │  objects, arrays,        │
│  primitives (number, boolean)         │  │  functions, closures,    │
│  REFERENCES to heap objects           │  │  strings                 │
│                                       │  │                          │
│  ~1MB · freed automatically on return │  │  ~2-4GB · garbage        │
│  overflow = instant crash             │  │  collected               │
└───────────────────────────────────────┘  └──────────────────────────┘
```

```js
function demo() {
  let count = 42;                 // the VALUE 42 → stack
  let user = { name: 'Ada' };     // the OBJECT → heap
                                  // the REFERENCE to it → stack
}                                 // ← frame popped: count gone instantly,
                                  //   {name:'Ada'} becomes GC-eligible
```

> **This settles "pass by value vs reference":** JavaScript always copies what's on the **stack**. For a primitive that's the value; for an object that's the *reference* — so both variables point at the same heap object.

## Two different crashes — constantly confused

```js
function boom() { return boom(); }
// RangeError: Maximum call stack size exceeded   ← STACK · recursion · CATCHABLE

const arr = []; while (true) arr.push(new Array(1e6));
// FATAL ERROR: JavaScript heap out of memory     ← HEAP · data volume · PROCESS DIES
```

Stack overflow throws a normal `RangeError` you can catch. **Heap exhaustion kills the process** — V8 aborts, no exception, no cleanup.

<a name="organization"></a>
# 2. How the heap is organized

V8 doesn't treat all objects the same, and the reason is one observation about how programs actually behave:

> **Most objects die almost immediately.** A request handler creates hundreds of temporary objects — a parsed body, some intermediate arrays, a response object — and every one is garbage milliseconds later. Meanwhile a few things, like your database connection pool, live for days.

So checking every object equally would be wasteful: you'd repeatedly re-examine the long-lived things that are obviously still in use.

**V8's answer is to split memory in two: a small area for new objects, and a large area for things that have proved they'll stick around.** New objects get checked constantly (cheap, because most are already garbage). Survivors get promoted to the big area, which is checked rarely.

This is called **generational** garbage collection — objects are grouped by age.

```
┌─────────────── HEAP ────────────────────────────────────┐
│  YOUNG GENERATION (~16-64MB)      OLD GENERATION (~2GB) │
│  ┌──────────────────────┐         ┌───────────────────┐ │
│  │ new objects          │ survive │ long-lived stuff  │ │
│  │ collected constantly │ 2 GCs   │ collected rarely  │ │
│  │ ~1ms  ✅ cheap       │ ──────▶ │ 50-200ms ⚠️ slow  │ │
│  └──────────────────────┘         └───────────────────┘ │
│  + LARGE OBJECT SPACE — big arrays/buffers, never moved │
└─────────────────────────────────────────────────────────┘
```

| | **Minor GC** (young) | **Major GC** (old) |
|---|---|---|
| Frequency | constantly | rarely |
| Pause | ~1 ms | **50–200 ms+** ⚠️ |
| Cost scales with | *survivors* only | **total heap size** |

**Why this matters for latency:** minor GC is cheap because it only touches survivors — usually few. Major GC cost scales with **how much sits in the old generation**, and those pauses **block the event loop** like any other CPU work.

> ⭐ **This is the causal chain behind "leaks cause latency spikes before crashes":**
> more retained objects → bigger old generation → longer major GCs → **p99 climbs**. The OOM arrives much later.

<a name="marksweep"></a>
# 3. ⭐ Mark & Sweep

## How does JavaScript know what to delete?

It could count references — *"three things point at this object, so keep it."* **JavaScript doesn't do that.** Instead it asks a different question:

> **"Starting from the things I definitely can't delete, can I still reach this object?"**

Those starting points are called **roots**. A root is anything guaranteed to be alive right now:
- the **global object** — anything global is permanently reachable
- the **current call stack** — variables in functions that are mid-execution
- **active closures**, **running timers**, and **registered event listeners**

Garbage collection walks outward from those roots, following every reference. **Anything it reaches, it keeps. Anything it never reaches, it deletes.**

```
        ROOTS  (global object · current call stack · active closures)
          │
          ├──▶ app ──▶ config ──▶ dbUrl              ✅ reachable → KEEP
          │      └──▶ userCache ──▶ {user objects}   ✅ reachable → KEEP
          │
          ✗    orphan ⟷ orphan2                     ❌ unreachable → FREE
               (they reference EACH OTHER, but nothing
                reaches them from a root)
```

```
1. MARK     start at the roots, walk every reference, mark what you reach
2. SWEEP    anything unmarked is garbage — free it
3. COMPACT  slide survivors together to remove fragmentation
```

## Why reachability, not reference counting

```js
const a = {}; const b = {};
a.friend = b;  b.friend = a;      // circular reference
// both then go out of scope
```

Reference counting would see one reference each and **leak forever** — a real problem in languages that use it. Mark & sweep only asks *"can I reach it from a root?"* No → collect, cycles and all.

> ⭐ **So circular references do NOT leak in JavaScript.** Anyone who says they do is thinking of reference-counted languages. What *does* leak is anything still reachable from a root — a global cache, a live listener, a running timer. **Those are roots.**

**Why GC still pauses:** marking needs a consistent view of memory, so the world stops. V8 marks incrementally and concurrently to soften this, but the finishing work still pauses — which is why a large heap hurts.

<a name="oom"></a>
# 4. ⭐ Why Node runs out of memory

## ① The heap limit is V8's, not your machine's
```bash
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit / 1e9)"  # ~2-4
```
**A 64GB server still gives Node ~2–4GB by default.** You crash with RAM to spare:
```
FATAL ERROR: Ineffective mark-compacts near heap limit
             JavaScript heap out of memory
```
That message literally means *"GC ran repeatedly and couldn't free enough."*
```bash
node --max-old-space-size=8192 app.js
```

## ② You genuinely loaded too much
```js
const rows = await Order.find();               // ❌ 5M documents into an array
const data = await fs.readFile('huge.csv');    // ❌ 2GB into a Buffer
JSON.parse(hugeString);                        // ❌ doubles it while parsing
```
Not a leak — just more than fits. **Fix with streaming, pagination or batching** ([Part 9.5](09.5-streams-deep-dive.md)), never with a bigger heap flag.

## ③ An actual leak — §5

## ④ ⭐ The container kills you and the heap looks fine

The one almost nobody knows:

```
RSS (what the OS sees) = HEAP + EXTERNAL + CODE + STACK
                                  ↑
                          Buffers live HERE — OFF-heap
```

**`Buffer` memory is external.** It doesn't count against `--max-old-space-size` and barely appears in a heap snapshot:

```
Heap: 400MB  ✅ healthy
RSS:  2.1GB  💥 container limit 2GB → OOMKilled, exit code 137
```

| | **Heap OOM** | **Container OOMKill** |
|---|---|---|
| Error | `JavaScript heap out of memory` | killed, **exit 137**, no JS error |
| Cause | JS objects | usually **Buffers**, or heap limit > container limit |
| Diagnose | heap snapshot | `process.memoryUsage().rss` vs `.heapUsed` |

> ⚠️ **The classic misconfiguration:** container limit 2GB, `--max-old-space-size=4096`. V8 grows to 4GB and the orchestrator kills it at 2GB — **before V8 ever feels pressure to GC hard.**
> **Set the heap ceiling to ~75% of the container limit.**

```js
const m = process.memoryUsage();
// rss: total OS memory · heapUsed: live JS objects · external: Buffers ⭐
```

<a name="leaks"></a>
# 5. Memory leaks — the four causes

A leak is **memory that's still reachable but will never be used again.** GC is working correctly; you told it to keep things.

```js
// ① a global collection that only grows          ← by far the most common
const cache = {};
app.use((req, res, next) => { cache[req.id] = req; next(); });
// → LRU with a max size, or Redis with a TTL

// ② listeners added, never removed
emitter.on('data', handler);     // inside a request handler = one leak per request
// → emitter.off(); the "11 listeners added" warning IS the leak detector

// ③ timers never cleared
setInterval(poll, 1000);         // the interval is a ROOT; it retains its closure
// → clearInterval on disconnect / shutdown

// ④ closures retaining a whole scope
function outer() {
  const huge = new Array(1e7);   // 80MB
  return () => 42;               // ⚠️ doesn't use `huge`, but SHARES ITS CONTEXT
}
```

④ is the V8 shared-context trap from [Part 1 §4](01-javascript-execution-model.md): **one context object per scope, shared by every closure declared in it.** If any surviving closure needs any variable from that scope, the whole context — `huge` included — stays alive.

## `Weak` collections exist for exactly this
```js
const cache = new Map();       // ❌ strong reference — keys can never be collected
const cache = new WeakMap();   // ✅ the entry disappears when the key is collected
```
Useful for metadata attached to objects whose lifecycle you don't own. Trade-off: not enumerable, no `size` — deliberately, since entries can vanish at any moment.

<a name="retained"></a>
# 6. ⭐ Retained memory & heap snapshots

## Shallow vs Retained — the question

```js
const app = {
  name: 'server',              // shallow: a few bytes
  users: new Map(/* 10,000 user objects, 50MB */),
};
```

```
SHALLOW SIZE  = memory the object itself occupies
                → `app` is tiny. A few pointers. ~100 bytes.

RETAINED SIZE = shallow + everything that would be FREED if this object vanished
                → `app` retains 50MB, because deleting it orphans the whole Map
```

```
        app  (shallow: 100B · retained: 50MB)  ⭐
         │
         └──▶ Map ──┬──▶ user1  (shallow 200B)
                    ├──▶ user2
                    └──▶ ... 10,000 more
```

> ⭐ **Retained size is the number that matters, because it answers "what do I delete to get the memory back?"**
> Sorting by *shallow* size shows thousands of small strings — true, and useless. Sorting by *retained* size shows the **one** object holding them all.

**The related concept — the dominator.** X dominates Y if **every** path from a root to Y passes through X. Deleting a dominator frees everything it dominates. Retained size is exactly the total of what an object dominates, which is why the Dominators view finds culprits fastest.

## The three-snapshot technique
```
1. Take snapshot #1               (baseline, after warmup)
2. Exercise the suspect endpoint  1,000 times
3. Take snapshot #2
4. Wait, force GC, take #3
5. Compare #1 → #3, sort by Delta
```

**Why three:** snapshot #2 is full of garbage that simply hasn't been collected yet. Anything **still present in #3 after GC** is genuinely retained — your leak, not noise.

> DevTools forces a full GC before every snapshot, so you only see live objects. That's also why snapshotting **pauses the process** — seconds, on a large heap. Don't casually snapshot a production instance under traffic.

<a name="devtools"></a>
# 7. Chrome DevTools workflow

```bash
node --inspect app.js        # then chrome://inspect → Memory tab
```

| View | Use it for |
|---|---|
| **Summary** | objects grouped by constructor — start here |
| **Comparison** ⭐ | delta between two snapshots — *what did those 1,000 requests leave behind?* |
| **Containment** | walk the graph from the roots |
| **Dominators** | sorted by retained size — biggest culprits first |
| **Retainers** panel ⭐ | **the answer** — names exactly what's holding this object |

> ⭐ **The Retainers panel is where the investigation ends.** Everything else tells you *what* leaked; Retainers tells you *who is holding it* — which is the line of code you fix.

**Allocation instrumentation on timeline** records allocations over time; blue bars are memory still live at the end. Those bars are your leak, and you can click through to the allocating stack trace.

**In production:**
```js
require('v8').writeHeapSnapshot();
// or start with --heapsnapshot-signal=SIGUSR2, then: process.kill(pid, 'SIGUSR2')
```
Snapshot a **drained** instance. And note the file is roughly the size of your heap — a 2GB heap makes a 2GB file you then have to load into DevTools.

<a name="interview"></a>
# 8. Interview Questions & Answers

### Q1. Why does Node run out of memory?
> "Four distinct causes, needing different fixes.
>
> **① The V8 heap limit is ~2–4GB by default, regardless of machine RAM** — so you get `JavaScript heap out of memory` while `free -h` shows plenty available. `--max-old-space-size` raises it.
>
> **② You genuinely loaded too much** — `find()` with no limit, `readFile` on a 2GB CSV, `JSON.parse` on a huge string. Not a leak, just more than fits. Fix with streaming, pagination or batching — **not a bigger heap flag**, which only delays it.
>
> **③ A real leak** — something retained that will never be used again.
>
> **④ The one people miss — the container kills you while the heap looks fine.** `Buffer` memory is **off-heap**: it doesn't count against `max-old-space-size` and barely shows in a snapshot. Heap sits at 400MB, RSS hits 2.1GB, and Kubernetes OOMKills with **exit 137** and no JavaScript error. The classic misconfiguration is a 2GB container with `--max-old-space-size=4096` — V8 grows past the container limit before it ever feels enough pressure to GC hard. **Set the heap ceiling to ~75% of the container limit.**
>
> Diagnostically: an OOM **error** means heap; **exit 137 with no error** means the OS killed you — compare `rss` against `heapUsed` and look at Buffers."

### Q2. How do you debug memory leaks?
> "**Confirm it's a leak first, from the shape of the graph.** Healthy memory is a sawtooth returning to the same floor after each GC. A leak is a sawtooth whose **floor keeps rising** — each GC recovers less than the last. Flat-but-high isn't a leak, just a big working set.
>
> **Then the three-snapshot technique.** Snapshot after warmup, exercise the suspect path a thousand times, snapshot again, force GC and take a third. Compare first and third in the **Comparison** view, sorted by delta. Three matter because the second is full of uncollected garbage — anything still in the third is genuinely retained.
>
> **Sort by retained size, not shallow** — shallow lists thousands of small strings, which is true and useless. Retained shows the one object holding them all.
>
> **Then the Retainers panel, which is where it ends** — it names exactly what's holding the object, and that's the line you fix. Usual answers: a Map used as a cache with no eviction, listeners added per request without `off()`, or an uncleared `setInterval`.
>
> In production I'd start from metrics — a rising post-GC baseline plus climbing p99 — then snapshot a **drained** instance, since snapshotting pauses the process for seconds."

### Q3. What is retained memory?
> "**Retained size is the memory that would be freed if that object were deleted** — its own size plus everything only reachable through it. **Shallow size** is just the object itself.
>
> Classic example: an object holding a Map of 10,000 users has a shallow size of maybe 100 bytes — a few pointers — but a retained size of 50MB, because deleting it orphans the entire Map.
>
> **It's the number that matters because it answers 'what do I delete to get the memory back?'** Shallow size ranks thousands of small strings at the top and tells you nothing actionable.
>
> The related idea is a **dominator** — X dominates Y if every path from a root to Y passes through X. Retained size is exactly the total of what an object dominates, which is why the Dominators view finds culprits fastest.
>
> And it ties back to how GC works: JavaScript frees by **reachability**, not reference counting. A large retained size means something is keeping a whole subgraph reachable from a root — which is what a leak actually is."

### Q4. Do circular references leak in JavaScript?
> "No. Mark & sweep works on **reachability from roots**, not reference counts, so two objects pointing at each other with nothing else referencing them are collected normally. Reference-counted languages have that problem; V8 doesn't. What actually leaks is anything still reachable from a root — a global, a live listener, a running timer. **Those are roots.**"

### Q5. Does `--max-old-space-size` fix a leak?
> "No — it raises the ceiling, so you crash later instead of sooner. It's right when you legitimately need a bigger working set, wrong for a leak, where you're only buying time. It can even make things worse: a bigger old generation means **longer major GC pauses**, so p99 degrades before the crash does."

### Q6. Stack overflow vs heap out of memory?
> "**Stack overflow** is a `RangeError` from too-deep recursion — the stack is ~1MB, roughly 11,000 frames. Normal, catchable, and about call depth, not data size. **Heap OOM** is V8 aborting the process because GC can't free enough — fatal, not catchable, and about data volume. Different regions, different causes, different fixes."

### Q7. When would you use `WeakMap`?
> "When attaching data to objects whose lifetime you don't control. A regular `Map` holds a **strong** reference, so its keys can never be collected — using one as a cache keyed by request or socket objects is a textbook leak. `WeakMap` holds keys weakly, so entries vanish when the key is collected. The trade-off is that it isn't enumerable and has no `size` — deliberately, since entries can disappear at any moment."

<a name="cheatsheet"></a>
# 9. Cheat Sheet

### Stack vs Heap
```
STACK  frames · primitives · REFERENCES · ~1MB · auto-freed · LIFO
HEAP   objects · arrays · closures · strings · ~2-4GB · garbage collected

overflow → RangeError, CATCHABLE, about call DEPTH
heap OOM → FATAL, process dies, about data VOLUME
```

### GC
```
generational hypothesis: MOST OBJECTS DIE YOUNG

YOUNG  constant · ~1ms · cost scales with SURVIVORS
OLD    rare · 50-200ms ⚠️ · cost scales with TOTAL HEAP

⭐ GC runs ON THE MAIN THREAD → pauses BLOCK the event loop
⭐ chain: more retained → bigger old gen → longer GC → p99 climbs → OOM LAST
```

### Mark & Sweep
```
MARK (walk from ROOTS) → SWEEP (free unmarked) → COMPACT (defragment)
ROOTS = global object · call stack · active closures · TIMERS · LISTENERS

⭐ frees by REACHABILITY, not reference counts
   → circular references do NOT leak in JS
   → what leaks is anything still reachable FROM A ROOT
```

### Why Node OOMs
```
① heap limit is ~2-4GB regardless of machine RAM → --max-old-space-size
② loaded too much (find() no limit · readFile · JSON.parse) → STREAM instead
③ a real leak
④ ⭐ CONTAINER OOMKill with a healthy heap:
     RSS = heap + EXTERNAL(Buffers, off-heap) + code + stack
     exit 137, no JS error
     ⚠️ never set max-old-space-size ABOVE the container limit → ~75% of it
```

### Leaks — 4 causes
```
① growing global collection   ← most common (cache with no eviction)
② listeners never removed     ← "11 listeners added" warning IS the detector
③ timers never cleared        ← an interval is a ROOT
④ closures sharing a scope's context (V8: one context per scope)

WeakMap/WeakSet → weak keys, no leak. Not enumerable, no .size.
```

### Retained memory ⭐
```
SHALLOW  = the object itself                      (~100B)
RETAINED = shallow + all it EXCLUSIVELY keeps alive  (50MB)  ⭐ THE useful number

DOMINATOR: every root→Y path goes through X  →  retained size = what X dominates

⭐ sort by RETAINED, not shallow
   shallow → 10,000 tiny strings (true, useless)
   retained → the ONE object holding them
```

### Debugging
```
SHAPE first: sawtooth to the same floor ✅ · RISING FLOOR ❌ leak

3-SNAPSHOT: baseline → 1000× the suspect → snapshot → GC → snapshot#3
            compare 1→3 (snapshot 2 is full of uncollected garbage)

DevTools: Summary · COMPARISON ⭐ · Containment · Dominators · RETAINERS ⭐⭐
          Retainers = WHO is holding it = the line you fix

prod: v8.writeHeapSnapshot() on a DRAINED instance (it pauses for seconds,
      and the file is as big as your heap)
process.memoryUsage() → rss · heapUsed · external(Buffers)
```
