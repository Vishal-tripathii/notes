<a name="deploy"></a>
# 1. What happens during a deploy

A rolling deploy in Kubernetes (most platforms are similar):

```
1. New pod starts → app boots → readiness check passes → starts receiving traffic
2. Old pod is told to stop:
   a. it's removed from the load balancer's list   (takes a few seconds to spread!)
   b. it receives SIGTERM
   c. it has terminationGracePeriodSeconds (default 30s) to finish
   d. still running after that? → SIGKILL (exit 137), no more chances
```

> **Analogy 🍽️ — closing a restaurant for the night.** You lock the front door so no new guests come in. The guests already eating finish their meal. Then you clean up and switch off the lights. You don't switch off the lights while people are still eating.

<a name="shutdown"></a>
# 2. ⭐ Graceful shutdown, step by step

```js
const server = app.listen(PORT);
let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return;            // SIGTERM + SIGINT could both arrive
  shuttingDown = true;
  logger.info({ signal }, 'shutting down');

  // ⏱️ hard backstop — if anything hangs, exit anyway before the platform SIGKILLs us
  setTimeout(() => { logger.error('forced exit'); process.exit(1); }, 25_000).unref();

  // 1. fail the readiness check so the load balancer stops sending new requests (§3)
  // 2. give the load balancer a moment to notice (it doesn't react instantly)
  await new Promise(r => setTimeout(r, 5_000));

  // 3. stop accepting new connections; wait for in-flight requests to finish
  server.close();                       // callback/close event fires when all connections are gone
  server.closeIdleConnections();        // drop idle keep-alive sockets now (Node 18.2+)

  await once(server, 'close');          // from 'node:events'

  // 4. close everything else, in order
  await queueWorker.close();            // stop taking new jobs, finish the current one
  await mongoose.disconnect();
  await redis.quit();

  process.exitCode = 0;                 // let the event loop empty and exit naturally
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));
```

**Why each step matters:**

| Step | Without it |
|---|---|
| fail readiness + short wait | the load balancer still routes new requests to a server that's closing → connection errors |
| `server.close()` | the process exits with requests half-done → users see errors after every deploy |
| `closeIdleConnections()` | idle keep-alive connections keep `close()` waiting until they time out on their own |
| close DB/queue | jobs left half-processed; connections left dangling on the database |
| hard timeout | one stuck request blocks shutdown until SIGKILL — no logs, no clean exit |

**Make the numbers fit:** wait-for-LB (5s) + longest normal request + cleanup **<** your own backstop (25s) **<** the platform's grace period (30s).

> 🧠 **Remember the order:** **stop new → finish current → close connections → exit.**

<a name="health"></a>
# 3. ⭐ Health checks: liveness vs readiness

The platform asks your app two **different** questions:

| | **Liveness** — "are you alive?" | **Readiness** — "can you take traffic right now?" |
|---|---|---|
| If it fails | the platform **restarts** the container | the platform **stops sending traffic** (no restart) |
| Should check | only the process itself: can it answer at all? | dependencies you can't work without (DB, cache), and "am I shutting down?" |
| Typical endpoint | `GET /health/live` → 200 | `GET /health/ready` → 200 or 503 |

```js
app.get('/health/live', (req, res) => res.sendStatus(200));     // cheap, no dependencies

app.get('/health/ready', async (req, res) => {
  if (shuttingDown) return res.sendStatus(503);
  try {
    await mongoose.connection.db.admin().ping();
    res.sendStatus(200);
  } catch {
    res.sendStatus(503);
  }
});
```

**The classic mistake: checking the database in the liveness probe.** The database blips for 20 seconds → every instance fails liveness → the platform **restarts all of them at once** → they all reconnect at the same time → the database gets hammered → outage. A database problem is a reason to stop traffic (readiness), not to restart a healthy Node process.

Also:
- Keep health checks **fast** and cheap — they run every few seconds.
- A blocked event loop makes the liveness check time out — so liveness indirectly detects a frozen server. That's useful.
- **Startup probe** (Kubernetes): gives a slow-starting app time to boot before liveness checks begin.

> 🧠 **Remember:** liveness = "should I restart you?" Readiness = "should I send you users?"

<a name="docker"></a>
# 4. Docker for Node — a good Dockerfile

```dockerfile
# ---- build stage: has dev tools, compiles TypeScript etc. ----
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                                  # exact versions from the lockfile (Part 4.5 §4)
COPY . .
RUN npm run build

# ---- runtime stage: only what's needed to run ----
FROM node:22-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node                                   # don't run as root
EXPOSE 3000
CMD ["node", "dist/index.js"]               # exec form, node directly (see §5)
```

Why each choice:

| Choice | Reason |
|---|---|
| **multi-stage** | build tools and dev dependencies stay out of the final image → smaller, fewer security holes |
| copy `package*.json` **before** the source | Docker caches the `npm ci` layer; it only re-runs when dependencies change, so builds are fast |
| `npm ci` | reproducible install from the lockfile |
| `--omit=dev` | no test/build tools in production |
| pinned base image (`node:22-slim`) | known Node version; slim = smaller. Pin a digest for full reproducibility |
| `USER node` | if the app is compromised, the attacker isn't root in the container |
| `NODE_ENV=production` | libraries switch to production behaviour ([Part 4.5 §6](04.5-npm-packages-and-configuration.md)) |
| `.dockerignore` with `node_modules`, `.git`, `.env` | keeps local junk and secrets out of the image |

**Secrets never go in the Dockerfile** (`ENV API_KEY=...`) — anyone with the image can read them. Inject them at runtime.

<a name="pid1"></a>
# 5. ⭐ The PID 1 problem

The first process in a container is **PID 1**, and Linux treats PID 1 specially: **signals like SIGTERM are ignored unless the process installed a handler.**

Two common ways to get this wrong:

```dockerfile
CMD npm start            # ❌ shell form → /bin/sh is PID 1, node is its child
CMD ["npm", "start"]     # ❌ npm is PID 1 → may not pass SIGTERM on to node
```

In both cases SIGTERM never reaches your `process.on('SIGTERM')` handler, so there's **no graceful shutdown** — the container just sits there until the platform SIGKILLs it after 30 seconds. Deploys become slow and drop requests.

**Fixes:**
- ✅ `CMD ["node", "dist/index.js"]` — exec form, Node itself is PID 1 and receives SIGTERM.
- ✅ Add a tiny init process: `docker run --init`, or `tini` as the entrypoint. It forwards signals and cleans up zombie child processes — useful if your app spawns children.

<a name="memory"></a>
# 6. Memory limits in containers

- Modern Node (12+) notices the container's memory limit when sizing its heap — but the heap is only part of memory. **Buffers, native code and the stack live outside the heap** ([Part 2.8 §4](02.8-memory-management.md)).
- If you set `--max-old-space-size` yourself, keep it **well below** the container limit (around 75%), so V8 garbage-collects hard before the container hits the limit and gets **OOMKilled (exit 137)**.
- Watch the container's memory (RSS), not just `heapUsed`.

<a name="pm2"></a>
# 7. PM2 vs Docker/Kubernetes

| | PM2 | Docker + Kubernetes (or ECS, Cloud Run…) |
|---|---|---|
| Restarts crashed apps | ✅ | ✅ |
| Uses all CPU cores | cluster mode: `pm2 start app.js -i max` | run several containers/pods (one Node process each) |
| Zero-downtime deploys | `pm2 reload` | rolling updates |
| Multiple machines, autoscaling | ❌ | ✅ |
| Typical use | a single VM / small setups | most modern production systems |

**Don't stack them:** PM2 cluster mode inside a Kubernetes pod means two systems both trying to manage processes and restarts. In containers, run **one Node process per container** and let the platform do the rest.

<a name="interview"></a>
# 8. Interview Questions & Answers

### Q1. Walk me through graceful shutdown in a Node API.
> "On SIGTERM: mark the app as shutting down so readiness returns 503, wait a few seconds so the load balancer stops routing to it, then `server.close()` to stop new connections while in-flight requests finish, closing idle keep-alive connections too. Then close the queue worker, database and Redis, and exit. A hard timeout makes sure it exits before the platform's grace period runs out and it gets SIGKILLed."

### Q2. Liveness vs readiness?
> "Liveness asks whether the process should be restarted — it should only check that the app can respond at all. Readiness asks whether it should receive traffic — it can check the database and return 503 while shutting down. Putting a database check in liveness is a classic mistake: a short DB outage restarts every instance at the same time."

### Q3. Our deploys take 30 seconds per pod and drop requests. Why?
> "Probably SIGTERM never reaches Node — the container runs `npm start` or the shell form of `CMD`, so a shell or npm is PID 1 and doesn't forward the signal. The platform waits out the grace period and SIGKILLs it. Fix: `CMD [\"node\", \"index.js\"]` or an init like tini, plus a proper SIGTERM handler."

### Q4. What makes a good Node Dockerfile?
> "Multi-stage build so dev tools stay out of the final image; copy `package.json` and the lockfile before the source so the install layer caches; `npm ci --omit=dev`; a pinned slim base image; `NODE_ENV=production`; run as the non-root `node` user; exec-form `CMD` with node directly; a `.dockerignore`; and no secrets baked in."

### Q5. The container keeps getting killed with exit code 137, but the heap looks fine. Why?
> "137 is SIGKILL — in containers that's the OOM killer. The heap is only part of the memory; Buffers and native memory are outside it. Check the container's RSS, look for large Buffers or streams without backpressure, and keep `--max-old-space-size` well below the container limit."

### Q6. PM2 or Kubernetes?
> "PM2 is a process manager for one machine — restarts, cluster mode, reloads. Kubernetes manages containers across machines with autoscaling and rolling deploys. In Kubernetes I run one Node process per container and don't use PM2 inside, so two systems aren't fighting over restarts."

<a name="cheatsheet"></a>
# 9. Cheat Sheet

```
DEPLOY: new pod ready → old pod: removed from LB → SIGTERM → 30s grace → SIGKILL (137)

GRACEFUL SHUTDOWN — stop new → finish current → close connections → exit
shuttingDown = true → readiness 503 → wait ~5s → server.close() + closeIdleConnections()
→ close queue, DB, Redis → exitCode = 0
hard backstop timer (unref) < platform grace period

HEALTH
liveness  = "restart me?"   → cheap, NO dependency checks
readiness = "send users?"   → DB ping, 503 while shutting down
DB check in liveness → whole fleet restarts during a DB blip ❌

DOCKERFILE
multi-stage · copy package*.json first (layer cache) · npm ci --omit=dev
slim pinned base · NODE_ENV=production · USER node · .dockerignore · no secrets
CMD ["node", "dist/index.js"]   ← exec form

PID 1: `CMD npm start` / shell form → SIGTERM never reaches node → fix: node directly or --init/tini

MEMORY: heap ≠ container memory · max-old-space-size ≈ 75% of limit · watch RSS · 137 = OOMKilled

PM2 = one machine · Kubernetes = many · in containers: one node process per container
```
