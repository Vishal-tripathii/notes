<a name="rule"></a>
# 1. The rule: every wait needs a limit

> **Analogy ☎️ — a phone call with no end.** If you call a shop and they put you on hold, you hang up after a few minutes. A server that never hangs up keeps every "on hold" call open forever — and eventually has no lines left for anyone else.

Every time your code waits on something — a client sending its request, a database, another API — there must be a **timeout**. Without one, a single slow dependency piles up open connections, memory and pool slots until the whole service stops.

There are timeouts on **both sides**:

```
client ──▶ [load balancer] ──▶ YOUR NODE SERVER ──▶ database / other APIs
            its idle timeout     server timeouts (§2)    outgoing timeouts (§4-5)
```

---

<a name="server-timeouts"></a>
# 2. ⭐ Server-side timeouts

Node's `http.Server` has several separate timers. The ones that matter:

| Setting | Limits | Default (Node 18+) | Protects against |
|---|---|---|---|
| `server.headersTimeout` | time to receive the request **headers** | 60s | slowloris: clients that send headers one byte at a time |
| `server.requestTimeout` | time to receive the **whole request** (headers + body) | 300s (5 min) | slow uploads tying up the server |
| `server.keepAliveTimeout` | how long an **idle** kept-alive connection stays open | 5s | idle sockets piling up |
| `server.timeout` | socket inactivity | 0 (off) | — mostly superseded by the above |

```js
const server = app.listen(3000);
server.headersTimeout = 20_000;
server.requestTimeout = 30_000;
server.keepAliveTimeout = 65_000;   // see §3 — why it's bigger than you'd guess
```

**Important:** none of these stop **your handler** if *it* is slow (say, waiting 2 minutes on a database). For that you need timeouts on the things you wait on (§4–5), or a per-route timeout that responds `503`/`504` and aborts the work.

<a name="502"></a>
# 3. ⭐ The random-502 bug: keep-alive timeouts

**Keep-alive** means one TCP connection is reused for many requests, which saves a handshake every time. Load balancers (AWS ALB, nginx, GCP) keep connections to your Node servers open and reuse them.

**The bug:** each side closes an idle connection after its own timeout. Node's default is **5 seconds**. AWS ALB's default idle timeout is **60 seconds**.

```
0s   LB ↔ Node connection becomes idle
5s   Node: "idle 5s, closing it"  ──── close is on its way ────┐
5s   LB: "still open for me, I'll reuse it" → sends a request ─┘  💥 crosses the close
     → connection reset → the LB returns 502 Bad Gateway to the user
```

It happens rarely and randomly — only when a request lands in that tiny window — so it's maddening to debug.

**The fix: Node must keep idle connections open *longer* than the load balancer does**, so the LB is always the one that closes first:

```js
server.keepAliveTimeout = 65_000;   // > ALB's 60s
server.headersTimeout   = 66_000;   // keep this ≥ keepAliveTimeout (needed on older Node versions)
```

> 🧠 **Remember:** **"the backend waits longer than the load balancer."** Random 502s behind a load balancer → check keep-alive timeouts first.

<a name="outgoing"></a>
# 4. Outgoing calls: keep-alive agents & `fetch`

When **your** server calls other services, the same rules apply in reverse.

**Reuse connections.** Opening a new TCP + TLS connection for every outgoing call adds several round trips of delay. Since **Node 19, the global `http`/`https` agent uses keep-alive by default**. Node's built-in **`fetch`** (stable since Node 21, built on the `undici` library) also pools and reuses connections.

**Give every outgoing call a timeout.** `fetch` has **no timeout by default** — it can wait for minutes.

```js
const res = await fetch('https://payments.example.com/charge', {
  method: 'POST',
  body: JSON.stringify(payload),
  headers: { 'content-type': 'application/json' },
  signal: AbortSignal.timeout(3000),          // give up after 3 seconds ✅
});
if (!res.ok) throw new AppError(`payments returned ${res.status}`, { status: 502 });
```

⚠️ `fetch` does **not** reject on 404 or 500 — it only rejects on network failures and aborts. Always check `res.ok` / `res.status`.

**Also remember:** a timeout should be shorter than whatever is waiting on *you*. If the client gives up after 10s and you wait 30s on a downstream call, you're doing work for nobody.

<a name="abort"></a>
# 5. ⭐ `AbortController` — cancelling work

`AbortController` is the standard way to say **"stop, I don't need this anymore."** It's the same API as in browsers.

```js
const controller = new AbortController();
const { signal } = controller;

setTimeout(() => controller.abort(), 5000);   // cancel after 5s (or on any condition)

await fetch(url, { signal });                  // throws an AbortError when cancelled
```

Many Node APIs accept a `signal`: `fetch`, `fs.readFile`, `events.once`, `timers/promises` `setTimeout`, `child_process.spawn`, `stream.pipeline`, and many libraries.

**Shortcuts:**

```js
AbortSignal.timeout(3000)                     // a signal that aborts itself after 3s
AbortSignal.any([req.signal, AbortSignal.timeout(3000)])   // abort on whichever comes first (Node 20+)
```

**Real use — stop working when the user leaves:**

```js
app.get('/report', async (req, res) => {
  const controller = new AbortController();
  req.on('close', () => controller.abort());   // client closed the tab / gave up
  const data = await buildReport({ signal: controller.signal });
  res.json(data);
});
```

Your own long functions can respect it too: check `signal.aborted` in loops, or call `signal.throwIfAborted()`.

> 🧠 **Remember:** a timeout says "don't wait forever." An `AbortSignal` is how you tell the work to **actually stop**.

<a name="retries"></a>
# 6. Retries — only the safe ones

A failed call is often worth one more try — networks blip. But retries can also **multiply** an outage. Rules:

- **Only retry what's safe to repeat.** `GET`, `PUT`, `DELETE` are idempotent. A `POST` that charges a card isn't — unless you send an idempotency key ([Part 11 §5](11-api-design.md)).
- **Only retry errors that might go away:** network errors, timeouts, `429`, `502`, `503`, `504`. Never retry `400`, `401`, `403`, `404`, `422` — they'll fail the same way again.
- **Wait longer each time, with randomness** (exponential backoff + jitter): ~200ms, 400ms, 800ms ± random. Without jitter, every client retries at the same instant and hits the struggling service together.
- **Cap it:** 2–3 attempts, and a total time budget.
- **Respect `Retry-After`** when the server sends it.
- When a dependency is clearly down, stop calling it for a while — a **circuit breaker** ([Part 9](09-performance.md), [System-design Part 22](../System-design/22-design-patterns.md)).

<a name="caching"></a>
# 7. ⭐ HTTP caching headers: `Cache-Control` & `ETag`

The cheapest request is the one that never reaches your server. HTTP caching lets **browsers and CDNs** reuse responses.

### `Cache-Control` — "how long may you keep this?"

| Header | Means | Use for |
|---|---|---|
| `Cache-Control: public, max-age=31536000, immutable` | anyone may cache it for a year, it will never change | files with a hash in the name: `app.3f9a1c.js` |
| `Cache-Control: public, max-age=60` | cache for 60 seconds | a public product list that can be a minute old |
| `Cache-Control: private, max-age=0, must-revalidate` | only the user's browser, and check with the server each time | a user's own dashboard data |
| `Cache-Control: no-cache` | you may store it, but **ask the server before reusing** | data that changes but is often unchanged |
| `Cache-Control: no-store` | never store it anywhere | bank details, tokens, anything sensitive |

⚠️ `no-cache` does **not** mean "don't cache." It means "check first." The one that means "don't store" is **`no-store`**.

⚠️ Never mark per-user responses `public` — a CDN might serve one user's data to another.

### `ETag` — "has it changed since you last saw it?"

```
1. GET /products/42           → 200, body, ETag: "v7"
2. GET /products/42           → If-None-Match: "v7"
   server: still "v7"?        → 304 Not Modified, NO body   (tiny, fast)
```

Express sets `ETag`s on responses automatically and answers `304` when they match. You save bandwidth and the client's time — though your server still runs the handler unless you check the version *before* doing the expensive work.

`ETag`s also prevent lost updates in APIs: `PUT` with `If-Match: "v7"` → `412 Precondition Failed` if someone else changed it first (optimistic locking over HTTP — [database Part 04.6](../database/04.6-locking-deadlocks-and-anomalies.md)).

<a name="http2"></a>
# 8. HTTP/2, briefly

- **One connection, many requests at once** (multiplexing) — HTTP/1.1 needed several connections to load assets in parallel.
- **Header compression**, binary framing.
- Node has an `http2` module, but in practice **HTTP/2 is handled by the load balancer, CDN or reverse proxy**, which then talks HTTP/1.1 to Node. Express itself runs on HTTP/1.1.
- **HTTP/3** runs over QUIC (UDP) and helps on unreliable mobile networks — again, usually the CDN's job.

<a name="interview"></a>
# 9. Interview Questions & Answers

### Q1. We get random 502s behind an AWS load balancer. What's your first guess?
> "Keep-alive timeouts. Node closes idle connections after 5 seconds by default, the ALB keeps them for 60. Sometimes the ALB reuses a connection at the exact moment Node is closing it, and the request fails with a 502. The fix is making Node's `keepAliveTimeout` longer than the load balancer's idle timeout — say 65 seconds — and `headersTimeout` a bit longer still."

### Q2. What timeouts would you set in a Node API?
> "On the server: `headersTimeout` and `requestTimeout` against slow clients, and `keepAliveTimeout` above the load balancer's. On every outgoing call — HTTP, database, Redis — an explicit timeout, because `fetch` has none by default. And the downstream timeouts should be shorter than the client's, so I'm never working on a request nobody is waiting for."

### Q3. How do you add a timeout to `fetch`?
> "Pass `signal: AbortSignal.timeout(ms)`. When it fires, `fetch` rejects with an abort error. I also check `res.ok`, since `fetch` doesn't reject on 4xx or 5xx statuses."

### Q4. What is `AbortController` used for?
> "Cancelling async work. You pass its `signal` to `fetch`, file operations, timers, streams or your own functions, and call `abort()` when the result isn't needed — on a timeout, or when the client disconnects, so the server stops doing work for someone who's gone. `AbortSignal.any` combines several reasons."

### Q5. When should you retry a failed request?
> "Only when it's safe and might succeed: idempotent operations, or a POST with an idempotency key, and only for network errors, timeouts, 429 and 5xx — never 4xx. Use exponential backoff with jitter, cap the attempts, respect `Retry-After`, and use a circuit breaker so retries don't hammer a service that's already down."

### Q6. `no-cache` vs `no-store`?
> "`no-cache` lets the response be stored but forces a check with the server before reuse — usually via an ETag and a 304. `no-store` forbids storing it at all; that's the one for sensitive data."

### Q7. How does an ETag work?
> "The server sends a version tag with the response. Next time the client sends `If-None-Match` with that tag; if nothing changed, the server replies `304 Not Modified` with no body. With `If-Match` on a `PUT`, it also protects against overwriting someone else's change — the server returns 412 if the version moved on."

<a name="cheatsheet"></a>
# 10. Cheat Sheet

```
EVERY WAIT NEEDS A LIMIT — incoming and outgoing

SERVER                               defaults (Node 18+)
headersTimeout   slow headers        60s
requestTimeout   whole request       300s
keepAliveTimeout idle connection     5s   ⚠️ must be > load balancer idle timeout
behind ALB (60s): keepAliveTimeout = 65_000, headersTimeout = 66_000  → fixes random 502s
"the backend waits longer than the load balancer"

OUTGOING
fetch: no timeout by default → signal: AbortSignal.timeout(3000)
fetch doesn't reject on 4xx/5xx → check res.ok
keep-alive agents default since Node 19 · fetch (undici) pools connections
downstream timeout < client timeout

ABORT
new AbortController() → pass .signal → .abort()
AbortSignal.timeout(ms) · AbortSignal.any([...]) · req.on('close') → abort
timeout = stop waiting · abort = stop the work

RETRIES
safe ops only (GET/PUT/DELETE, or POST + idempotency key)
retry: network, timeout, 429, 502-504 · never 4xx
backoff + jitter, 2-3 tries, Retry-After, circuit breaker

CACHING
immutable hashed assets → public, max-age=31536000, immutable
per-user data → private · sensitive → no-store
no-cache = "check before reuse" (NOT "don't cache")
ETag + If-None-Match → 304 · If-Match on PUT → 412 if changed

HTTP/2 / 3 → usually terminated at the LB/CDN; Node behind it speaks HTTP/1.1
```
