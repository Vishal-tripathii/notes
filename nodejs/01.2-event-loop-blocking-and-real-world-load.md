# Node.js Study Notes — Part 1.2

## What Happens Under Real Load — Loops, Databases, and Thousands of Users

> **Format:** Q&A — my prompts are the questions, the explanations are the answers. Written the way you'd *say* it in an interview.
>
> **Follows:** [Part 1](01-javascript-execution-model.md), which explained *why* one blocked thread freezes everything. This part answers the two questions that come next:
>
> **1. "My handler loops over data — is that a problem?"**
> **2. "What actually happens when thousands of people use the app at once?"**
>
> ⭐ **The short answers:** looping 50 rows is free — do it without guilt. Looping 5 million means **you asked the database the wrong question**. And thousands of users doesn't break the single thread, because almost all of that traffic is *waiting*, which costs nothing. What breaks it is one handler doing real computing.

<a name="numbers"></a>
# 1. Is my loop actually a problem?

People read *"loops block the event loop"* and become scared of `array.map()`. **That's the wrong lesson.** It depends entirely on how many items you're looping over.

Roughly what a simple loop costs:

| Number of items | Time it takes | Verdict |
|---|---|---|
| 100 | 0.0005 ms | 😴 invisible — stop worrying |
| 1,000 | 0.005 ms | 😴 invisible |
| 10,000 | 0.1 ms | ✅ fine |
| 100,000 | 1–5 ms | ✅ acceptable |
| 1,000,000 | 10–50 ms | ⚠️ now you're hurting people |
| 10,000,000 | 100–500 ms | ❌ server-wide freeze |
| 10,000 × 10,000 (nested) | 30–60 **seconds** | ☠️ outage |

> **The practical line: under about 1 millisecond is noise. Over about 10 milliseconds, you're taking time away from every other user.**

So the normal API handler is completely fine:

```js
app.get('/orders', async (req, res) => {
  const orders = await db.query(
    'SELECT * FROM orders WHERE user_id = ? LIMIT 50', [id]
  );
  // ↑ 20ms of WAITING. During this, your thread is free and serving other people.

  const formatted = orders.map(o => ({ ...o, total: o.price * o.qty }));
  // ↑ 50 items. About 2 MICROseconds. This is not your problem. ✅

  res.json(formatted);
});
```

## ⚠️ Watch the shape, not just the count

A **nested** loop is the real danger, because the cost multiplies:

```js
for (const a of listA) {          // 10,000 items
  for (const b of listB) {        // 10,000 items
    if (a.id === b.aId) { ... }   // → 100,000,000 comparisons
  }
}
```

Ten thousand sounds small. **Ten thousand squared is a hundred million.**

And this is the bug that survives code review, because **in development you have 200 seeded rows and it runs instantly.** It only explodes when production data grows. Any time you see a loop inside a loop over data that grows, that's a future outage.

<a name="who"></a>
# 2. ⭐ The real mistake — who does the looping?

This is the actual answer to *"I need to find data and loop over it."*

Compare these two. They return the **same result**:

```js
// ❌ THE MISTAKE
const allOrders = await db.query('SELECT * FROM orders');   // FIVE MILLION rows
const mine  = allOrders.filter(o => o.userId === id);       // 5,000,000 iterations
const total = mine.reduce((sum, o) => sum + o.price, 0);    // 5,000,000 more
```

```js
// ✅ CORRECT
const [{ total }] = await db.query(
  'SELECT SUM(price) AS total FROM orders WHERE user_id = ?', [id]
);
```

**The first version burns ~200ms of computing and freezes every other user. The second burns essentially none.**

But there's a second problem that's arguably worse: the bad version **also pulled 5 million rows across the network into your server's memory.** That's memory pressure, garbage collection pauses, and possibly a crash — on top of the frozen thread.

## Why the database always wins

`WHERE user_id = ?` is fast **because of the index** ([09-database-indexing.md](../09-database-indexing.md)). An index is a sorted structure that lets the database jump straight to the matching rows — roughly 20 steps instead of examining 5,000,000.

> **You cannot beat that with a JavaScript `.filter()`.** You'd be comparing 20 operations against five million. It's not a close race, and no amount of optimizing your loop changes that.

## Where each job belongs

| What you want | ❌ In your code | ✅ In the database |
|---|---|---|
| Only some rows | `.filter()` | `WHERE` |
| In order | `.sort()` | `ORDER BY` (with an index) |
| A count or total | `.reduce()` | `COUNT()` / `SUM()` |
| Data from two tables | a nested loop | `JOIN` |
| Just the first 50 | `.slice(0, 50)` | `LIMIT 50` |
| Grouped totals | building an object by hand | `GROUP BY` |
| No duplicates | `new Set(...)` | `DISTINCT` |

> ⭐ **The rule: never pull data into Node in order to filter, sort, count, join or group it. That's the database's entire job, and it's written in C with indexes.**

## And always paginate

`LIMIT 50` means the number of rows is **bounded** — 50 today, 50 when the table has a hundred million rows.

> **The unbounded query is the real bug. The slow loop is just the symptom.**

Any endpoint returning a list needs a limit ([11-api-design.md](../11-api-design.md)). A query with no `LIMIT` is a time bomb that goes off the day your data grows.

<a name="overlap"></a>
# 3. ⭐ Why waiting is free but computing isn't

This is the mental model for what happens with many users at once, and it's the core insight of the whole note.

## Case A — a normal handler: 5ms of computing, 50ms of waiting

Three users arrive at the same moment:

```
              0ms    5ms         10ms                 55ms  60ms
User A:  CPU [█████]                                  [█]
              └───────── waiting on the DB (FREE) ─────┘
User B:  CPU       [█████]                              [█]
                    └──────── waiting (FREE) ───────────┘
User C:  CPU             [█████]                          [█]
                          └────── waiting (FREE) ─────────┘

Thread:  [A][B][C] ....... idle, all 3 DB queries running at once ....... [A][B][C]
```

**All three finish in about 60ms — not 180ms.**

**Why?** Because the three 50ms waits happened **at the same time**. Your thread handed each query off and moved on immediately, and the database worked on all three simultaneously.

> ⭐ **Waiting overlaps perfectly and costs your thread nothing.**

## Case B — the same handler, but with 200ms of computing

```
User A:  [████████████ 200ms of computing ████████████]
User B:                                                [████ 200ms ████]
User C:                                                                 [████ 200ms ████]
          └─ B waited 200ms doing NOTHING. C waited 400ms doing NOTHING. ─┘
```

**Computing cannot overlap.** There's one thread, and it can only be in one place. So the work queues up, strictly, one after another.

This is called **head-of-line blocking** — like one person at the front of a checkout queue with a full trolley. Everyone behind them waits, no matter how little they're buying.

> **And notice the unfairness: the users being punished did nothing wrong.** One expensive endpoint slows down *every other endpoint on the server*, including your health checks.

<a name="throughput"></a>
# 4. How many users can one server handle?

There's a simple formula, and it's worth being able to state:

```
   requests per second  =  1000 ms  ÷  milliseconds of COMPUTING per request
```

| Computing per request | Max requests/sec | With 1,000 people waiting, the last one waits |
|---|---|---|
| 1 ms | 1,000/s | 1 second |
| 5 ms | 200/s | 5 seconds |
| 50 ms | 20/s | 50 seconds ⚠️ |
| 200 ms | **5/s** | **200 seconds** ☠️ everyone times out |

**Now notice what is NOT in that formula: database time, network time, disk time.**

You could have a query that takes 500ms and still serve a thousand requests a second — **because that 500ms costs your thread nothing.**

> ⭐ **Only computing limits how many users you can serve. That's the whole thesis of Node: waiting is free, computing is not.**

## It fails suddenly, not gradually

This is worth knowing because it explains why servers seem fine and then aren't:

**Below the limit**, everything looks great. Latency is flat, dashboards are green.

**Cross it**, and the queue grows faster than you can drain it. Latency climbs without limit, requests start timing out, clients retry — **and the retries add more load.** There's no gentle warning; you fall off a cliff.

<a name="worldwide"></a>
# 5. What a real production setup looks like

The instinct is *"thousands of users = one poor thread melting."* But in production you're never running just one Node process.

```
                        🌍 users everywhere
                               │
                  ┌────────────▼────────────┐
                  │  CDN (images, JS, CSS)  │ ← ~80% of requests never reach you
                  └────────────┬────────────┘
                               │
                  ┌────────────▼────────────┐
                  │     LOAD BALANCER       │ ← spreads requests around
                  └──┬──────────┬──────────┬┘
                     │          │          │
              ┌──────▼───┐ ┌────▼─────┐ ┌──▼───────┐
              │ SERVER 1 │ │ SERVER 2 │ │ SERVER 3 │
              │ 8 cores  │ │ 8 cores  │ │ 8 cores  │
              │ 8 Node   │ │ 8 Node   │ │ 8 Node   │ ← one process per core
              │ processes│ │ processes│ │ processes│    (cluster)
              └────┬─────┘ └────┬─────┘ └────┬─────┘
                   └────────────┼────────────┘
                                │
                   ┌────────────▼────────────┐
                   │  REDIS cache → DATABASE │
                   └─────────────────────────┘
```

So "one thread" is really **8 processes × 3 servers = 24 independent event loops**. At 5ms of computing per request, that's roughly 4,800 requests/second — and you add servers for more.

## Three things worth understanding about this picture

**① More processes doesn't fix blocking — it divides the damage.**
A 200ms block still freezes the process it lands on. With 24 processes, **1/24th of users get frozen instead of all of them.** That buys you tolerance, not immunity. Scaling out a bad handler multiplies your cloud bill without fixing the defect.

**② Users being far away is a different problem entirely.**
Someone in Tokyo hitting a server in the US pays about 150ms in network travel time, **no matter how fast your code is.** You don't fix distance with threads — you fix it with placement: servers in multiple regions, and a CDN holding copies close to users ([02.7-cdn.md](../02.7-cdn.md)).

**③ Caching is what actually saves you.**
If 10,000 people request the same trending feed, don't compute it 10,000 times. Compute it once, keep it in Redis, serve it in ~1ms ([05-caching.md](../05-caching.md)). **Your 200ms report becomes 200ms once a minute instead of 200ms per request.**

> **One prerequisite for all of this:** any of those 24 processes must be able to serve any request. That means no storing sessions or data in a process's memory — it goes in Redis. This is what "stateless servers" means ([02.5-load-balancer-deep-dive.md](../02.5-load-balancer-deep-dive.md)).

<a name="ladder"></a>
# 6. What to do when you genuinely have a lot of work

Cheapest fix first:

### ① Let the database do it — 95% of cases
Everything in §2. Filter, sort, total and paginate in SQL. Add the index.

### ② Cache the result — compute once, serve many
```js
let report = await redis.get('report');
if (!report) {
  report = await buildReport();                  // slow, but only sometimes
  await redis.setex('report', 300, report);      // reuse for 5 minutes
}
```

### ③ Take it out of the request entirely
For exports, reports, image processing, emails ([13-message-queues.md](../13-message-queues.md)):

```js
app.post('/export', async (req, res) => {
  await queue.add('generate-csv', { userId });
  res.status(202).json({ status: 'processing' });   // responds in ~2ms
});
// a SEPARATE worker process does the actual work
```

**The user gets an instant answer, and the heavy work happens somewhere that isn't serving traffic.**

### ④ `worker_threads` — when you must compute now
Video encoding, PDF generation, image resizing. Runs on a different thread so the main one stays free ([Part 1 §14](01-javascript-execution-model.md)).

### ⑤ Break it up and give others a turn
If it truly must run in this process:

```js
async function processInChunks(items) {
  for (let i = 0; i < items.length; i += 1000) {
    items.slice(i, i + 1000).forEach(doWork);
    await new Promise(r => setImmediate(r));   // ⭐ let the loop breathe
  }
}
```

**That `setImmediate` line hands control back to the event loop**, so queued requests get served before you continue. The total time is the same — but you've stopped hogging.

### ⑥ Stream instead of loading everything
```js
db.queryStream('SELECT * FROM orders').pipe(csvTransform).pipe(res);
```
Constant memory, and the thread is free between chunks ([Part 9.5](09.5-streams-deep-dive.md)).

<a name="detect"></a>
# 7. How you'd notice this in production

The measurement is **event loop lag** — how late a timer fires.

You ask Node to run something in 0ms. If it runs 300ms later, something hogged the thread for 300ms, because Node can't interrupt running code to fire your timer.

```js
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => console.log('lag:', h.percentile(99) / 1e6, 'ms'), 5000);
```

```
under 10ms   ✅ healthy
10–100ms     🟡 something is hogging it sometimes
over 100ms   ❌ requests are queueing behind computing
```

> ⭐ **This is the most important Node health metric, and the reason is subtle: a blocked event loop looks HEALTHY on every other dashboard.** The process isn't crashing or leaking memory. CPU shows one core busy — which is normal for Node. **Only lag reveals it.**

<a name="interview"></a>
# 8. Interview Questions & Answers

### Q1. Is looping over query results bad for the event loop?
> "It depends entirely on how many rows. Over 50 rows it's microseconds — completely irrelevant. Over five million it's about 200ms and freezes every other user.
>
> **But if I'm looping over five million rows in Node, the real bug is that I fetched five million rows.** Filtering, totalling and pagination belong in the database, where an index makes it about twenty operations instead of five million. It also avoids pulling all that data across the network into memory.
>
> **The one I'd watch for specifically is a nested loop** — ten thousand by ten thousand is a hundred million comparisons, and it looks fine in development with 200 seeded rows."

### Q2. If Node is single-threaded, how does it serve thousands of users?
> "Because those requests are almost entirely **waiting** — on the database, on the network — and waiting is handed off to the operating system, so it overlaps perfectly and costs the thread nothing. Three requests each waiting 50ms finish in 50ms total, not 150ms.
>
> **Only computing serializes.** Max throughput is roughly `1000ms ÷ computing-milliseconds per request`, and notice database time isn't in that formula — you could have a 500ms query and still serve a thousand requests a second.
>
> And in production it isn't one process anyway: `cluster` runs one per core behind a load balancer, across several servers."

### Q3. An endpoint takes 3 seconds of computation. What do you do?
> "Get it off the request path. Return `202 Accepted` with a job ID, push the work to a queue, and let a separate worker process do it — then notify by polling or a webhook.
>
> If it genuinely has to be synchronous, `worker_threads` keeps the main thread free. And if many users want the same result, cache it — then it's computed once per cache period instead of once per request.
>
> **What I wouldn't do is leave it in the handler and add more servers.** That doesn't fix it, it just spreads the damage."

### Q4. Does adding more servers fix a blocking endpoint?
> "No — it divides the damage. A 200ms block still freezes whichever process it lands on. With 24 processes, one in twenty-four users gets frozen instead of all of them.
>
> **That's tolerance, not a fix**, and you're paying for extra machines to hide a defect. The actual fix is moving the work to the database, a cache, or a queue."

### Q5. My API got slow under load. How do you start?
> "First I'd check **event loop lag**. If it's high, the problem is computing on the main thread, and it affects *every* endpoint. If lag is fine but one endpoint is slow, the problem is downstream — a database query or an external call.
>
> **That distinction matters because it tells you where to look.** High lag means look for a loop, a big `JSON.parse`, or a synchronous file read. Normal lag means look for a missing index, or an unbounded query that grew past the point where a full scan was survivable.
>
> I'd also check **p50 versus p99** — if p50 doubled, everything got slower, which is systemic. If only p99 moved, it's occasional: garbage collection, cache misses, or waiting for a free thread."

### Q6. Why is a blocked event loop worse than a crash?
> "Because a crash is visible and self-healing — the process restarts, the load balancer routes around it, and traffic moves on.
>
> **A blocked loop keeps the process 'up'.** The port is open, memory looks normal, CPU is just busy. Health checks may even pass, so the load balancer keeps sending traffic into a black hole. **It fails silently and takes every concurrent user with it.**"

<a name="cheatsheet"></a>
# 9. Cheat Sheet

### The three sentences
```
1. Looping 50 rows is FREE. Looping 5 million means you asked the database
   the wrong question.
2. WAITING overlaps and costs nothing. COMPUTING serializes and costs everyone.
3. requests/sec = 1000ms ÷ computing-ms per request
   ⭐ database and network time are NOT in that formula
```

### Loop size
```
  ≤ 10,000     😴 invisible
  ~ 100,000    ✅ 1-5ms, fine
  ~ 1,000,000  ⚠️ 10-50ms, hurting people
  ~ 10,000,000 ❌ 100-500ms, server-wide freeze
  NESTED       ☠️ 10k × 10k = 100 MILLION — looks fine on 200 dev rows
```

### Where work belongs
```
filter → WHERE        sort → ORDER BY + index     count/sum → COUNT()/SUM()
join   → JOIN         limit → LIMIT               group → GROUP BY
                      duplicates → DISTINCT

⭐ ALWAYS PAGINATE — the unbounded query is the real bug,
   the slow loop is only the symptom
```

### Waiting vs computing
```
3 requests × (5ms compute + 50ms wait) = ~60ms total
   → the waits happened AT THE SAME TIME

3 requests × 200ms compute = 600ms
   → user C waited 400ms doing nothing (head-of-line blocking)
   → and users on OTHER endpoints are frozen too
```

### Production reality
```
CDN → load balancer → N servers × M cores (cluster) → Redis → database

• more processes DIVIDE blocking damage, they don't fix it
• distance is a LATENCY problem → fixed by CDN + regions, not threads
• CACHE is what actually saves you (compute once, serve 10,000)
• servers must be STATELESS → sessions in Redis, not in memory
```

### The fix ladder
```
1. let the DATABASE do it (+ index)   ← 95% of cases
2. CACHE the result                    ← compute once, serve many
3. QUEUE it, return 202                ← exports, reports, emails
4. worker_threads                      ← must compute right now
5. chunk it + await setImmediate       ← must run in this process
6. STREAM it                           ← big files
```

### The health metric
```
EVENT LOOP LAG = how late a 0ms timer actually fires
   <10ms ✅ · 10-100ms 🟡 · >100ms ❌

⭐ a blocked loop looks HEALTHY on CPU and memory dashboards.
   The process is up, health checks may pass, and nothing works.
   Only lag reveals it.
```
