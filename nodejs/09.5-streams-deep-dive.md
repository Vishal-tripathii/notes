<a name="problem"></a>
# 1. The problem streams solve

You need to read a file and send it to a user. The obvious way:

```js
const data = await fs.readFile('video.mp4');   // read the whole file
res.send(data);                                 // send it
```

**This works fine until the file is big.** Here's what actually happens with a 2GB file:

```
1. Node reads all 2GB from disk
2. It puts all 2GB into memory, as one Buffer
3. Only THEN does your next line run
4. It sends all 2GB
```

Three separate things go wrong:

**① You used 2GB of memory** for one request. Ten users doing this at once needs 20GB, and your server has 8GB. It crashes.

**② The user waited for the entire read before receiving a single byte.** On a big file that's minutes of a blank screen.

**③ Above about 2GB it simply cannot work at all.** `readFile` puts everything into one Buffer, and a Buffer has a maximum size ([Part 5](05-buffers.md)). No configuration flag fixes this.

## The stream version

```js
fs.createReadStream('video.mp4').pipe(res);
```

```
Read 64KB → send it → read the next 64KB → send it → ...
```

**Memory used: about 64KB, no matter how big the file is.** The user starts receiving data immediately. And there's no size limit, because you never hold the whole thing.

> **Moving a shipment.** You don't lift the entire pallet — you put it on a conveyor belt and handle one box at a time. It doesn't matter whether the shipment is 10 boxes or 10,000; you're only ever holding one.

| | `readFile` | stream |
|---|---|---|
| Memory | as big as the file | **about 64KB, always** |
| User starts receiving | after the whole file is read | **immediately** |
| Maximum size | ~2GB (Buffer limit) | **no limit** |
| 10 users × 1GB file | 10GB 💥 | 640KB ✅ |

> **Honest exception:** for *small* files `readFile` is actually faster and simpler — there's less machinery involved. Streams win when files are large or when **you don't know how large they'll be.** That last case is the important one: if a user uploads the file, you don't control its size.

<a name="what"></a>
# 2. What a stream actually is

A stream is an object that **hands you data in pieces over time**, and tells you when things happen by emitting events.

Each piece is called a **chunk**. For file and network streams a chunk is a Buffer of raw bytes — usually 64KB.

```js
const stream = fs.createReadStream('big.txt');

stream.on('data',  chunk => console.log('got', chunk.length, 'bytes'));
stream.on('end',   ()    => console.log('no more data'));
stream.on('error', err   => console.error('something broke'));
```

**Streams are EventEmitters** — the same `.on()` pattern used everywhere in Node. That's *why* they don't use promises: a promise resolves **once**, but a stream produces **many** chunks. Promises are the wrong shape for something that happens repeatedly ([Part 4](04-modules.md)).

The events you'll actually use:

| Event | Means |
|---|---|
| `'data'` | here's a chunk |
| `'end'` | the source has no more data |
| `'finish'` | the destination has written everything |
| `'error'` | something failed |
| `'drain'` | the destination was full, and now has room again ⭐ |

That last one is §4, and it's the important one.

---

<a name="types"></a>
# 3. The four types

Streams are categorized by **which direction data moves**.

### Readable — data comes OUT of it
Something you read *from*. A source.
```js
fs.createReadStream('file.txt')     // a file you're reading
req                                  // an incoming HTTP request body
process.stdin                        // keyboard input
```

### Writable — data goes INTO it
Something you write *to*. A destination.
```js
fs.createWriteStream('out.txt')     // a file you're writing
res                                  // the HTTP response going to the user
process.stdout                       // the terminal
```

### Transform — data goes in, changed data comes out
Sits in the middle and modifies what passes through.
```js
zlib.createGzip()                    // bytes in → compressed bytes out
csvParser()                          // text in → objects out
```

### Duplex — reads and writes, but the two are unrelated
```js
net.Socket()                         // a network connection
```

## Duplex vs Transform — the one people mix up

Both do reading *and* writing. The difference is **whether the two sides are connected**:

- **Transform** — what comes out is **made from** what went in. You put text in, gzip gives you back *that same text*, compressed.
- **Duplex** — the two sides have **nothing to do with each other**. On a network socket, the messages you receive aren't derived from the messages you send. They're two independent pipes that happen to share one object.

**In practice you'll write Transforms constantly and Duplexes almost never.**

<a name="backpressure"></a>
# 4. ⭐ Backpressure — the whole point

This is the concept that makes streams actually work. Everything else is detail.

## The problem, concretely

You're reading a file from disk and sending it to a user over the internet:

```
Reading from disk:      500 MB per second   (fast)
Sending to the user:      5 MB per second   (slow — it's the internet)
```

**You're producing data 100× faster than you can get rid of it.** So where does the extra go?

```
   disk ──▶ 500 MB/s ──▶ [ pile up in memory ] ──▶ 5 MB/s ──▶ user
                                  ↑
                     this grows and grows and grows
```

After 10 seconds you've read 5GB and sent 50MB. **The other 4.95GB is sitting in your memory.**

> ⭐ **You have accidentally recreated `readFile`.** Same memory problem, more code. This is why "I used a stream" doesn't automatically mean "I fixed the memory problem."

## The solution

**Backpressure is the slow side telling the fast side to wait.**

> **Filling a bucket from a tap.** If water comes in faster than you can empty the bucket, it overflows. So you watch the level, and when it gets high you **turn the tap down**. When there's room again, you turn it back up. Backpressure is that feedback.

The mechanism in Node:

```
1. The reader sends a chunk to the writer.
2. The writer stores it in a small internal buffer.
3. When that buffer is full, write() returns FALSE
                                        ↑ "stop, I'm full"
4. The reader pauses.
5. The writer works through its buffer.
6. When there's room, the writer emits 'drain'
                                        ↑ "ok, ready again"
7. The reader resumes.
```

## In code

```js
// ❌ BROKEN — this ignores the "I'm full" signal entirely
source.on('data', chunk => {
  dest.write(chunk);          // write() returns false sometimes. We never check.
});
// memory grows without limit

// ✅ CORRECT — but you'd never actually write this by hand
source.on('data', chunk => {
  if (!dest.write(chunk)) {              // full?
    source.pause();                      // stop reading
    dest.once('drain', () => source.resume());   // resume when there's room
  }
});

// ✅✅ WHAT YOU ACTUALLY WRITE — pipe/pipeline do all of the above for you
await pipeline(source, dest);
```

> ⭐ **This is the single most important thing about streams: `.pipe()` and `pipeline()` handle backpressure automatically. That is their entire reason for existing.**
>
> **The corollary: if you're calling `.write()` in a loop yourself, you have opted out of backpressure** and your memory will grow. Almost every "my streaming code still ran out of memory" bug is this.

**See it happen:** run [`work/streams.js`](../work/streams.js) section 3. A producer that could generate instantly is throttled to a consumer taking 40ms per item — it produces a handful, stops on its own, and only continues once the consumer catches up.

<a name="hwm"></a>
# 5. HighWaterMark — how full is "full"?

In §4, the writer said "I'm full" at some point. **`highWaterMark` is the setting that decides when.**

It's the size of that internal buffer:

```
default:  64 KB      for normal (byte) streams
          16 items   for object mode (see §8)
```

```
 ┌──────────── internal buffer ────────────┐
 │████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│  below the mark → keep going
 └─────────────────────────────────────────┘

 ┌──────────── internal buffer ────────────┐
 │█████████████████████████████████████████│  at the mark → write() returns false
 └─────────────────────────────────────────┘
```

**It's a tuning dial, not a safety limit:**
- **Smaller** → less memory held, but you stop and start more often, so more overhead
- **Larger** → fewer interruptions, but more memory held, and you react to a slow consumer later

```js
fs.createReadStream(file, { highWaterMark: 256 * 1024 });   // read 256KB at a time
```

> **Leave it alone unless you've measured.** In [`work/streams.js`](../work/streams.js) section 4, three different values give nearly identical times — because the *consumer* was the bottleneck, not the buffer. **Changing `highWaterMark` only helps if buffering is genuinely your problem**, which it usually isn't.
>
> The real exception is object mode, where the default "16 items" means nothing until you know whether an item is 100 bytes or a megabyte.

<a name="writing"></a>
# 6. Writing your own

Node gives you base classes. You fill in one method, and Node handles the rest.

## Readable — you implement `_read()`

**`_read()` means "the consumer wants more data — give it some."**

```js
class Counter extends Readable {
  constructor(max) {
    super({ objectMode: true });
    this.i = 0;
    this.max = max;
  }

  _read() {                                 // Node calls this when it wants data
    if (this.i >= this.max) {
      return this.push(null);               // ⭐ null means "that's everything"
    }
    this.push({ id: this.i++ });            // hand over one piece
  }
}
```

Two rules:
- **`push(chunk)`** sends a piece downstream.
- **`push(null)`** ends the stream. Forget this and your stream never finishes.

**Backpressure from this side:** `push()` returns `false` when the buffer is full. Node then simply stops calling `_read()` until there's room — so if you only push inside `_read()`, you get backpressure for free.

## Writable — you implement `_write()`

**`_write()` means "here's a piece, deal with it, and tell me when you're ready for the next one."**

```js
class DbWriter extends Writable {
  constructor() {
    super({ objectMode: true });
    this.batch = [];
  }

  async _write(row, encoding, callback) {
    this.batch.push(row);

    if (this.batch.length >= 1000) {
      await db.insertMany(this.batch);      // takes 200ms
      this.batch = [];
    }

    callback();          // ⭐ "done — send me the next one"
  }

  async _final(callback) {                  // called once, at the very end
    if (this.batch.length) await db.insertMany(this.batch);
    callback();
  }
}
```

> ⭐ **`callback()` is the backpressure lever, and this is the cleverest thing about streams.**
>
> Node will not send another chunk until you call `callback()`. So when you `await` a 200ms database insert *before* calling it, **everything upstream automatically pauses for 200ms** — the file read slows down to match your database speed.
>
> **You get perfect flow control without writing a single line of flow-control code.** You just… don't call back until you're ready.

`_final()` runs once when the source is finished — that's where you flush the last partial batch, or you'd silently lose up to 999 rows.

## Transform — you implement `_transform()`

**"Here's a piece; give me back the changed version."**

```js
class Upper extends Transform {
  _transform(chunk, encoding, callback) {
    callback(null, chunk.toString().toUpperCase());
    //       ↑ error (none)   ↑ the transformed chunk
  }

  _flush(callback) {          // called at the end — emit anything you're holding
    callback();
  }
}
```

**`_flush()` matters whenever your transform holds state between chunks** — like a line splitter sitting on half a line (§10). Without it, that leftover is lost.

<a name="pipeline"></a>
# 7. pipeline vs pipe

Both connect streams together. **Use `pipeline`.** Here's why:

```js
source.pipe(gzip).pipe(dest);        // ❌
await pipeline(source, gzip, dest);  // ✅
```

**The problem with `.pipe()`:** if `gzip` fails halfway, `source` and `dest` are **left open**. The file handles stay allocated, and nothing tells you. Do that a few thousand times and the process runs out of file descriptors and dies for a reason that looks unrelated.

`.pipe()` also doesn't pass errors along, so you need an `.on('error')` handler on **every stream in the chain** or a failure becomes an unhandled crash.

**`pipeline` does three things `.pipe()` doesn't:**
1. Passes errors from any stream in the chain to one place
2. **Closes every stream** when something fails
3. Returns a promise, so `await` and `try/catch` work normally

```js
const { pipeline } = require('stream/promises');

try {
  await pipeline(source, gzip, dest);
} catch (err) {
  // any stream failing lands here, and everything is already cleaned up
}
```

**See it:** [`work/streams.js`](../work/streams.js) section 5 makes a middle stream fail both ways and prints whether the other streams were closed. With `.pipe()` they aren't.

## A related gotcha: 'data' starts the flow

```js
stream.on('data', chunk => console.log('saw a chunk'));   // ⚠️
```

**Attaching a `'data'` listener immediately starts the stream flowing**, whether or not anything is ready to consume it. Adding one "just to log something" can cause data to be pulled and dropped before the real consumer is attached. Read with `pipeline` or `for await` instead (§9).

<a name="objectmode"></a>
# 8. Object mode

By default streams carry **Buffers** — raw bytes. `objectMode: true` lets them carry **anything**: objects, arrays, numbers.

```js
new Transform({ objectMode: true });          // objects in AND out
new Transform({ readableObjectMode: true });  // bytes IN, objects OUT ⭐
```

That second one is exactly what a parser is: **bytes come in, structured rows come out.** You'll use it whenever you build a CSV or JSON parser.

In object mode `highWaterMark` counts **items**, not bytes — the default is 16.

<a name="asynciter"></a>
# 9. Async iterators — the easy way

You can loop over a stream with a normal `for` loop:

```js
for await (const chunk of readable) {
  await saveToDatabase(chunk);       // takes 100ms
}
```

**And you get backpressure automatically**, because the loop can't start the next iteration until this one finishes — so the stream simply waits for you.

**This is usually the clearest option** when you're consuming a stream and doing something per chunk:
- no events to wire up
- `try/catch` works normally
- `await` works normally
- the pacing is obvious from reading the code

Use `pipeline` when you're **connecting** streams together, and `for await` when you're **consuming** one.

There's also a way to *build* a stream from a generator, which is the cleanest way to turn a database cursor or paginated API into a stream:

```js
const rows = Readable.from(async function* () {
  for await (const doc of db.collection.find().stream()) yield doc;
}());
```

<a name="csv"></a>
# 10. ⭐ Design: processing a 10GB CSV

A classic interview question. Structure the answer: **constraints → the pipeline → the hard parts → operations.**

## ① State the constraints first

> "10GB won't fit in memory, and it's over the Buffer limit anyway, so `readFile` isn't just slow — it can't work at all. Memory has to stay flat regardless of file size. And the database will be slower than reading from disk, so **backpressure is the central design concern, not an optimization.**"

## ② The pipeline

```js
await pipeline(
  fs.createReadStream('10gb.csv'),   // 1. raw bytes, 64KB at a time
  new LineSplitter(),                 // 2. bytes → complete lines
  new CsvParser(),                    // 3. lines → objects
  new Validator(),                    // 4. drop or quarantine bad rows
  new BatchInserter(1000),            // 5. objects → database, 1000 at a time
);
```

**Memory stays at a few MB throughout** — the same code handles 10MB or 10TB.

## ③ The hard part nobody mentions: chunks don't respect lines ⭐

A 64KB read stops after 64KB. It has **no idea where your lines end**:

```
chunk 1 ends with:    1,Ada,NYC\n2,Joh
chunk 2 starts with:  n,LA\n3,Cy,SF\n
                       ↑ "Joh" and "n,LA" are the SAME ROW, split in half
```

If you split each chunk on `\n` independently, you get a broken row **at every chunk boundary**. A 10GB file has about 160,000 chunks — so **160,000 silently corrupted rows**, with no error anywhere.

**The fix: hold onto the incomplete last piece until the next chunk arrives.**

```js
class LineSplitter extends Transform {
  constructor() {
    super({ readableObjectMode: true });
    this.leftover = '';                       // the half-line from last time
  }

  _transform(chunk, encoding, callback) {
    const lines = (this.leftover + chunk).split('\n');
    this.leftover = lines.pop();              // ⭐ the last one may be incomplete
    for (const line of lines) this.push(line);  // these are all complete
    callback();
  }

  _flush(callback) {                          // ⭐ the file's last line has no \n
    if (this.leftover) this.push(this.leftover);
    callback();
  }
}
```

> **Raising this before you're asked is what shows you've actually done it.** The same problem hits multi-byte characters — a 3-byte `中` can be split across two chunks, and `StringDecoder` solves that one ([Part 5 §4](05-buffers.md)).

## ④ Batching — and backpressure for free

```js
class BatchInserter extends Writable {
  constructor(size) {
    super({ objectMode: true });
    this.size = size;
    this.batch = [];
  }

  async _write(row, encoding, callback) {
    this.batch.push(row);
    if (this.batch.length >= this.size) {
      await db.insertMany(this.batch);   // one trip for 1000 rows
      this.batch = [];
    }
    callback();                          // ⭐ delayed → the file read pauses
  }

  async _final(callback) {
    if (this.batch.length) await db.insertMany(this.batch);   // the remainder
    callback();
  }
}
```

**Ten million individual inserts would take hours. Batches of 1,000 take minutes.** And because `callback()` waits for the insert, **the disk read automatically slows to database speed** — no flow-control code required.

## ⑤ Resumability — the requirement they hope you raise

> "A 10GB job runs long enough that it **will** be interrupted — a deploy, a crash, a network blip. Starting over from zero isn't acceptable, so I'd:
> - record the **byte offset** after each successful batch
> - on restart, `createReadStream(file, { start: lastOffset })` to resume from there
> - make inserts **idempotent** — an upsert or a unique key — so a replayed batch can't create duplicates ([Part 11](11-api-design.md))"

## ⑥ Error policy — a product decision, so say it out loud

> "Does one malformed row on line 4 million kill the whole job, or get set aside? Usually set aside — write bad rows to a separate file with line numbers, count them, and abort only past a threshold, since 50% bad rows probably means the wrong file was uploaded. **A 10GB job that dies on the last row because of one stray quote is a bad design.**"

## ⑦ Operations

> - **Progress reporting** — bytes done ÷ total. A 40-minute job with no output is indistinguishable from a hung one.
> - **Not in a request handler.** This is a background job; the HTTP call returns `202 Accepted` with a job ID ([Part 1.2](01.2-event-loop-blocking-and-real-world-load.md)).
> - **Compressed input** — add `zlib.createGunzip()` as step two. A 10GB CSV is usually shipped as a 1GB `.gz`.
> - **If parsing is the bottleneck**, that's CPU work on the main thread — move the job to its own process or a worker ([Part 2](02-nodejs-internals.md)).

## ⑧ Name the trade-offs
> "Bigger batches are faster but lose more work when one fails and hold more rows in memory. Running multiple workers in parallel multiplies throughput but makes resumability much harder. **I'd start sequential, measure, and only add parallelism if the numbers demand it.**"

<a name="interview"></a>
# 11. Interview Questions & Answers

### Q1. Why do streams outperform `readFile()`?
> "**Memory is the headline — it stays flat instead of matching the file size.** But there are four more reasons.
>
> **Time to first byte:** a stream sends the first chunk immediately, while `readFile` waits until the entire file is in memory before your code runs at all. On a large file that's minutes of nothing.
>
> **A hard size limit:** `readFile` puts everything in one Buffer, and Buffers max out around 2GB. Past that it simply cannot work — no flag helps.
>
> **Concurrency:** ten users downloading a 1GB file is 10GB of memory with `readFile` and about 640KB with streams. That's the difference between a server that works and one that crashes.
>
> **Garbage collection:** huge buffers make GC pauses longer, so `readFile` hurts latency for every other request too ([Part 2.8](02.8-memory-management.md)).
>
> **The honest caveat:** for small files `readFile` is faster and simpler. Streams win when the size is large or **unknown** — and if a user is uploading the file, it's always unknown."

### Q2. What is backpressure?
> "It's flow control between a fast producer and a slow consumer. If you read from disk at 500MB/s and send to a user at 5MB/s, that difference has to go somewhere — and without coordination it piles up in memory until you've buffered the whole file. **Which means you've accidentally recreated `readFile`, just with more code.**
>
> **Mechanically:** the destination's `write()` returns `false` once its buffer hits the `highWaterMark`. The source pauses, and resumes when the destination emits `'drain'`.
>
> **`.pipe()` and `pipeline()` do all of that automatically — it's their whole purpose.** The only way to lose it is to call `.write()` yourself in a loop and ignore the return value, which is where almost every 'my streaming code still ran out of memory' bug comes from.
>
> **The most elegant version is on the writing side:** in a Writable you control backpressure by simply not calling `callback()` until you're ready. So a batch inserter that awaits a database write automatically slows the file read to database speed — perfect flow control, and you never wrote any flow-control code."

### Q3. Design a CSV processor handling 10GB files.
See §10 — constraints → pipeline → chunk boundaries → batching → resumability → error policy → operations → trade-offs.

### Q4. Why use `pipeline()` instead of `.pipe()`?
> "Three reasons. **`.pipe()` doesn't clean up** — if a stream in the middle fails, the ones on either side stay open, leaking file descriptors until the process dies for a reason that looks unrelated. **It doesn't pass errors along**, so you need a handler on every stream or a failure becomes an unhandled crash. And **`pipeline` returns a promise**, so `await` and `try/catch` work normally. There's no situation where `.pipe()` is the better choice in modern code."

### Q5. Duplex vs Transform?
> "Both read and write; the difference is whether the two sides are connected. In a **Transform**, the output is **made from** the input — gzip gives you back the same data, compressed. In a **Duplex**, the two sides are unrelated — a network socket, where what you receive has nothing to do with what you send. **You'll write Transforms all the time and Duplexes almost never.**"

### Q6. What does `highWaterMark` do?
> "It sets how much a stream buffers before signalling backpressure — 64KB by default, or 16 items in object mode. **It's a tuning dial, not a safety limit.** Smaller means less memory but more stop-start overhead; larger means fewer interruptions but more memory held and a slower reaction to a slow consumer.
>
> I leave it at the default unless I've measured, because **it only helps if buffering is actually the bottleneck**, which it usually isn't — normally the consumer is. The real exception is object mode, where '16 items' is meaningless until you know if an item is 100 bytes or a megabyte."

### Q7. Can you use `async/await` with streams?
> "Yes, and it's usually the clearest option. `for await (const chunk of readable)` loops over a stream with **automatic backpressure**, because the next iteration can't start until the current one finishes — so the stream waits for you. No event wiring, and `try/catch` works normally.
>
> `pipeline` from `stream/promises` is awaitable too. And `Readable.from()` builds a stream out of an async generator, which is the cleanest way to turn a database cursor or a paginated API into a stream.
>
> **Rule of thumb: `pipeline` to connect streams, `for await` to consume one.**"

<a name="cheatsheet"></a>
# 12. Cheat Sheet

### Why streams
```
readFile 2GB → 2GB in memory · user waits for ALL of it · dies above ~2GB
stream   2GB → ~64KB in memory · user gets byte 1 immediately · no size limit

10 users × 1GB file:  readFile 10GB 💥  ·  streams 640KB ✅
small files? readFile is fine. Unknown/user-supplied size? ALWAYS stream.
```

### The four types
```
Readable   data comes OUT   (file read, http request, stdin)
Writable   data goes IN     (file write, http response, stdout)
Transform  in → CHANGED out (gzip, a parser)      ← you'll write these
Duplex     both, UNRELATED  (a network socket)    ← you rarely write these

streams are EventEmitters (many chunks) — that's why they aren't promises
'data' · 'end' · 'finish' · 'error' · 'drain'(= room again) ⭐
```

### Backpressure ⭐ (the whole point)
```
disk 500MB/s ──▶ [ piles up in memory ] ──▶ user 5MB/s
⭐ ignore this and you've RECREATED readFile, with more code

HOW: write() returns FALSE at the highWaterMark → source pauses
     → destination empties → emits 'drain' → source resumes

⭐ .pipe() and pipeline() DO THIS FOR YOU — it is their entire purpose
⚠️ calling .write() yourself in a loop = opting OUT of backpressure
   (this is the #1 cause of "my stream still ran out of memory")
```

### Writing your own
```js
Readable   _read()               push(chunk) · push(null) ENDS IT
Writable   _write(c, enc, cb)    ⭐ cb() = "send me the next one"
                                    DELAY cb() = upstream pauses = free flow control
           _final(cb)            runs once at the end — flush the last batch!
Transform  _transform(c,e,cb)    cb(null, changedChunk)
           _flush(cb)            REQUIRED if you hold state between chunks
Readable.from(asyncGenerator)    build a stream from a generator/cursor
```

### highWaterMark
```
64KB byte streams · 16 items object mode
smaller → less memory, more stop-start · larger → more memory, slower reaction
⭐ a DIAL, not a limit. Only helps if BUFFERING is the bottleneck (it rarely is).
```

### pipeline > pipe
```
.pipe()    ❌ leaves other streams OPEN on failure (fd leak)
           ❌ no error propagation (needs .on('error') on every stream)
pipeline() ✅ errors in one place · closes everything · returns a promise

⚠️ attaching .on('data') STARTS the flow immediately — can drop data
   use pipeline (to connect) or for await (to consume)
```

### 10GB CSV ⭐
```
read → LineSplitter → CsvParser → Validator → BatchInserter(1000)

⭐ CHUNK BOUNDARIES: a 64KB read does NOT stop at a newline
   "1,Ada,NYC\n2,Joh" | "n,LA\n" ← one row split in half
   naive splitting = ~160,000 SILENTLY corrupted rows in a 10GB file
   FIX: keep `leftover` in _transform, emit it in _flush

⭐ BATCHING gives backpressure free — awaiting the insert before cb()
   throttles the file read to database speed

RESUMABLE: save the byte offset · createReadStream(f, {start}) · idempotent inserts
ERRORS:    quarantine bad rows to a file, abort past a threshold
OPS:       progress % · background job (202 + jobId) · gunzip stage · worker if CPU-bound
```
