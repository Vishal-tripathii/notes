# 1. EventEmitter — what it is

> **Analogy 🔔 — a doorbell.** You wire up what should happen when the bell rings (`on`). Someone presses the bell (`emit`). Everything wired to it runs. The bell doesn't know or care who is listening.

```js
const { EventEmitter } = require('events');

const shop = new EventEmitter();

shop.on('order', (item) => console.log('kitchen: cooking', item));
shop.on('order', (item) => console.log('billing: charging for', item));

shop.emit('order', 'pizza');
// kitchen: cooking pizza
// billing: charging for pizza
```

The idea is called the **observer pattern**: one thing announces "this happened," and any number of listeners react — without the announcer knowing who they are.

**Where you already use it:** `http.Server` (`'request'`), every stream (`'data'`, `'end'`, `'error'`), sockets, `process` (`'SIGTERM'`, `'exit'`), Mongoose connections (`'connected'`), Socket.IO.

**Making your own class an emitter:**

```js
class Order extends EventEmitter {
  pay() {
    // ...charge the card...
    this.emit('paid', { id: this.id });
  }
}
```

> 🧠 **Remember:** `on` = "when this happens, do that." `emit` = "this happened."

<a name="emit"></a>
# 2. The rules of `emit()`

**Rule 1 — `emit()` is synchronous.** It runs every listener **right now**, one after another, before `emit()` returns. This surprises people who assume events are async.

```js
shop.on('order', () => console.log('B: listener'));
console.log('A: before emit');
shop.emit('order');
console.log('C: after emit');
// A, B, C — the listener ran INSIDE emit()
```

So a slow listener blocks whoever called `emit()` — and the whole event loop.

**Rule 2 — listeners run in the order they were added.** (`prependListener()` puts one at the front.)

**Rule 3 — the useful methods:**

| Method | Does |
|---|---|
| `on(name, fn)` | listen every time |
| `once(name, fn)` | listen one time, then remove itself |
| `off(name, fn)` / `removeListener` | stop listening (you need the **same function reference**) |
| `emit(name, ...args)` | run all listeners; returns `true` if there were any |
| `listenerCount(name)` | how many are listening — handy when hunting leaks |

**Rule 4 — an `async` listener's errors are not caught by `emit()`.** `emit()` doesn't wait for promises. If an async listener throws, it becomes an **unhandled rejection** (§8). Catch inside the listener, or create the emitter with `new EventEmitter({ captureRejections: true })` so rejections are routed to the `'error'` event.

<a name="error-event"></a>
# 3. The `'error'` event — the one that crashes you

`'error'` is special. **If you emit `'error'` and nobody is listening, Node throws it — and an uncaught throw crashes the process.**

```js
const e = new EventEmitter();
e.emit('error', new Error('boom'));   // 💥 no listener → thrown → process crashes
```

This is why an unhandled stream error, socket error, or database-connection error can take down your whole server.

> 🧠 **Remember:** **every emitter you create or receive needs an `'error'` listener** — streams, sockets, child processes, DB clients. (`stream.pipeline()` attaches them for you — [Part 9.5 §7](09.5-streams-deep-dive.md).)

```js
db.on('error', (err) => logger.error({ err }, 'db connection error'));
```

<a name="leaks"></a>
# 4. Listener leaks & the "max listeners" warning

Every `on()` keeps a reference to the listener — and to everything the listener's closure can see. Add a listener **per request** to a long-lived emitter and never remove it, and memory grows forever ([Part 2.8 §5](02.8-memory-management.md)).

```js
// ❌ a new listener on a global emitter for every request — never removed
app.get('/live', (req, res) => {
  bus.on('update', (data) => res.write(JSON.stringify(data)));
});

// ✅ remove it when the client goes away
app.get('/live', (req, res) => {
  const send = (data) => res.write(JSON.stringify(data));
  bus.on('update', send);
  req.on('close', () => bus.off('update', send));
});
```

**`MaxListenersExceededWarning`:** Node prints this when one event gets more than **10** listeners. It's not an error and nothing stops working — it's a **smoke alarm** saying "you're probably adding listeners in a loop." Find the leak first; only raise the limit (`emitter.setMaxListeners(50)`) if the number is genuinely intentional.

<a name="promises"></a>
# 5. EventEmitter with promises

Two helpers from the `events` module turn events into promise-friendly code:

```js
const { once, on } = require('events');

// wait for ONE event, as a promise
await once(server, 'listening');
const [msg] = await once(socket, 'message');   // resolves with the event's arguments (an array)
// if the emitter emits 'error' first, the promise rejects ✅

// loop over MANY events
for await (const [msg] of on(socket, 'message')) {
  handle(msg);
}
```

Both accept an `AbortSignal` (`{ signal }`) so you can stop waiting — useful for timeouts ([Part 6.5 §5](06.5-production-http-timeouts-keepalive-caching.md)).

**EventEmitter vs a promise:** a promise is for **one** result. An emitter is for **many** things over time (chunks, messages, connections). That's why streams are emitters, not promises.

<a name="process"></a>
# 6. The `process` object

`process` is a global object that describes **the running program** and lets it talk to the operating system. It's also an EventEmitter.

| You want | Use |
|---|---|
| config & secrets | `process.env.DATABASE_URL` — ⚠️ **always strings** ([Part 4.5 §5](04.5-npm-packages-and-configuration.md)) |
| command-line args | `process.argv` — `[node path, script path, ...your args]` |
| the folder you ran `node` from | `process.cwd()` — not the same as `__dirname` ([Part 5.5 §4](05.5-file-system-and-paths.md)) |
| memory numbers | `process.memoryUsage()` — `rss`, `heapUsed`, `external` |
| precise timing | `process.hrtime.bigint()` (nanoseconds) or `performance.now()` |
| how long it's been running | `process.uptime()` |
| process id | `process.pid` |
| platform | `process.platform` (`'linux'`, `'win32'`...) |
| Node version | `process.version` |

<a name="exit"></a>
# 7. Exit codes & signals

## Exit codes — how a process says how it ended

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | general failure (uncaught exception, `process.exit(1)`) |
| `137` | killed by `SIGKILL` (128 + 9) — in containers this almost always means **OOMKilled** ([Part 2.8 §4](02.8-memory-management.md)) |
| `143` | stopped by `SIGTERM` (128 + 15) — normal during a deploy |

**Prefer `process.exitCode = 1` over `process.exit(1)`.** `process.exit()` stops **immediately** — pending log writes and in-flight work are thrown away. Setting `exitCode` lets Node finish what's queued and then exit with that code.

## Signals — how the OS talks to your process

| Signal | Sent when | Can you handle it? |
|---|---|---|
| `SIGINT` | you press Ctrl+C | ✅ |
| `SIGTERM` | Docker/Kubernetes/PM2 asks you to stop | ✅ — this is where graceful shutdown starts ([Part 6.6](06.6-graceful-shutdown-health-checks-and-docker.md)) |
| `SIGKILL` | the OS force-kills you (or the stop timeout ran out) | ❌ never — you're just gone |

```js
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));
```

> 🧠 **Remember:** SIGTERM = "please leave." SIGKILL = "you're removed." You only get to clean up after the first one.

<a name="crash"></a>
# 8. ⭐ Crashes: `uncaughtException` & `unhandledRejection`

## What they are

- **`uncaughtException`** — a `throw` that nothing caught. It bubbled all the way up.
- **`unhandledRejection`** — a promise rejected and nothing had `.catch()` or `await` + `try/catch` on it.

**Since Node 15, an unhandled rejection crashes the process by default**, exactly like an uncaught exception. (Before that it was only a warning — a lot of old blog posts still say so.)

## What to do in the handlers

> **Analogy ✈️ — an engine fire.** The pilot doesn't keep flying to the destination. They land at the nearest airport. Your handler's job is the same: **log what happened, then land (exit).** Your process manager (PM2, Docker, Kubernetes) takes off again with a fresh plane.

```js
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception — exiting');
  process.exit(1);                          // don't keep running
});

process.on('unhandledRejection', (reason) => {
  logger.fatal({ reason }, 'unhandled rejection — exiting');
  process.exit(1);
});
```

**Why not just log and carry on?** After an unexpected error you no longer know what state the app is in — a half-finished write, a lock never released, a counter never decremented, a connection left open. Carrying on means serving requests from a **possibly corrupted** process. Crashing and restarting gives you a known-good state in a second or two.

What to avoid:
- ❌ `process.on('uncaughtException', () => {})` — swallowing everything. Bugs become invisible and the process slowly rots.
- ❌ Relying on these handlers for normal error handling. They're the **last** safety net. Normal errors should be caught where they happen (Express error middleware, `try/catch`).
- ✅ Run more than one instance so a crash-and-restart doesn't mean downtime.

<a name="design"></a>
# 9. ⭐ Error design: expected errors vs bugs

Split every error into one of two kinds. It decides what you do with it.

| | **Operational error** (expected) | **Programmer error** (a bug) |
|---|---|---|
| Examples | user not found, invalid input, payment declined, DB timeout, third-party API down | `undefined is not a function`, wrong argument type, forgot `await` |
| Can you predict it? | yes — it *will* happen in normal life | no — it shouldn't happen at all |
| What to do | handle it: return a 4xx/5xx, retry, fall back | **fix the code**; in production, let it crash and restart |

### Use your own error classes

```js
class AppError extends Error {
  constructor(message, { status = 500, code = 'INTERNAL', cause } = {}) {
    super(message, { cause });             // `cause` keeps the original error attached (ES2022)
    this.name = this.constructor.name;
    this.status = status;
    this.code = code;                      // stable, machine-readable: clients switch on this
  }
}
class NotFoundError extends AppError {
  constructor(what) { super(`${what} not found`, { status: 404, code: 'NOT_FOUND' }); }
}

// use
const user = await User.findById(id);
if (!user) throw new NotFoundError('User');

try { await payments.charge(card); }
catch (err) { throw new AppError('Payment failed', { status: 502, code: 'PAYMENT_FAILED', cause: err }); }
```

### One place turns errors into responses

```js
app.use((err, req, res, next) => {
  const known = err instanceof AppError;
  if (!known) logger.error({ err, reqId: req.id }, 'unexpected error');   // a bug → log loudly
  res.status(known ? err.status : 500).json({
    error: { code: known ? err.code : 'INTERNAL', message: known ? err.message : 'Something went wrong' }
  });
});
```

Rules that keep this clean:
- **Always throw `Error` objects**, never strings (`throw 'oops'` has no stack trace).
- **Never send stack traces or raw DB errors to clients** — they leak internals.
- **Wrap, don't lose:** when you re-throw, pass `{ cause: err }` so the real reason stays in the logs.
- Give clients a stable `code` (`NOT_FOUND`, `VALIDATION_FAILED`), not just a message that might change. ([Part 11 §7](11-api-design.md) — error contracts.)

<a name="interview"></a>
# 10. Interview Questions & Answers

### Q1. Is `emit()` synchronous or asynchronous?
> "Synchronous. It calls every listener right away, in the order they were added, before it returns. So a slow listener blocks the caller and the event loop. If I want a listener's work to happen later, the listener itself has to schedule it with `setImmediate` or a promise."

### Q2. What happens if an EventEmitter emits `'error'` with no listener?
> "Node throws the error, and if nothing catches it the process crashes. That's why every stream, socket and DB client needs an `'error'` listener — or, for streams, `pipeline()`, which handles it for you."

### Q3. What does the `MaxListenersExceededWarning` mean?
> "More than 10 listeners on one event. It's a leak detector, not an error — usually someone adds a listener per request and never removes it. I'd find and fix the leak; raising the limit is only right if the listeners are genuinely meant to be there."

### Q4. What should you do in an `uncaughtException` handler?
> "Log it with as much context as possible and exit with a non-zero code. After an unexpected error the process is in an unknown state, so continuing risks corrupted data. A process manager restarts it, and running several instances means users don't notice."

### Q5. What happens to an unhandled promise rejection?
> "Since Node 15, it crashes the process by default, same as an uncaught exception. Before that it was only a warning. The fix is to always `await` inside `try/catch`, or attach `.catch()`, on every promise — and keep a top-level handler that logs and exits as a last resort."

### Q6. Operational errors vs programmer errors?
> "Operational errors are expected events in a working system — invalid input, not found, a timeout from another service. I handle them: return the right status, retry, or fall back. Programmer errors are bugs — calling something undefined, a wrong type. You can't handle a bug at runtime; you fix the code, and in production you let the process crash and restart rather than continue in an unknown state."

### Q7. `process.exit()` vs `process.exitCode`?
> "`process.exit()` stops immediately and drops anything pending — unflushed logs, in-flight writes. Setting `process.exitCode` just records the code, and Node exits with it once the event loop is empty. I use `exitCode` unless I truly need to stop right now."

### Q8. What do exit codes 137 and 143 mean?
> "128 plus the signal number. 143 is SIGTERM — a normal stop, for example during a deploy. 137 is SIGKILL — in a container that usually means the memory limit was hit and the container was OOM-killed."

<a name="cheatsheet"></a>
# 11. Cheat Sheet

### EventEmitter
```
on = listen always · once = listen once · off = stop (same fn reference) · emit = fire
emit() is SYNCHRONOUS — listeners run inside it, in order
'error' with no listener → THROWS → crash   ← always add an 'error' listener
> 10 listeners → warning = probably a leak
async listener errors aren't caught by emit → captureRejections or try/catch inside
events.once(e, 'x') → promise · events.on(e, 'x') → for await loop
```

### process
```
env (strings!) · argv · cwd() · memoryUsage() · hrtime.bigint() · pid · uptime()
exit codes: 0 ok · 1 failure · 137 SIGKILL (OOMKilled) · 143 SIGTERM
SIGTERM / SIGINT → you can clean up · SIGKILL → you can't
prefer process.exitCode = 1 over process.exit(1)
```

### Crashes
```
uncaughtException / unhandledRejection (crashes by default since Node 15)
handler = LOG + EXIT(1). Never swallow. Let the supervisor restart.
"Engine fire → land the plane, don't keep flying."
```

### Error design
```
operational (expected) → handle: 4xx/5xx, retry, fallback
programmer (bug)       → fix the code; in prod crash + restart
own classes: AppError { status, code, cause } · throw Error objects, never strings
one error middleware maps errors → responses · no stack traces to clients
```
