<a name="multipart"></a>
# 1. How a file arrives: `multipart/form-data`

A JSON body can't carry a file efficiently. Browsers send files as **`multipart/form-data`**: the body is split into parts, one per form field, separated by a random "boundary" string.

```
POST /avatar
Content-Type: multipart/form-data; boundary=----X42

------X42
Content-Disposition: form-data; name="userId"

17
------X42
Content-Disposition: form-data; name="photo"; filename="me.jpg"
Content-Type: image/jpeg

<raw bytes of the image>
------X42--
```

`express.json()` does **not** read this. You need a multipart parser — `multer` (built on `busboy`) is the usual choice.

---

<a name="multer"></a>
# 2. `multer` — the standard middleware

```js
import multer from 'multer';

const upload = multer({
  storage: multer.memoryStorage(),               // or diskStorage — see §3
  limits: { fileSize: 5 * 1024 * 1024, files: 1 },   // 5 MB, one file — ALWAYS set limits
  fileFilter: (req, file, cb) => {
    const ok = ['image/jpeg', 'image/png', 'image/webp'].includes(file.mimetype);
    cb(ok ? null : new AppError('Only JPEG, PNG or WebP', { status: 415, code: 'BAD_FILE_TYPE' }), ok);
  },
});

app.post('/avatar', upload.single('photo'), async (req, res) => {
  // req.file  → { originalname, mimetype, size, buffer (memory) or path (disk) }
  // req.body  → the other text fields (userId...)
  const key = await saveToStorage(req.file);
  res.status(201).json({ key });
});
```

- `upload.single('photo')` — one file. `upload.array('photos', 5)` — up to 5. `upload.fields([...])` — several named fields.
- A file over `fileSize` → multer raises `LIMIT_FILE_SIZE` → your error middleware should turn it into `413 Payload Too Large`.

<a name="storage"></a>
# 3. ⭐ Memory vs disk vs streaming

| Storage | How it works | Problem |
|---|---|---|
| `memoryStorage()` | the whole file is held in a Buffer in RAM | 20 users × 50 MB = 1 GB of memory → OOM. OK only for **small** files with a **strict** size limit |
| `diskStorage()` | written to the server's local disk | local disk **isn't shared** between instances, often vanishes when a container restarts, and fills up. Fine as a temporary step, not as the final home |
| **stream onward** | pipe the incoming bytes straight to S3/GCS while they arrive | constant memory, any size — but more code |

**Where files should end up:** **object storage** (S3, Google Cloud Storage, Azure Blob) — shared by every instance, practically unlimited, cheap, and can be served through a CDN. Store only the **key and metadata** (owner, size, type, original name) in your database.

```js
// streaming to S3 with the AWS SDK's multipart Upload helper (works with a stream body)
import { Upload } from '@aws-sdk/lib-storage';
await new Upload({ client: s3, params: { Bucket, Key: key, Body: fileStream, ContentType } }).done();
```

<a name="presigned"></a>
# 4. ⭐ The best way: upload straight to S3 with a pre-signed URL

Why make the file travel through your Node server at all? Let the browser send it **directly** to storage.

> **Analogy 🎟️ — a parking ticket from the front desk.** The hotel desk (your API) doesn't carry your car to the garage. It gives you a ticket valid for one spot, for 5 minutes. You drive in yourself.

```
1. Browser → API:   "I want to upload me.jpg, image/jpeg, 2.1 MB"
2. API checks the user + type + size, picks a key (uuid), and returns a PRE-SIGNED URL
   (a URL that allows ONE upload to THAT key, for a few minutes)
3. Browser → S3:    PUT the file directly to that URL           ← Node never touches the bytes
4. Browser → API:   "done, key = 8f2c…"  (or S3 sends an event to your backend)
5. API verifies the object exists (size, type), saves metadata, maybe queues a thumbnail job
```

```js
import { PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

app.post('/uploads', requireAuth, async (req, res) => {
  const { contentType, size } = uploadSchema.parse(req.body);     // validate first
  const key = `avatars/${req.user.id}/${crypto.randomUUID()}`;
  const url = await getSignedUrl(s3, new PutObjectCommand({ Bucket, Key: key, ContentType: contentType }), { expiresIn: 300 });
  res.json({ url, key });
});
```

**Benefits:** no memory or bandwidth used on your servers, works for huge files (S3 multipart upload for multi-GB), scales automatically. **Costs:** a couple more steps, and you must verify the upload afterwards because the client did it.

For **downloads**, the same trick: pre-signed `GET` URLs for private files, or a CDN in front of public ones — don't stream every download through Node.

<a name="safety"></a>
# 5. ⭐ Safety checklist

1. **Limit size and count** — `limits` in multer, plus a body limit on your proxy. No limit = anyone can fill your memory or disk.
2. **Don't trust the file's type from the client.** Both the extension (`.jpg`) and the `Content-Type` header are just text the client sent. Check the actual bytes (the "magic number" at the start of the file) with a library like `file-type`, and allow-list the types you accept.
3. **Never use the uploaded file name as a path.** `../../app/server.js` is a valid "file name." Store under a generated id; keep the original name only as data ([Part 5.5 §7](05.5-file-system-and-paths.md)).
4. **Never serve uploads from the same origin as your app with their original type.** An uploaded `.html` or `.svg` can contain JavaScript → stored XSS. Serve user files from a separate domain/bucket, with `Content-Disposition: attachment` for downloads and `X-Content-Type-Options: nosniff`.
5. **Re-process images** (resize/re-encode with `sharp`, in a worker or queue job — it's CPU work). This also strips hidden metadata like GPS location.
6. **Scan for malware** if other users or staff will open the files (ClamAV, or your cloud's scanning service).
7. **Check permissions** — who may upload where, and who may read which file. A private file needs a private bucket + short-lived signed URLs, not a public URL that's merely hard to guess.

<a name="interview"></a>
# 6. Interview Questions & Answers

### Q1. How would you implement file uploads in a Node API?
> "For anything beyond small files, I'd have the API hand out a pre-signed S3 URL after checking the user, file type and size, let the browser upload directly to S3, then confirm and save the metadata. Node never handles the bytes, so memory and bandwidth stay flat and it works with many instances. For small files through the API, `multer` with strict limits, then straight to object storage."

### Q2. What's wrong with `multer.memoryStorage()`?
> "It holds the entire file in RAM until the handler finishes. With a few concurrent large uploads the process runs out of memory. It's acceptable only with a small, strict `fileSize` limit."

### Q3. Why not just save uploads to the server's disk?
> "Local disk isn't shared — with two instances, a file uploaded to one isn't on the other. Containers usually lose their disk on restart, and disks fill up. Uploads belong in object storage, with metadata in the database."

### Q4. How do you make sure a user didn't upload something malicious?
> "Limit size, detect the real type from the file's bytes rather than trusting the extension or Content-Type, store under a generated name, re-encode images, scan if others will open the files, and serve user content from a separate domain with `nosniff` and `attachment` so an uploaded HTML or SVG can't run scripts on my site."

### Q5. What's a pre-signed URL?
> "A URL signed with the server's credentials that grants one specific action — upload or download one object — for a short time. The client can use it directly with S3 without having any credentials of its own."

<a name="cheatsheet"></a>
# 7. Cheat Sheet

```
files arrive as multipart/form-data → express.json() can't read it → multer (busboy)
upload.single('photo') → req.file + req.body · ALWAYS set limits (fileSize, files)
LIMIT_FILE_SIZE → 413

memoryStorage = whole file in RAM (small files only)
diskStorage   = local disk (not shared, not durable)
final home    = OBJECT STORAGE (S3/GCS); DB stores key + metadata

BEST: pre-signed URL → browser uploads straight to S3 → API verifies + saves metadata
"the desk gives you a parking ticket; you park the car yourself"
downloads: pre-signed GET / CDN, not through Node

SAFETY
limit size · check real type from bytes (file-type), allow-list
generated names, never user file names as paths
serve user files from another domain + nosniff + attachment (no stored XSS)
re-encode images (sharp, in a worker) · malware scan · permissions + private buckets
```
