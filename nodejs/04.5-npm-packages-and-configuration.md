<a name="package-json"></a>
# 1. `package.json` — the project's ID card

```json
{
  "name": "orders-api",
  "version": "1.4.0",
  "type": "module",
  "main": "src/index.js",
  "engines": { "node": ">=22" },
  "scripts": {
    "start": "node src/index.js",
    "dev": "node --watch src/index.js",
    "test": "node --test"
  },
  "dependencies":    { "express": "^5.1.0" },
  "devDependencies": { "eslint": "^9.0.0" }
}
```

| Field | What it's for |
|---|---|
| `name`, `version` | identity — matters when you publish a package |
| `type` | `"module"` makes `.js` files ES modules ([Part 4 §2](04-modules.md)) |
| `main` / `exports` | which file someone gets when they `require`/`import` your package; `exports` can also **hide** internal files |
| `engines` | which Node versions the app supports — CI and some hosts check it |
| `scripts` | named commands: `npm run dev`, `npm test`, `npm start` |

<a name="deps"></a>
# 2. The three kinds of dependencies

| Section | Needed when | Example |
|---|---|---|
| `dependencies` | the app **runs** in production | express, mongoose, zod |
| `devDependencies` | only while **developing/building/testing** | eslint, jest, typescript, nodemon |
| `peerDependencies` | a **plugin** says "I work with *your* copy of X" | a React component library lists `react` |

Install production-only: `npm ci --omit=dev`. Smaller image, fewer packages that could have security holes.

> ⚠️ **Classic production bug:** code imports something that's only in `devDependencies`. Works locally (it's installed), crashes in production (it isn't). Rule: if `src/` imports it, it goes in `dependencies`.

<a name="semver"></a>
# 3. ⭐ Version numbers: `^`, `~`, and semver

**Semantic versioning — `MAJOR.MINOR.PATCH`**, e.g. `4.18.2`:

```
4   . 18   . 2
│     │      └── PATCH — bug fix, nothing else changes
│     └───────── MINOR — new feature, old code still works
└─────────────── MAJOR — breaking change, old code may break
```

What the symbols in `package.json` allow:

| You write | npm may install | Memory trick |
|---|---|---|
| `"4.18.2"` | exactly 4.18.2 | pinned |
| `"~4.18.2"` | 4.18.x (patches only) | **~ = "about this version"** |
| `"^4.18.2"` | 4.x.x (minor + patch) — npm's default | **^ = "up to the next major"** |
| `"*"` / `"latest"` | anything | ❌ never in a real project |

⚠️ **Special case for `0.x`:** `^0.4.2` only allows `0.4.x`. Before 1.0, every minor bump is treated as possibly breaking.

**Semver is a promise, not a guarantee.** A package author can break things in a "minor" release by accident. That's exactly why the lockfile (next) exists.

<a name="lockfile"></a>
# 4. ⭐ The lockfile, and `npm ci` vs `npm install`

`^4.18.2` is a **range**. Today it might install 4.18.2; next month 4.21.0. So two developers — or your laptop and the server — could get different code.

**`package-lock.json` records the exact version of every package**, including the dependencies of your dependencies (hundreds of them), plus a checksum of each.

> **Analogy 🧾 — a shopping list vs a receipt.** `package.json` is the list: "some milk, about 1 litre." The lockfile is the receipt: "Amul Gold, 1L, batch #4417." To get exactly the same groceries again, you shop from the receipt.

| Command | Reads | Changes the lockfile? | Use it |
|---|---|---|---|
| `npm install` | `package.json` (+ lockfile as a hint) | yes, if something changed | while developing, to add/update packages |
| `npm ci` | **the lockfile only** | never — fails if it doesn't match `package.json` | **CI and production builds** |

`npm ci` also deletes `node_modules` first, so every build starts clean and gets exactly the receipt.

Rules:
- ✅ **Commit `package-lock.json`.** Always, for applications.
- ✅ Use `npm ci` in Dockerfiles and CI.
- ✅ Update deliberately: `npm outdated` → `npm update` (within ranges) or `npm install pkg@latest` (major), then run the tests.
- Security checks on dependencies (`npm audit`, typo-squatting) → [Part 7.5 §7](07.5-security-beyond-auth.md).

<a name="scripts"></a>
# 5. Scripts, `npx`, and useful commands

```bash
npm run dev            # runs scripts.dev
npm test / npm start   # shortcuts for scripts.test / scripts.start
npm run build -- --watch   # everything after -- is passed to the script
```

- Scripts can use packages from `node_modules/.bin` directly — `"lint": "eslint ."` works without a global install.
- `pre` / `post` hooks: a `pretest` script runs automatically before `test`.

**`npx <tool>`** runs a package's command. It uses the project's installed copy if there is one, otherwise downloads it temporarily: `npx prisma migrate dev`, `npx create-vite@latest`.

| Command | Does |
|---|---|
| `npm ls express` | why/where a package is installed (the dependency tree) |
| `npm outdated` | what has newer versions |
| `npm why <pkg>` (alias: `npm explain`) | which of your dependencies pulled it in |
| `npm pkg get version` | read a field from `package.json` |

<a name="config"></a>
# 6. ⭐ Configuration: environment variables done right

**Config = anything that changes between environments** (local, staging, production): database URL, port, API keys, feature flags. Keep it **out of the code** and pass it in through **environment variables**. The same build then runs everywhere. (This is one of the "12-factor app" rules.)

### The three traps of `process.env`

```js
process.env.PORT          // "3000"   ← a STRING, not a number
process.env.DEBUG         // "false"  ← a non-empty string → TRUTHY 😱
process.env.DB_URL        // undefined if you forgot to set it → crashes 3 calls deep
```

### The fix: read and check everything once, at startup

```js
// config.js — the ONLY file that touches process.env
import { z } from 'zod';

const schema = z.object({
  NODE_ENV:     z.enum(['development', 'test', 'production']).default('development'),
  PORT:         z.coerce.number().int().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET:   z.string().min(32),
  DEBUG:        z.enum(['true', 'false']).default('false').transform(v => v === 'true'),
});

export const config = schema.parse(process.env);   // ❌ missing/bad value → crash NOW, with a clear message
```

Everywhere else: `import { config } from './config.js'` → `config.PORT` is a real number, `config.DEBUG` a real boolean.

> 🧠 **Remember:** **fail at boot, not at 3 a.m.** A bad config should stop the deploy in the first second, not break the first user who hits that code path.

### Loading a `.env` file locally

```bash
node --env-file=.env src/index.js      # built into Node 20.6+ — no dotenv package needed
```

```
# .env  (local only — never committed)
DATABASE_URL=postgres://localhost/orders
JWT_SECRET=dev-only-secret-at-least-32-characters-long
```

- Commit a **`.env.example`** with the variable names and fake values, so new developers know what to set.
- Put `.env` in `.gitignore`.
- In production, the platform sets the variables (Kubernetes, Docker, your cloud's settings page) — there is no `.env` file there.

**`NODE_ENV=production`** matters: Express and many libraries switch on it (Express caches view templates and hides error details; some libraries skip expensive debug checks). Always set it in production.

<a name="secrets"></a>
# 7. Secrets

Secrets = passwords, API keys, signing keys, DB credentials.

- ❌ **Never in git** — not in code, not in a committed `.env`. Git history keeps them forever, even after you delete the file. If one leaks: **rotate it** (make a new one, revoke the old one); deleting the commit is not enough.
- ❌ **Never in logs** — redact them ([Part 10.5 §3](10.5-logging-and-observability.md)).
- ❌ **Never baked into a Docker image** (`ENV API_KEY=...` in a Dockerfile) — anyone with the image can read it.
- ✅ Store them in a **secret manager** (AWS Secrets Manager, GCP Secret Manager, Vault, Kubernetes Secrets) and inject them as environment variables or files at runtime.
- ✅ Give each environment its own secrets — a staging leak shouldn't open production.
- ✅ Turn on secret scanning (GitHub does this) to catch accidental commits.

<a name="interview"></a>
# 8. Interview Questions & Answers

### Q1. What's the difference between `^1.2.3` and `~1.2.3`?
> "`~1.2.3` allows patch updates only — 1.2.x. `^1.2.3` allows minor and patch — anything below 2.0.0. The caret is npm's default because, by semver, minor versions shouldn't break anything. One exception: for 0.x versions, `^0.4.2` only allows 0.4.x."

### Q2. Why commit `package-lock.json`?
> "Because `package.json` only has ranges. The lockfile records the exact version of every package in the tree, so every developer, CI run and production build installs identical code. Without it, a dependency can release a new version between your test and your deploy and you ship something you never tested."

### Q3. `npm install` vs `npm ci`?
> "`npm install` resolves from `package.json` and may update the lockfile — it's for development. `npm ci` installs exactly what the lockfile says, deletes `node_modules` first, and fails if the lockfile and `package.json` disagree — so it's reproducible, which is what you want in CI and Docker builds."

### Q4. `dependencies` vs `devDependencies`?
> "`dependencies` are needed at runtime in production; `devDependencies` only for development, building and testing. Production installs skip dev ones with `--omit=dev`. A common bug is importing a dev-only package from app code — it works locally and crashes in production."

### Q5. How do you manage configuration in a Node app?
> "Environment variables, read in one config module at startup and validated with a schema — converting types, because everything in `process.env` is a string. If anything is missing or invalid the app refuses to start, so the problem shows up at deploy time instead of in a user's request. Locally I load a `.env` with `node --env-file`; in production the platform injects the variables."

### Q6. A secret was committed to git. What do you do?
> "Rotate it immediately — generate a new one and revoke the old — because it's in the history and possibly already cloned or scanned. Then clean the history if needed, move the secret to a secret manager, and add secret scanning so it can't happen silently again."

### Q7. Why does `NODE_ENV=production` matter?
> "Libraries change behaviour on it. Express hides error details and caches templates, and many packages skip development-only checks and warnings. Forgetting it in production can mean slower performance and leaked stack traces."

<a name="cheatsheet"></a>
# 9. Cheat Sheet

```
MAJOR.MINOR.PATCH   breaking . feature . fix
"1.2.3" exact · "~1.2.3" → 1.2.x · "^1.2.3" → 1.x.x (default) · ^0.4.2 → 0.4.x only

package.json = shopping list (ranges) · package-lock.json = receipt (exact) → COMMIT IT
npm install = dev, may change lock · npm ci = CI/prod, exact, clean, never changes lock
dependencies = runtime · devDependencies = dev/build/test · peerDependencies = plugins
prod install: npm ci --omit=dev
npx = run a package's command (local copy first, else temporary download)

CONFIG
env vars, not code · ONE config module · validate + convert types at boot (zod)
process.env values are ALWAYS strings ("false" is truthy!)
local: node --env-file=.env · commit .env.example, gitignore .env
NODE_ENV=production in prod
"Fail at boot, not at 3 a.m."

SECRETS
never in git / logs / Docker images · secret manager · per-environment · leaked → ROTATE
```
