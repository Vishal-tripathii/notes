<a name="pillars"></a>
# 1. The three pillars: logs, metrics, traces

> **Analogy 🏥 — a hospital patient.** **Metrics** are the heart-rate monitor: numbers over time that tell you *something* is wrong. **Logs** are the nurse's notes: what happened, when, with details. **Traces** are the patient's path through the hospital: reception → X-ray → doctor → pharmacy, with how long each step took.

| | Answers | Example |
|---|---|---|
| **Metrics** | "Is something wrong? How bad?" | p99 latency jumped from 120ms to 2s; error rate 4% |
| **Logs** | "What exactly happened?" | `payment failed for order 812: card_declined` |
| **Traces** | "Where did the time go across services?" | 1.8s of the 2s was a call to the inventory service |

You usually go **metrics → traces → logs**: an alert fires on a metric, a trace shows which service/step is slow, logs for that request explain why.

<a name="structured"></a>
# 2. ⭐ Structured logging with pino

`console.log('user ' + id + ' paid ' + amount)` produces text that's hard to search across millions of lines. **Structured logs** are JSON objects with fields you can filter on.

```js
import pino from 'pino';
export const logger = pino({ level: process.env.LOG_LEVEL ?? 'info' });

logger.info({ userId: 42, orderId: 812, amountCents: 4999 }, 'payment succeeded');
// {"level":30,"time":1763900000000,"userId":42,"orderId":812,"amountCents":4999,"msg":"payment succeeded"}
```

Now your log tool can answer "all failed payments for user 42 in the last hour" in one query.

**Why pino:** it's very fast, and logging happens on every request, so a slow logger slows everything. (`winston` is also common and more configurable, but slower.)

- **Pretty output only in development:** `node app.js | pino-pretty`. Production logs stay JSON.
- **Write to stdout.** In containers, the platform collects stdout and ships it to your log system (Datadog, Loki, CloudWatch, ELK). Don't make the app manage log files.
- **Log errors as objects** so the stack is kept: `logger.error({ err }, 'failed to charge card')` — not `logger.error(err.message)`.
- For HTTP: **`pino-http`** logs every request and response (method, url, status, duration) automatically and gives each request its own child logger, `req.log`.

<a name="what"></a>
# 3. What to log — and what never to log

**Log at the boundaries:**
- each incoming request and its response (status, duration) — `pino-http` does this
- each call to another system (DB, API, queue) that fails or is slow
- important business events: "order placed", "payment refunded", "user deleted account"
- every error, with context (ids, what was being attempted)
- startup (version, config **names**, not secret values) and shutdown

**Never log:**
- passwords, tokens, API keys, session ids, cookies, `Authorization` headers
- full card numbers, government ids, health data — and be careful with emails/phone numbers (privacy laws)
- whole request bodies by default (they often contain the above)

Logs are usually seen by more people, kept longer, and protected less than the database. pino can **redact** fields automatically:

```js
pino({ redact: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token'] });
```

**Don't log too much either:** logging inside tight loops or every cache hit costs money and buries the important lines. Log events, not steps.

<a name="levels"></a>
# 4. Log levels

| Level | Use for |
|---|---|
| `fatal` | the app is about to exit (uncaught exception — [Part 2.5 §8](02.5-eventemitter-process-and-errors.md)) |
| `error` | something failed and needs attention — a bug, or a dependency down |
| `warn` | unusual but handled — retry succeeded, deprecated API used, slow query |
| `info` | normal important events — request completed, order placed, server started |
| `debug` | detailed info for developers — off in production |
| `trace` | extremely detailed — almost never on |

Production usually runs at `info`. Make the level changeable via config, so you can turn on `debug` briefly while investigating.

> 🧠 **Remember:** if it would wake someone up → `error`. If it's interesting later → `info`. If it's only for you while coding → `debug`.

<a name="request-id"></a>
# 5. ⭐ Request IDs — following one request

Your server handles hundreds of requests at once, so their log lines are **interleaved**. Without a shared id, you can't tell which lines belong to which request.

**Give every request an id, put it on every log line, and pass it on to every service you call:**

```
client → API (reqId=7f3a) → orders service (x-request-id: 7f3a) → payments (x-request-id: 7f3a)
search logs for reqId=7f3a → the whole story, across all three services
```

```js
import pinoHttp from 'pino-http';
import { randomUUID } from 'node:crypto';

app.use(pinoHttp({
  logger,
  genReqId: (req, res) => {
    const id = req.headers['x-request-id'] ?? randomUUID();   // reuse the caller's id if there is one
    res.setHeader('x-request-id', id);                         // return it — support can ask users for it
    return id;
  },
}));

app.get('/orders/:id', async (req, res) => {
  req.log.info({ orderId: req.params.id }, 'loading order');   // reqId is attached automatically
});
```

Also called a **correlation id**. Include it in error responses too (`{ "error": {...}, "requestId": "7f3a" }`) so a user's bug report leads straight to the logs.

<a name="als"></a>
# 6. ⭐ AsyncLocalStorage — context without passing it around

**The problem:** a service deep down — `paymentService.charge()` → `db.save()` → `logger.info()` — wants the request id (or the current user, or the tenant). Passing `req` through every function call is ugly and leaks HTTP into business code.

**`AsyncLocalStorage`** (from `node:async_hooks`) gives each request its own **"invisible backpack"** that follows it through every `await`, callback and timer — without passing anything.

```js
import { AsyncLocalStorage } from 'node:async_hooks';
export const requestContext = new AsyncLocalStorage();

// middleware: start a context for this request
app.use((req, res, next) => {
  requestContext.run({ reqId: req.id, userId: req.user?.id }, next);
});

// anywhere deeper, in any file, after any number of awaits:
export function log() {
  const ctx = requestContext.getStore();     // { reqId, userId } of THIS request
  return logger.child({ reqId: ctx?.reqId, userId: ctx?.userId });
}

// paymentService.js
await stripe.charge(...);
log().info('charged');                       // has the right reqId — no parameters passed
```

Two requests running at the same time each see **their own** store, even though they share one thread and interleave on the event loop.

Uses: request-scoped logging, the current user/tenant for authorization or multi-tenant queries, tracing (OpenTelemetry uses this mechanism internally). It has a small performance cost and is stable and widely used.

> 🧠 **Remember:** `run(store, fn)` puts on the backpack; `getStore()` looks inside it — from anywhere in that request's async journey.

<a name="metrics"></a>
# 7. Metrics — the numbers on the dashboard

**The four golden signals** (from Google's SRE book) — watch these for every service:

| Signal | Question | Example metric |
|---|---|---|
| **Latency** | how slow? | p50 / p95 / **p99** request duration ([Part 9 §1](09-performance.md)) |
| **Traffic** | how busy? | requests per second |
| **Errors** | how broken? | % of 5xx responses |
| **Saturation** | how full? | CPU, memory, DB pool usage, **event loop lag** |

**Node-specific ones:** event loop lag (`perf_hooks.monitorEventLoopDelay` — [Part 9 §6](09-performance.md)), heap used, GC pause time, active handles, DB connection pool waiting count.

Typical setup: **`prom-client`** exposes a `/metrics` endpoint that **Prometheus** scrapes, and **Grafana** draws the charts — or a hosted tool (Datadog, New Relic) via an agent. `prom-client`'s `collectDefaultMetrics()` gives event loop lag, heap and GC numbers for free.

⚠️ **Don't put unbounded values in metric labels** (user id, full URL with ids). Every unique label value creates a new time series; millions of them overload the metrics system. Use the route pattern `/orders/:id`, not `/orders/812`.

<a name="tracing"></a>
# 8. Distributed tracing with OpenTelemetry

With several services, "the request took 2 seconds" isn't enough — you need **where**. A **trace** is one request's journey; each step (an HTTP call, a DB query) is a **span** with a start time and duration.

```
trace 7f3a  ───────────────────────────────── 2000 ms
 ├─ API: GET /checkout                         2000 ms
 │   ├─ mongo: orders.findOne                    12 ms
 │   ├─ HTTP: inventory-service /reserve       1800 ms   ← here
 │   │   └─ postgres: UPDATE stock             1750 ms   ← really here (lock wait)
 │   └─ redis: SET                                2 ms
```

**OpenTelemetry (OTel)** is the standard. Its Node SDK **auto-instruments** Express, `http`/`fetch`, MongoDB, Postgres, Redis and more — you add a few lines at startup and get spans without changing your code. It passes the trace id between services in the `traceparent` header (W3C standard), and sends data to Jaeger, Tempo, Datadog, Honeycomb, etc.

Put the **trace id in your logs** too, and you can jump from a slow trace straight to its log lines.

<a name="alerts"></a>
# 9. Alerts

- **Alert on symptoms users feel** — high error rate, high p99 latency, queue backlog growing — not on every internal cause (CPU at 80% might be fine).
- Every alert should be **actionable**: someone receiving it at 3 a.m. knows what it means and what to check. Link a runbook.
- Too many noisy alerts → people ignore all of them. Tune or delete alerts that fire without needing action.
- Track **SLOs** (e.g. "99.9% of requests succeed in under 500ms") and alert when you're burning through the error budget too fast.

<a name="interview"></a>
# 10. Interview Questions & Answers

### Q1. Why structured logging instead of `console.log`?
> "Structured logs are JSON with named fields, so a log system can filter and aggregate them — 'all errors for order 812' or 'count of payment failures by reason.' Plain strings need fragile text searches. I use pino because it's fast, write to stdout, and let the platform ship the logs."

### Q2. What should never be logged?
> "Secrets and credentials — passwords, tokens, API keys, cookies, Authorization headers — and sensitive personal data like card numbers. Logs are kept longer and protected less than the database. I avoid logging whole request bodies and use the logger's redaction for known sensitive fields."

### Q3. What's a correlation or request ID?
> "A unique id for each incoming request, attached to every log line it produces, returned in a response header and forwarded to downstream services. With it, one search shows a request's entire path across services, and a user can quote it in a bug report."

### Q4. How do you get the request id into logs deep inside services without passing `req` everywhere?
> "`AsyncLocalStorage`. A middleware calls `run()` with a store holding the request id and user, and any code later in that request's async chain calls `getStore()` to read it. Concurrent requests each see their own store. OpenTelemetry uses the same mechanism for trace context."

### Q5. What metrics would you watch for a Node service?
> "The four golden signals — latency percentiles, traffic, error rate, saturation — plus Node-specific ones: event loop lag, heap usage and GC pauses, and DB connection pool waits. Event loop lag is the one that reveals a blocked loop when everything else looks normal."

### Q6. Logs vs metrics vs traces?
> "Metrics are cheap numbers over time that tell you something's wrong. Traces show where time went across services for a request. Logs give the detailed story of what happened. Usually an alert on a metric leads me to a trace, and the trace to the logs for that request."

### Q7. What makes a good alert?
> "It's based on something users feel — error rate or latency — and it's actionable, with a runbook. Alerts that fire often without needing action get ignored, so I'd rather have a few reliable ones tied to SLOs."

<a name="cheatsheet"></a>
# 11. Cheat Sheet

```
METRICS = heart monitor ("something's wrong") · TRACES = patient's path ("where") · LOGS = nurse's notes ("what")
usual flow: alert on metric → trace → logs

LOGS
pino, JSON, stdout · pino-pretty only in dev · pino-http for requests (req.log)
logger.error({ err }, 'msg')  ← keep the stack
log boundaries: requests, external calls, business events, errors, startup
NEVER: passwords, tokens, keys, cookies, auth headers, card numbers, full bodies → redact
levels: fatal · error (wake someone) · warn · info (prod default) · debug · trace

REQUEST ID
reuse x-request-id or generate · on every log line · return in header + error body · forward downstream

AsyncLocalStorage = per-request "invisible backpack"
run(store, next) in middleware → getStore() anywhere later in that request

METRICS — golden signals: latency (p99) · traffic · errors · saturation
Node: event loop lag · heap · GC · pool waits · prom-client → Prometheus → Grafana
no user ids / raw URLs in labels (cardinality)

TRACING — OpenTelemetry auto-instruments express/http/mongo/redis · spans · traceparent header
trace id in logs

ALERTS — on user-facing symptoms · actionable + runbook · few and reliable · SLOs
```
